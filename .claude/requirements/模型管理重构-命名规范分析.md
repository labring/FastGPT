# 模型管理重构 — model/modelId 命名规范分析

> 状态：**部分执行（2026-08，用户裁决）**。原「暂不执行改名」结论经评审后按用户决策调整为：**仅执行嵌套响应字段改名**（`deepSearchResult.modelId/model` → `llmModelId/llmModelName`、`imageCaptionResult.modelId/model` → `vlmModelId/vlmModelName`，含类型/写入方/消费方/测试），**回滚并放弃顶层字段改名**（`DispatchNodeResponseSchema` 顶层 `modelId/model`、`CreateAgentLoopCoreToolCallNodeResponseParams` 等参数名、`vectorModelId→embeddingModelId`、`SearchDatasetDataProps`）——顶层/参数名/持久化字段改名波及面大而收益有限，按「改动最小化」原则保留现状。已执行项见 §三.1，未执行项维持本文档原结论。

## 命名规则（用户定义）

1. 模型类型 `MODEL_TYPE` 为前缀（如果无法区分才忽略前缀）
2. `{MODEL_TYPE}ModelName`：模型名称，对应 `modelData.model`（provider 内标识）
3. `{MODEL_TYPE}ModelAlias`：模型别名，对应 `modelData.name`（展示名）
4. `{MODEL_TYPE}Model`：对应 `modelData` 本身（完整对象）

## 规则修订建议（subagent 分析得出，待用户确认）

> ⚠️ **规则 4 与现状冲突**：代码库中"字符串模型名"用 `model` 字段表示是根深蒂固的惯例（`ChatNodeUsageType.model`、`SelectedDatasetSchema.vectorModel.model`），直接套用"规则 4"会大面积破坏。建议把规则 4 拆为：
> - `{MODEL_TYPE}ModelName` = provider 模型名（`modelData.model`）—— 运行时响应字段一律用此
> - `{MODEL_TYPE}Model` 保留给完整对象，仅在函数参数中使用
> - 运行时结果字段中的 `{MODEL_TYPE}Model` 指 provider 模型名（如 `queryExtensionResult.llmModel`/`embeddingModel` 已如此用）

## 三、关键风险点与结论

> ✅ **已执行（2026-08，用户裁决）**：仅第 1 条的**嵌套字段**部分落地 —— `deepSearchResult.modelId/model` → `llmModelId/llmModelName`、`imageCaptionResult.modelId/model` → `vlmModelId/vlmModelName`（类型 runtime/type.ts + search/type.ts、写入方 defaultRecall/imageCaption.ts + defaultRecall/index.ts、消费方 dispatch/dataset/search.ts + agent/sub/dataset/index.ts + searchTest.ts、合并方 mergeNode.ts、测试同步）。顶层字段与 vectorModelId 部分按裁决**放弃**（改动最小化）。

1. **最值得改的 3 处**（成本低、收益大）：
   - ~~`DispatchNodeResponseSchema` 顶层 `modelId` → `llmModelId`、`model` → `llmModelName`（type.ts:77-78）~~ — **放弃（用户裁决）**：波及 10+ 写入方/参数名/前端展示，收益有限
   - `deepSearchResult.modelId` → `llmModelId`、`imageCaptionResult.modelId` → `vlmModelId`（search/type.ts:70-80 + runtime/type.ts:116-123）— **已执行**
   - ~~`searchTest.ts` 两处 FIXME 依赖上述改名自动消除~~ — searchTest.ts 无残留 FIXME，已随改名同步

2. **历史遗留但影响面大**：`vectorModelId`/`vectorModel`（dataset schema + search props + 前端快照）应统一为 `embedding*` 前缀，但涉及 Mongo 字段、工作流快照结构和前端多组件 —— **放弃（用户裁决）**，维持现状。

3. **规则修订建议**：现状中 `llmModel`/`embeddingModel`（queryExtensionResult）与 `model`（顶层/deepSearchResult）都表示"provider 模型名字符串"。代码库中"字符串模型名"用 `model` 字段表示是根深蒂固的惯例（`ChatNodeUsageType.model`、`SelectedDatasetSchema.vectorModel.model`），直接套用"规则 4"会大面积破坏。建议把规则 4 拆为：`{MODEL_TYPE}ModelName` = provider 模型名（modelData.model），`{MODEL_TYPE}Model` 保留给完整对象仅在函数参数中使用；运行时响应字段一律用 `{MODEL_TYPE}ModelName`。

4. **LLM 请求链路**（已按评审决策重构，2026-08）：`LLMRequestBodyType` 不再含 model/modelId，wire body 的 `model` 由 `llmCompletionsBodyFormat(input, modelData)` 从 `modelData.model` 解析；`CreateLLMResponseProps` 携带 `modelData: LLMModelItemType` 显式传入。
