## 1. 当前架构分析

### 1.1 数据模型（现状）

**MongoDB Schema** — `packages/service/core/ai/config/schema.ts:1-26`

```typescript
// 集合: system_models
{
  model: { type: String, required: true, unique: true },  // 唯一索引，业务主键
  metadata: { type: Object, required: true, default: {} }  // 所有配置嵌套于此
}
```

核心问题：
- `model` 字段（如 `"gpt-4o"`）同时承担唯一标识、查找 key、关联外键三重角色
- 多个自定义模型共用同一 OpenAI model 名时，`unique: true` 导致写入冲突
- `metadata: Object` 无 Schema 约束，运行时依赖 Zod 校验，存在类型断层

### 1.2 全局缓存结构（现状）

**文件**: `packages/service/core/ai/config/utils.ts:28-298`

`loadSystemModels()` 函数构建 5 个全局 Map，均以 **model 名字符串** 为 key：


### 1.5 完整调用链（现状）

从 API 请求到 LLM 调用的 model 参数传递路径（5 层）：

```
API 层 (model: "gpt-4o") → 缓存加载 (pushModel 写 5 个 Map, key=model 名)
  → 工作流 Dispatch (getLLMModel("gpt-4o")) → LLM 请求 (body.model = modelData.model)
  → 计费层 (findAIModel("gpt-4o") 遍历 5 个 Map)
```

关键特征：model 名字符串在每一层都是查找 key；多个自定义模型共用同一 OpenAI model 名时存在歧义。

### 1.8 模型→API 连接（现状）

当前架构中，模型直接携带 `requestUrl` 和 `requestAuth` 字段（存储在 `metadata` 内），各 AI 调用模块自行读取并覆盖默认的 API 端点。

**默认 API 客户端** — `packages/service/core/ai/config.ts:29-48`

```typescript
// getAIApi 创建 OpenAI 客户端，使用环境变量中的默认 baseUrl/apiKey
const baseUrl = userOpenAIAccount?.baseUrl || global?.systemEnv?.oneapiUrl || openaiBaseUrl;
const apiKey = userOpenAIAccount?.key || global?.systemEnv?.chatApiKey || openaiBaseKey;
return { ai: new OpenAI({ baseURL: baseUrl, apiKey, ... }), requestMeta };
```

**模型级覆盖机制** — 各模块在调用时检查 `modelData.requestUrl`/`modelData.requestAuth`，非空时覆盖默认端点：

| 模块 | 文件 | 覆盖方式 |
|------|------|---------|
| LLM Chat | `ai/llm/request/createChatCompletion.ts:42-48` | `path: modelData.requestUrl` + `Authorization: Bearer ${modelData.requestAuth}`（仅非用户自有 key 时） |
| Embedding | `ai/embedding/index.ts:90-94` | `path: model.requestUrl` + `Authorization: Bearer ${model.requestAuth}` |
| Rerank | `ai/rerank/index.ts:97-108` | 替换完整 `requestUrl` + `Authorization` header |
| TTS Speech | `ai/audio/speech.ts:34-38` | `path: modelData.requestUrl` + `Authorization` |
| STT Transcribe | `ai/audio/transcriptions.ts:31-35` | 替换完整 `requestUrl` + `Authorization` |

**脱敏处理** — `loadSystemModels()` 在构建 `systemActiveDesensitizedModels` 时主动清除这两个字段（`config/utils.ts:230-231`），确保前端不可见。
> ⚠️ **实现修订（经评审确认，2026-08）**：requestUrl/requestAuth 已从模型 schema 移除（由 Channel 管理，见 §2.9），且 `systemActiveDesensitizedModels` 无消费方已删除——脱敏需求由「模型不再存储密钥字段」从源头满足。

**核心问题**：
- 接入信息与模型配置耦合，同一 provider 的多个模型需重复配置相同的 URL/Auth
- 无统一的渠道管理，无法做负载均衡、熔断、速率控制
- 自定义模型（`isCustom: true`）的接入信息混在模型配置中，权限边界模糊

## 2. 目标架构设计

> 本章为设计概要。详细定义（完整 Schema、Zod 校验、API 路由）见引用的详细设计文档。

### 2.1 新数据模型（MongoDB Schema）

**文件**: `packages/service/core/ai/model/schema.ts`（重构后，由 `config/schema.ts` 改名）

核心设计原则：
- **strict: false** — Schema 仅声明所有模型类型共享的 base 字段和价格字段。类型特有字段（如 `maxContext`、`voices`、`dimensions` 等）由 Zod schema 在写入前校验，动态存储在 MongoDB 文档中。
- **移除 `unique: true`** — `model` 字段不再唯一，允许不同团队创建指向同一 provider model 的模型配置。
- **移除 `requestUrl` / `requestAuth`** — 模型不再直接携带接入信息，统一由渠道（channel）维护。
- **移除 `isDefault`** — 默认模型由独立的系统默认模型表管理（见 2.4 节）。
- **`isSystem` 替换 `isCustom`** — `isSystem: true` 表示 root 创建的全平台公开模型，非 root 用户仅可读取（`getModelPermission` 返回 `ReadRoleVal`），全平台用户均可使用。
- **系统模型不维护 `tmbId` 和 `teamId`** — `isSystem: true` 的模型不属于任何团队或个人，不存储创建者和团队信息，全平台共享。

Schema 仅声明所有模型类型共享的 base 字段（`model`、`type`、`provider`、`name`、`avatar`、`isActive`、`isSystem`、`testMode`）。`tmbId` 和 `teamId` 仅在 `isSystem: false` 时存储（私有模型）。价格字段（`charsPointsPrice`、`priceTiers`）。类型特有字段（如 `maxContext`、`voices` 等）由 Zod schema 在写入前校验，通过 `strict: false` 动态存储。索引覆盖 `teamId`、`tmbId`、`{isActive, provider}`，移除 model 字段的 unique 索引。

> 完整 Schema、各类型特有字段定义及 Zod 校验规则见 [模型管理重构-详细设计-数据模型.md](./模型管理重构-详细设计-数据模型.md)。

### 2.3 全局缓存重构

**文件**: `packages/service/core/ai/model/utils.ts`（重构后）

> ⚠️ **实现修订（热升级兼容，2026-08）**：本节原稿「移除全部 name-keyed Map」在热升级窗口内改为「**id map 为主、name 兼容索引为辅**」的双 map 结构（见 §9.3 与[热升级技术分析 §6.2](./模型管理重构-热升级技术分析.md#62-缓存双-map-与-normalization)）：
> - 以 id（`_id.toString()`）为 key 的 `*ModelIdMap` 是唯一权威索引，所有新代码路径读取；
> - 同时构建 `model → modelData`（provider model 名）与 `name → modelData`（别名）**只读兼容索引**，供 getters 在接收 legacy 名字符串时解析（§2.5），并为 `resolveModelId` 提供快速路径；
> - 同一名字对应多个模型时 active/system 优先、first-wins，与迁移 Step 3 映射规则一致；
> - 兼容索引标记 `@deprecated`，随后续 contract release 与 legacy 字段一并移除。

**核心变更**：

1. **以 modelId 为 key 的 Map**（权威索引，key = `_id.toString()`）：
   - ~~`global.llmModelMap`~~ → `global.llmModelIdMap`
   - ~~`global.embeddingModelMap`~~ → `global.embeddingModelIdMap`
   - ~~`global.ttsModelMap`~~ → `global.ttsModelIdMap`
   - ~~`global.sttModelMap`~~ → `global.sttModelIdMap`
   - ~~`global.reRankModelMap`~~ → `global.reRankModelIdMap`

2. **新增统一索引 Map**：
   ```typescript
   global.systemModelIdMap = new Map<string, SystemModelItemType>()
   // 每个模型同时写入: systemModelIdMap.set(id, model)
   ```

3. **name → modelData 兼容索引**（仅热升级窗口期保留）：
   ```typescript
   // @deprecated — 仅用于兼容存量 model 名字符串引用，contract release 时移除
   global.llmModelNameMap = new Map<string, LLMModelItemType>()        // key = model.model / model.name
   global.embeddingModelNameMap = new Map<string, EmbeddingModelItemType>()
   global.ttsModelNameMap = new Map<string, TTSModelType>()
   global.sttModelNameMap = new Map<string, STTModelType>()
   global.reRankModelNameMap = new Map<string, RerankModelItemType>()
   // 同一 model 名/别名命中多个文档时：isActive=true 优先、isSystem=true 优先、first-wins
   ```
   该索引在 `loadSystemModels` 中与 id map 同源构建（同一份 normalization 输出），不在迁移前从数据库读取任何额外字段。

4. **模型配置模板独立缓存** — plugin 提供的原始模型定义不再 push 到已创建模型的缓存列表中，而是单独缓存为 `global.modelTemplateCache`：
   ```typescript
   // pluginClient.listModels() 的结果 → global.modelTemplateCache
   // 用于前端"新建模型"时查询可用模板并填充表单
   global.modelTemplateCache: ModelTemplateType[]
   ```

5. **默认模型加载** — 新增从 `default_models` 表读取系统级默认模型的逻辑（见 2.4 节）。

> 完整的缓存加载流程（`loadSystemModels` 重构后的伪代码）见 [模型管理重构-详细设计-缓存.md](./模型管理重构-详细设计-缓存.md)。

### 2.4 默认模型表

**系统级默认模型**统一存储在 `default_models` 集合中，包含 `llmId`、`embeddingId`、`ttsId`、`sttId`、`rerankId`、`datasetTextLLMId`、`datasetImageLLMId`、`chatTitleLLMId`、`helperBotLLMId` 九个字段（均为 ObjectId 字符串）。

**默认模型解析**：
- `loadDefaultModels()` 启动时从 `default_models` 集合读取
- **显式配置优先**，未配置的 → 回退到首个启用的同类型系统模型（`type=target, isSystem=true, isActive=true`）
- 无可用模型时返回 `undefined`
- 调用方通过 `getDefaultLLMModel()` 等获取，返回 `undefined` 时自行处理

### 2.5 模型查找函数重构

**文件**: `packages/service/core/ai/model/cache.ts`（重构后，由 `model.ts` 改名）

参数从 `model?: string`（model 名字符串，可选，空时回退默认模型）改为 `modelId: string`（ObjectId 字符串，必填，不做回退）。调用方需自行决定何时使用默认模型。

> ⚠️ **实现修订（热升级兼容，2026-08）**：getter 签名在热升级窗口期保持 `getXXXModel(modelIdOrName: string)` 兼容输入——参数为有效 ObjectId 时查 id map，未命中且参数不是 ObjectId 时按 provider model 名/别名查 name 兼容索引（§2.3 的 `*ModelNameMap`），仍未命中返回 `undefined`：
> - 存量 Workflow input（W0 `model` key + name value）、Dataset legacy 字段（D0）、chatConfig legacy `model` 均可直接运行，无需先迁移；
> - 新代码路径一律传 modelId，行为与原设计一致；
> - 兼容解析逻辑集中在一处（getter 内部），所有消费方经同一入口，不做逐调用点 fallback；
> - `assertModelUsable` 报错语义不变：无法解析仍显式失败，不静默回退默认模型。

**函数签名变更总览**：

| 函数 | 旧签名 | 新签名 |
|------|--------|--------|
| `getLLMModel` | `(model?: string) => LLMModelItemType` | `(modelId: string) => LLMModelItemType \| undefined` |
| `getEmbeddingModel` | `(model?: string) => EmbeddingModelItemType` | `(modelId: string) => EmbeddingModelItemType \| undefined` |
| ... 等模型获取函数 | 同模式 | model->modelId; 返回类型增加 `\| undefined` |

```typescript
// getModelPermission — 核心权限计算
// authModelByTmbId  — 单模型鉴权（含 resourceContext 绕过）
// authModel         — 带 Header 解析的单模型鉴权
```

**核心规则**：

| 模型类型 | root | 创建者/团队 owner | 协作者 | 普通成员 |

| 系统模型 (`isSystem: true`) | 全部权限 | 可使用 | 可使用 | 可使用 |

**`getModelPermission` 决策流程**：

```
getModelPermission(model, teamId, tmbId, isRoot, tmbPer)
├── isRoot?                         → isOwner: true（全部权限）
├── model.isSystem?                 → ReadRoleVal（全平台可读，不可写/管理）
├── tmbPer.isOwner OR model.tmbId === tmbId? → isOwner: true
├── model.teamId !== teamId?        → 无权限（非本团队模型不可访问）
└── getTmbPermission(...)           → 协作者角色位掩码 ?? 0（未配置则无权限）
```

### 2.9 渠道（Channel）系统（关联重构项）

> Channel 系统（aiproxy）是模型重构的关键关联项——模型不再直接携带 `requestUrl`/`requestAuth`（见 [1.8 节](#18-模型api-连接现状)），统一由 Channel 维护接入信息。

> ⚠️ **修订说明**：本节原稿基于「aiproxy 基于 modelId 查找对应 Channel 并转发请求」的假设。经对接 aiproxy 源码核实（`/data/home/cz/aiproxy`），**aiproxy 渠道通过 `models: []string`（上游模型名）绑定模型，relay 按上游模型名路由，请求体中的 `modelId` 字段 aiproxy 不消费**。2.9.2 的关联机制已按此重写：模型-渠道关联的对外口径仍为 FastGPT `modelId`，通过 owner 推导实现，无需 aiproxy 支持 modelId。

**关联要点**：

| 关联项 | 说明 |
|--------|------|
| 模型解耦接入信息 | `requestUrl`、`requestAuth` 从 `system_models` 移除，由 Channel 管理 |
| Channel 绑定模型 | aiproxy 渠道按**上游模型名**（`models` 数组）绑定；FastGPT 侧按 `modelId` 口径关联（见 2.9.2） |
| aiproxy 路由 | 请求在**自身 scope 内**按上游模型名匹配启用渠道转发（见下方「路由 scope 隔离」）；支持 `Aiproxy-Channel: <channelId>` 请求头锁定**系统**渠道（模型测试用） |
| 渠道删除保护 | 删除渠道前检查「仅关联该渠道的模型」，给出受影响模型清单 + 渠道名二次确认（F2-S4/F3-S4） |
| 模型删除保护 | 删除模型前检查同上游名的渠道引用，返回引用渠道信息供前端提示 |

**路由 scope 隔离（安全边界，aiproxy `middleware/auth.go` + `distributor.go` 源码核实）**：

| 模式 | 可选渠道 | 语义 |
|------|---------|------|
| global（默认） | **仅系统渠道**（`channels` 表） | group 渠道从不进入全局缓存，成员渠道不可达 |
| own（`X-Aiproxy-Group: <groupId>` + `X-Aiproxy-Group-Channel-Mode: own`） | **仅该 group 自己的渠道** | 组内无该模型名 → 404；**即使同名模型绑定在其他成员的渠道上，也绝不跨组命中** |
| `Aiproxy-Channel` 锁定 | 仅系统渠道 | 只查全局渠道缓存，group 渠道 id 不可锁定 |

模型选择同样受 scope 约束（`FindModelWithAllowList` + own 模式可用模型 = 组渠道模型 ∩ 组 scope 配置），因此**按模型名匹配不存在越权路径**；FastGPT 调用侧需按模型归属选择模式（系统模型 → global；成员自有模型 → own + 该成员 groupId），此为调用链路模块的关联点（见 2.9.6）。

#### 2.9.1 aiproxy Channel 对接架构

**渠道数据不落库**（FastGPT 侧无 channel 集合）：aiproxy 为渠道唯一事实源，FastGPT 服务层持有 admin 配置（`getAIProxyAdminConfig()` → baseUrl/token）以 admin API 完成读写与关联计算。

**渠道模型**（AddChannelRequest / ChannelResponse，aiproxy `core/model/channel.go`）：

| 字段 | 说明 |
|------|------|
| `name` | 渠道名 |
| `type` | 提供商类型（int，如 1=openai、14=anthropic、36=deepseek） |
| `key` | aiproxy 原生 API Key 凭证 |
| `base_url` | 自定义端点覆盖（可选） |
| `models: string[]` | **渠道服务的上游模型名**（与 FastGPT 模型的 `model` 字段匹配） |
| `model_mapping: map[string]string` | 公共名 → 上游实际名映射 |
| `priority` | 负载均衡权重（默认 10） |
| `status` | 1=启用 / 2=禁用 |
| `sets` | 模型集合（默认 `default`） |

**三族管理 API 映射**（全部走 `AdminAuth`：`Authorization: Bearer sk-<ADMIN_KEY>`，无用户级权限，FastGPT 服务层负责业务鉴权）：

| FastGPT 场景 | aiproxy API | 说明 |
|--------------|-------------|------|
| root 管理系统渠道 | `POST /api/channel/`、`PUT /api/channel/:id`、`DELETE /api/channel/:id`、`POST /api/channel/:id/status`、`GET /api/channels/`（分页 `{channels, total}`）、`GET /api/channels/type_metas` | 公共渠道 CRUD/列表/类型元数据 |
| 普通成员管理自有渠道 | `POST /api/group/:group/channel/`、`PUT /api/group/:group/channel/:id`、`DELETE /api/group/:group/channel/:id`、`POST /api/group/:group/channel/:id/status`、`GET /api/group/:group/channels/` | groupId 由服务端从会话推导，**拒绝客户端传入** |
| root 跨成员排障/运维 | `POST /api/group_channel/`、`PUT /api/group_channel/:id`、`GET /api/group_channels/`（可选 `?group=` 过滤）、`GET /api/group_channel/:id/test` 等 | 全量成员渠道管理 |
| 渠道测试 | `GET /api/channel/:id/test/{model}`、`GET /api/group/:group/channel/:id/test/{model}` | 测试结果持久化到 aiproxy |

**groupId 约定与幂等创建**：
- `groupId = "fastgpt:tmb:<tmbId>"`，一成员一 group，唯一标识成员的自有渠道归属
- **group 创建内置于渠道创建**：aiproxy `BatchInsertGroupChannels` 在事务内调用 `ensureGroups`（`clause.OnConflict{DoNothing: true}`），首次创建渠道时自动建 group，天然幂等——FastGPT 服务层无需先查 group 是否存在

#### 2.9.2 模型-渠道关联机制（modelId 口径）

**关联规则（owner 配对推导，无映射表）**：渠道 C 关联模型 M 当且仅当：

```
C 为系统渠道（无 groupId）  ∧  M.isSystem = true  ∧  M.model ∈ C.models
C 为成员 X 的 group 渠道（groupId = fastgpt:tmb:X）  ∧  M.tmbId = X  ∧  M.model ∈ C.models
```

推导链路：`C.groupId → tmbId（系统渠道跳过）→ Mongo 按归属查模型 → M.model ∈ C.models 名称匹配`。该规则与「路由 scope 隔离」严格一致：系统模型（global 路由）↔ 系统渠道；成员自有模型（own 路由）↔ 该成员自己的渠道（F3「渠道仅自己可用」、F2-S2「公共渠道服务系统模型」）。

**计算函数**（服务层 `getChannelModelsMap` / `getModelChannelsMap`）：
- `channelCount(modelId)`：M 所属桶内匹配渠道数（模型列表增强字段，替换原 `aiproxyChannelsCache` 按 modelId 的统计口径）
- `getModelChannels(modelId)`：M 的关联渠道明细（id/name/status），供悬浮查看
- `getChannelAffectedModels(channelId)`：删除渠道保护——仅该渠道一条通路的模型（同上游名渠道数 = 1 的模型集合）

**删除/停用保护**：
- **渠道删除**（F2-S4/F3-S4）：服务层返回 `affectedModels: { modelId, name, model }[]`；前端展示「以下模型仅关联该渠道，删除后这些模型将无法正常调用」+ 渠道名二次确认。同上游名存在其他启用渠道时 aiproxy 自动切换
- **模型删除**（F2-S3）：服务层返回同上游名的引用渠道数（仅统计同归属桶内渠道），由前端提示；不阻断（渠道按名路由，删除模型不影响渠道自身）
- **渠道 Key 轮换**：编辑即生效（aiproxy 渠道信息运行时缓存，无需重启）——F2-S4 场景2

#### 2.9.3 用户自有 Key 与 Channel 系统的交互

当用户配置了自己的 OpenAI Key（`userOpenAIAccount`）时，**不应进入团队共享的 Channel 路由体系**。核心规则：`requestMeta.usedUserOpenAIKey === true` 时，跳过 Channel 查找，直接使用用户自有 Key 调用。

**分流逻辑**：
- `usedUserOpenAIKey === true` → 跳过 Channel 查找，`getAIApi({ userOpenAIAccount })` 直接调用，不注入渠道 scope
- `usedUserOpenAIKey === false` → 正常 Channel 路由：请求经 aiproxy 转发，调用范围由 `getAiproxyScopeHeaders` 推导（系统模型 → `global` scope；私有模型 → `own` + `fastgpt:tmb:<tmbId>` scope），aiproxy 按上游模型名路由到对应 Channel

**与现有逻辑的继承关系**：当前 `createChatCompletion.ts`（L42-48）已有 `!requestMeta.usedUserOpenAIKey` 判断。重构后此逻辑自然延续：用户自有 Key 跳过旧的模型级 URL 覆盖，也跳过新的 Channel 路由查找。

> 详细数据流及实现要点见 [模型调用链路文档 §3.1](./模型管理重构-详细设计-模型调用链路.md#31-用户自有-key-与-channel-路由的分流)。

### 2.10 模型调用链路重构

> ⚠️ **实现修订（经评审确认）**：本节原稿「请求体增加 `modelId` 字段，aiproxy 基于此路由」已废弃。
> aiproxy 的 AST 往返**不剥离未知字段**，请求体中的 `modelId` 会透传上游触发 OpenAI 400，
> 因此最终方案为：
>
> - **`LLMRequestBodyType<T>` 不再包含 model/modelId**。wire body 的 `model` 由
>   `llmCompletionsBodyFormat(input, modelData)` 从 `modelData.model`（provider 模型名）解析，
>   返回值只含 requestBody。
> - **`CreateLLMResponseProps` 增加 `modelData: LLMModelItemType`**（与 `teamId` 同级），
>   调用方必须显式传入模型配置对象，不再按 id 反复查询，也不设守卫（参数定义本身即约束）。
> - **aiproxy 调用范围由 `getAiproxyScopeHeaders` 推导**：系统模型 → `global` scope；
>   私有模型 → `own` + `fastgpt:tmb:<tmbId>` scope。
> - **全平台 LLM 调用统一收敛**：LLM 收敛到 `createLLMResponse`、embedding 收敛到
>   `getVectors`、rerank 收敛到 `reRankRecall`、speech 收敛到 `text2Speech`。

模型查找函数签名从 `getLLMModel(model?: string)` 变为 `getLLMModel(modelId: string): T | undefined`（见 [2.5 节](#25-模型查找函数重构)）。⚠️ **热升级兼容**：热升级窗口期签名保持 `getXXXModel(modelIdOrName: string)` 兼容输入（id/name 皆可，§2.5 修订注记），下述「参数必填 modelId」为 contract release 最终形态。所有调用方按最终形态传入 modelId，兼容路径由 getter 内部承担。核心变更：

- **参数必填**（最终形态）：modelId 不再可选，调用方必须显式传入；⚠️ 热升级窗口期 name 值由 getter 兼容解析
- **不再静默回退**：模型不存在时返回 `undefined`，由调用方决定如何处理
- **默认模型需显式获取**：调用方通过 `getDefaultLLMModel()` 获取
- **模型配置对象随调用显式传入**：`CreateLLMResponseProps` 携带 `modelData: LLMModelItemType`，调用入口不再按 modelId 查询；请求体不含 model/modelId

**影响的调用链**（8 条主要链路；⚠️ 热升级：Workflow 参数为双字段输出，见 §3.1）：

| 链路 | 关键文件 | 变更要点 |
|------|---------|---------|
| 查询扩展 | `queryExtension.ts`, `dispatch/tools/queryExternsion.ts` | `llmModel` 参数 → `llmModelId`；`NodeInputKeyEnum.aiModel` → `aiModelId` |
| AI 对话 | `dispatchChatCompletion.ts`, `classifyQuestion.ts`, `extract.ts` | ⚠️ `getWorkflowNodeRunParams` 输出 `params.modelId`（+ `params.model` legacy）；节点读 `params.modelId` |
| Agent | `agent/sub/model/index.ts`, `agentLoop/base.ts`, `piAgent/modelBridge.ts` | model 名参数 → modelId |
| 知识库搜索 | `dataset/search/`, `embeddingRecall.ts`, `imageCaption.ts`, `rerank.ts` | `getEmbeddingModel(model)` → `getEmbeddingModel(modelId)` 等（getter 兼容 name） |
| 知识库训练 | `collection/controller.ts`, `training/controller.ts` | `dataset.vectorModel` → `dataset.vectorModelId`（legacy 字段保留，读取 fallback） |
| 训练/评测计费 | `createTrainingUsage.ts`, `createEvaluationUsage.ts` | 各 model 参数增加对应的 `xxxModelId` |
| Skill 调试 | `skill/debugChat/` | `model` 参数 → `modelId`（⚠️ 入站补回 legacy model，handler `modelId ?? model`） |
| 插件运行时 | `dispatch/plugin/run.ts` | 子 workflow 自动透传 modelId，无需额外改动 |

**变更规模**：约 49 个文件，涵盖模型查找函数、LLM 请求层、工作流 dispatch 节点、知识库运行时、Skill/插件运行时、计费入口等。

## 4. 知识库运行时重构

知识库（Dataset）运行时是模型调用的第二大入口（仅次于工作流 dispatch），涉及向量化（Embedding）、QA 生成、图片理解（VLM）、Rerank、查询扩展等多个模型调用路径。所有路径最终通过 `createTrainingUsage` 或工作流 `usagePush` 落库 `UsageItem` 表，因此需要同步补充 `modelId`。

> 详细的计费/用量引用分析见 [模型管理重构-计费用量引用分析.md](./模型管理重构-计费用量引用分析.md) 第 3 节（非工作流路径的 Usage 落库）。

### 4.1 Dataset Schema 模型字段

**文件**: `packages/service/core/dataset/schema.ts:99-109`


## 5. SKILL 运行时重构

SKILL（Agent Skill）是 FastGPT 的 Agent 技能系统。Skill 调试和执行复用工作流运行时，其模型引用通过 `NodeInputKeyEnum.aiModel` 传递给 Agent 节点，因此核心改造在于 model 参数的传递路径。

### 5.1 Skill 调试运行时

`buildDebugRuntimeNodes` 构造最小化工作流（workflowStart → agent），Agent 节点通过 `NodeInputKeyEnum.aiModel` 设置模型。重构后 `model` 参数从 model 名改为 `modelId: string`（ObjectId）。由于 `NodeInputKeyEnum.aiModel` 的枚举值已从 `'model'` 改为 `'modelId'`（见 §3.1），Agent 节点执行时自动通过 `getLLMModel(modelId)` 解析，无需额外改动。

### 5.2 Skill 调试 Handler

Handler 中 `modelId` 解析逻辑从取 model 名改为取 modelId（`modelId || getDefaultLLMModel()?.id`）。⚠️ 热升级兼容：debugChat 入站 schema 补回可选 legacy `model` 字段（§2.8 前提 1），handler 读取 `modelId ?? model`（name 值交给 getter 解析）；两者均未配置时才回退默认模型。计费点重算处 `formatModelChars2Points` 改为接收 `modelData` 对象，需传入 modelId 查找模型后再调用。

### 5.3 Skill 模型 Schema

Agent Skill 本身不直接存储模型字段（Skill 通过其 internal workflow 中的 Agent 节点引用模型），Skill schema 无需变更。

> 带行号的详细代码对比见 [模型管理重构-详细设计-模型调用链路.md §4.8](./模型管理重构-详细设计-模型调用链路.md#48-链路-8-skill-调试)。

### 5.4 插件运行时

**文件**: `packages/service/core/workflow/dispatch/plugin/run.ts:60-306`

`dispatchRunPlugin` 处理工作流插件（系统工具 / 个人插件 / 商业插件），其核心逻辑是加载子 workflow 并通过 `runWorkflow` 递归执行：

```typescript
// L227: 递归调用 runWorkflow
const { flowUsages } = await runWorkflow({
  ...props,
  runtimeNodes,
  runtimeEdges: storeEdges2RuntimeEdges(workflowTool.edges)

// L262-273: 汇总子 workflow 的用量
```

**重构要点**:
- 子 workflow 的 `runtimeNodes` 来自插件版本中的 `nodes`，这些节点 `inputs` 中可能包含 `modelId`（重构后），会被正常传递到各 dispatch 函数

- `dispatchRunPlugin` 本身不直接引用模型，无需额外改动
- `computedAppToolUsage` 计算插件消耗积分，不涉及模型维度

## 6. 数据迁移

迁移分多个步骤，涵盖索引调整、模型数据扁平化、所有引用集合的 model 名→modelId 补充、系统默认模型初始化及权限迁移。使用 cursor-based 分批处理（BATCH_SIZE = 500），所有步骤幂等可重入，遵循项目现有 migration 模式（参考 `projects/app/src/pages/api/admin/initv4151.ts`）。

> ⚠️ **实现修订（热升级兼容，2026-08）**：迁移语义由「破坏式（rename/$unset 旧字段）」调整为 **additive（只补 canonical，不删 legacy）**，使迁移前/中/后及回滚四个窗口内新老镜像均可运行存量数据。通用规则：
> - 只补 canonical 字段，不 `$unset` legacy（schema 双字段一致）；
> - 只写成功解析成真实 ObjectId 的值；unresolved 不写、计入结果；
> - 目标 canonical 已有有效值时不覆盖；
> - Step 1 本版本**不删除** `model` unique index（推迟到 contract release）；
> - 完整对照见[热升级技术分析 §7.1a](./模型管理重构-热升级技术分析.md#71a-代码现状与需要调整的步骤)。

**迁移步骤概要**：

| 步骤 | 内容 | 影响集合 |
|------|------|---------|
| 1 | 索引迁移 — 创建新索引（`teamId_1`/`tmbId_1`/`isActive_1_provider_1`）；旧 unique 索引本版本保留 | `system_models` |
| 2 | `system_models` 数据迁移 — metadata 扁平化（只补顶层缺失字段）+ isSystem 标记 + 收集 defaults/channel configs；不删除 metadata/isCustom/isDefault*/tmbId/teamId | `system_models` |
| 3 | 构建 modelName → modelId 映射表（active/system 优先 + name 别名 map + ambiguous 记录） | 内存 |
| 4 | datasets 迁移 — 只补 `*ModelId`（解析成功时），legacy `vectorModel`/`agentModel`/`vlmModel` 保留 | `datasets` |
| 5 | apps + app_versions 迁移 — 保留 legacy input + 补 canonical input；chatConfig 保留 `model` + 补 `modelId`；datasetParams 同 | `apps`, `app_versions` |
| 6 | eval 迁移 — 只补 `evalModelId`，保留 `evalModel` | `eval` |

## 8. 缓存刷新与变更监听

模型变更通过三个机制保证缓存一致性：

1. **MongoDB Change Stream** — `MongoSystemModel.watch()` 监听变更，debounce 500ms 后自动重载 `loadSystemModels` + 刷新配置缓存 + 刷新权限版本号
2. **模型更新后重载**（`updatedReloadSystemModel`）— 立即 reload → 更新共享缓存通知其他节点 → 刷新权限版本 → delay 1s 等待其他节点
3. **定时刷新**（`cronRefreshModels`）— 每 5 分钟兜底 `loadSystemModels` + `updateFastGPTConfigBuffer`

> 完整代码实现及 `ModelTemplateType` 定义见 [模型管理重构-详细设计-缓存.md](./模型管理重构-详细设计-缓存.md)。

## 9. 升级策略

> ⚠️ **实现修订（经评审确认，2026-08）**：本章由「停机升级 + 无过渡期」重写为「**热升级（滚动切换 + additive 迁移 + 备份恢复）**」。升级期间不要求实施配置写冻结；代码通过 additive 字段、双 map、getter 兼容和 CAS 尽量保证混合数据可读，运维可按部署环境自行安排写入窗口。完整分析与最小方案论证见 [模型管理重构-热升级技术分析.md](./模型管理重构-热升级技术分析.md)。

### 9.1 升级步骤

热升级分为四个阶段：

```
1. 预检查与备份
├── 1.1 全量备份受影响集合（system_models, apps, app_versions, datasets, eval, usage_items, resource_permissions, default_models）
├── 1.2 在备份副本上预跑迁移，记录各步骤总数、unresolved、耗时
├── 1.3 确认新镜像已包含全部读取兼容（双 map + getters + schema 双字段）

2. 滚动切换镜像
├── 2.1 滚动替换所有 FastGPT 与 pro 实例为兼容版新镜像
├── 2.2 数据库尚未迁移，但新镜像通过双 map + getters 兼容运行已有业务
├── 2.3 完成运行流量冒烟（Workflow/Agent 对话、知识库检索/训练、questionGuide/TTS）

3. 执行 additive migration（手动调用 /api/admin/initv4160）
├── 3.1 只补 canonical 字段（modelId 等），不删除 legacy 字段（model 等）
├── 3.2 分批执行、可重入；期间 legacy-only 与 dual 记录并存，新镜像均可运行
├── 3.3 无法解析的模型名不写入 *ModelId，计入 unresolved 返回资源定位
├── 3.4 重跑直到 conflicts=0 且 unresolved 全部登记/人工确认（见热升级技术分析 §9），第二次执行对已完成记录 no-op
├── 3.5 迁移后运行冒烟；验证 canonical 字段覆盖率

4. 迁移后收敛
├── 4.1 新保存/新建只写 canonical 格式；legacy 字段由 schema 声明保留，存量 legacy 字段不主动删除
├── 4.2 兼容代码（name map、getter name 解析、legacy 字段）在后续 contract release 单独移除
```

**切换顺序要求**：必须在「所有实例均为新兼容镜像」之后才执行迁移脚本；迁移脚本保持 root-only 手动调用，不自动绑定 pod 启动（避免旧实例在迁移中途被滚动替换）。

### 9.2 回滚方案

升级失败时采用「停止新镜像 → 恢复迁移前备份 → 回滚旧镜像 → 验证」：

1. 停止新镜像；
2. 恢复迁移前全量备份（system_models, apps, app_versions, datasets, eval, usage_items, resource_permissions, default_models）；
3. 回滚旧 FastGPT/pro 镜像并验证运行流量。

要点：

- 迁移采用 additive（保留 legacy 字段），因此旧镜像也能读取迁移后仍保留 legacy 结构的数据；但失败回滚仍**以备份恢复为准**。项目没有统一配置写冻结机制，恢复迁移前备份会丢失升级窗口内写入；需要保留时由部署侧增量备份或操作日志回放承担；
- Step 10 创建的 aiproxy Channel 是外部副作用，Mongo 恢复不会删除；旧镜像不读取新 Channel，可保留或按迁移返回清单人工清理。

### 9.3 兼容性实现要点

热升级读取兼容由三部分组成（详见[热升级技术分析 §6](./模型管理重构-热升级技术分析.md#6-最小代码改动设计)）：

| 兼容点 | 实现 |
|--------|------|
| Schema 双字段 | dataset/workflow input/chatConfig/eval/permission 保留 legacy 字段（`@deprecated`）+ 新增 required canonical 字段 |
| 缓存双 map | `loadSystemModels` 同时构建 `modelId → modelData`（权威）与 `model → modelData`/`name → modelData`（兼容）索引（§2.3） |
| getters 兼容输入 | `getXXXModel(modelIdOrName)` 先查 id map，未命中且非 ObjectId 时按名查兼容索引（§2.5） |
| Workflow 双 key | 持久化保留 legacy input + 迁移补 canonical input；`getWorkflowNodeRunParams` 双字段输出（§3.1） |
| 参数/鉴权 | handler 读取 `*ModelId ?? legacy`；`authModels`/`extractWorkflowModelIds` 识别 legacy key |
| modelCompat | 已移除，职责由入站 schema 双字段 + handler fallback + getter 承担（§2.8） |

### 9.4 配置写入说明

本次改造不新增配置写冻结机制，也不在 API 入口拒绝配置写入。升级期间若存在写操作，运行时通过 legacy/canonical 双字段、双 map、getter name fallback 兼容混合数据；迁移批量更新通过 CAS 或 canonical 字段快照条件避免覆盖检测到的并发修改，冲突记录在迁移结果中并可重跑处理。恢复迁移前备份会丢失升级窗口内写入，执行回滚前必须评估并记录窗口内变更。

## 11. 关键风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 数据迁移失败或遗漏 | 存量应用/知识库无法正常工作 | 迁移前全量备份；迁移脚本幂等可重入；热升级方案 additive 迁移 + 双 map/getters 读取兼容兜底（§9） |
| 新 ModelId 查找不到模型 | LLM 调用失败 | 调用方显式处理 `undefined` 返回值；getter 兼容 name 输入兜底存量数据；完善的日志和告警 |
| 前端组件遗漏更新 | 部分页面仍传 model 名 | 类型系统强制使用 modelId 类型，编译期检查；热升级窗口 getter 兼容 name 输入兜底 |
| 第三方/Open API 调用方不兼容 | 外部系统调用失败 | 响应体保持返回 model 名；Open API 兼容层自动转换（移除 modelCompat 后由入站 schema 双字段 + handler fallback 承担，§2.8） |
| isDefault 移除后默认模型回退异常 | 部分场景无可用默认模型 | 回退逻辑：显式配置 > 首个启用的同类型系统模型（type=target, isSystem=true, isActive=true）> undefined；root 需主动配置系统默认模型 |
| requestUrl/requestAuth 移除后模型调用不通 | 自定义 URL 的模型无法使用 | 迁移脚本 Step 10 将旧 requestUrl/requestAuth 通过 aiproxy API 自动创建对应 Channel（按 model+url+auth 去重）；aiproxy 未配置时记录日志供手动创建 |
| 热升级窗口新旧实例写不同字段 | 文档结构漂移、迁移批量写与用户保存互相覆盖 | legacy/canonical 双字段与 getter fallback 保证混合数据可读；迁移使用 CAS 或 canonical 字段快照条件，冲突记录后可重跑（见热升级技术分析 §7.6） |
| 迁移 unresolved（legacy 模型名无法解析） | 对应记录调用时报错 | 迁移只写解析成功的 ObjectId、unresolved 不写且计数；记录清单供后续人工修复（见热升级技术分析 §9） |
| 鉴权只识别 modelId key | legacy `model` key 绕过模型权限校验 | `extractWorkflowModelIds`/`authModels` 同步识别 legacy key（§3.1） |
