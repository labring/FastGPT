# 模型管理重构 — 详细设计：模型调用链路

> 基于主设计文档第 2.10 节展开。模型查找函数签名从 `getLLMModel(model?: string)` 变为 `getLLMModel(modelIdOrName: string): T | undefined` 后，所有调用方需同步修改。本文档逐链路追踪完整的调用链、参数传递路径及变更方案。热升级窗口的兼容规则以[模型管理重构-热升级技术分析.md](./模型管理重构-热升级技术分析.md)和主设计文档 §9 为准。

---

## 1. 核心原则

1. **热升级过渡**：新版本上线后先通过 canonical/legacy 双字段、id/name 双 Map 和 getter fallback 读取存量数据，再手动执行 additive migration。
2. **兼容签名有明确退场边界**：调用方以 `modelId` 为 canonical 参数；getter 在热升级版本兼容 modelId/provider model/name，并以 `@deprecated` 标记 name-keyed 缓存，后续 contract release 再移除。
3. **参数溯源修改**：不仅改函数调用，还需追溯调用方上游的参数来源（workflow input、dataset field、API query），将参数从 model 名字符串改为 modelId。
4. **LLMRequestBodyType.model → modelId**：请求体中的 `model` 字段改为 `modelId`（存 ObjectId）。aiproxy 基于 `modelId` 路由到对应 Channel，未找到 Channel 时 fallback 到 `modelData.model`（provider model 名）。

**新增函数实现**：

```typescript
// packages/service/core/ai/model/cache.ts（重构后，由 model.ts 改名）
export const getModelById = (modelId: string): SystemModelItemType | undefined => {
  return global.systemModelIdMap.get(modelId);
};
```

**关键行为变更**：
- **参数必填**：modelId 不再可选，调用方必须显式传入
- **不再静默回退**：模型不存在时返回 `undefined`，由调用方决定如何处理
- **默认模型需显式获取**：调用方通过 `getDefaultLLMModel()` 获取系统默认模型

## 3. LLMRequestBodyType 变更

**文件**: `packages/service/core/ai/llm/request/types.ts`

```typescript
// 重构前
export type LLMRequestBodyType<T> = Omit<T, 'model' | ...> & {
  model: string | LLMModelItemType;  // model 名字符串或完整对象
  ...
};

// 重构后
export type LLMRequestBodyType<T> = Omit<T, 'model' | ...> & {
  modelId: string;                     // 平台内 modelId (ObjectId)，必填
  model: string | LLMModelItemType;    // 保留兼容（provider model 名），由 llmCompletionsBodyFormat 自动从 modelData 填入
  ...
};
```

**`llmCompletionsBodyFormat` 变更**（`requestBody.ts`）：

```typescript
// 重构前: getLLMModel(body.model)
const modelData = getLLMModel(body.model);

// 重构后: getLLMModel(body.modelId)
const modelData = getLLMModel(body.modelId);
if (!modelData) return Promise.reject(ModelErrEnum.unExist);

// requestBody 中注入 modelId + model:
requestBody = {
  ...body,
  modelId: modelData.id,         // 平台内唯一标识（aiproxy 路由依据）
  model: modelData.model,        // provider model 名（fallback）
  ...
};
```

### 3.1 用户自有 Key 与 Channel 路由的分流

重构后 `requestUrl`/`requestAuth` 从 model 移除，统一由 Channel 管理。但当用户配置了自己的 OpenAI Key（`userOpenAIAccount`）时，该 Key 代表用户的私有凭证，**不进入 Channel 路由体系**。

**分流逻辑**（在 `createChatCompletion` / `llmCompletionsBodyFormat` 中）：

```
requestMeta.usedUserOpenAIKey?
├── true  → 跳过 Channel 查找
│           - 不注入 modelId 到 aiproxy 请求
│           - 直接使用 getAIApi({ userOpenAIAccount }) 的 baseUrl + apiKey
│           - modelData.model 作为 provider model 名传给 API
│
└── false → 正常 Channel 路由
            - requestBody.modelId = modelData.id   （aiproxy 查找 Channel）
            - requestBody.model = modelData.model  （fallback 直连）
            - aiproxy 找到 Channel → 使用 Channel 配置
            - aiproxy 未找到 → 使用 getAIApi() 默认端点 + modelData.model
```

**关键实现点**：

| 模块 | 变更 |
|------|------|
| `getAIApi()` | 无变更 — 已返回 `{ ai, requestMeta: { usedUserOpenAIKey } }` |
| `createChatCompletion.ts` | 已有 `!requestMeta.usedUserOpenAIKey` 检查（L42-48），重构后此逻辑延续 |
| `llmCompletionsBodyFormat` | 当 `usedUserOpenAIKey === true` 时，不注入 `modelId` 字段到 requestBody |
| 其他 AI 模块（Embedding/Rerank/TTS/STT） | 同此模式：用户有自有 Key 时跳过 Channel 查找 |

**安全约束**：用户私有 Key 不出现在 Channel 配置中、不计入团队共享配额、日志中始终脱敏。
