## 需求背景
### 1.1 背景概述
在托管云和集团型客户场景中，不同部门或用户会自行采购/部署模型，这些模型的密钥（Key）属于部门私有资产，不便交由超管统一管理。

同时社区版本用户通常使用 MaaS 模型，都是云厂商原生的，阿里百炼，火山这种号，习惯于通过模型渠道（Channel）方式配置模型。

因此需要将模型创建能力从 root 下放至授权用户，并建立「公共/私有」模型共享机制，让超管既能统一配置共享模型，又能让其下用户自主管理自己的模型，并灵活控制模型的可用范围。

核心设计原则：

+ root 负责创建和管理全平台系统模型及公共渠道，供所有团队使用
+ 授权团队成员仅可在团队内创建私有模型及私有渠道，模型归成员个人所有，通过协作者机制在团队内共享，渠道仅自己可用
+ 系统模型默认全平台可见、全平台可用；私有模型默认仅创建者可见，可通过添加协作者扩展使用范围
+ 所有模型都只有创建人可编辑/删除；root 可通过 Pro Admin 查看全平台模型信息及调用记录，工作台端按系统/当前成员渠道范围展示（Key 始终受保护）
+ 系统模型（isSystem: true）不维护 teamId 和 tmbId，不属于任何团队或个人，全平台共享
+ 所有涉及模型信息的接口（包括 debug、测试、调用日志等）均需通过模型鉴权，确保模型访问权限可控

### 1.2 目标用户群体
+ 平台管理员（root）：管理系统模型（全平台可用的模型），监测所有模型，包括所有用户创建的模型
+ 团队 Owner：在团队层面管控模型创建权限，也可新增自己的模型，并管理自己模型的可用范围
+ 团队成员（授权用户）：获得创建模型权限后，可新增自己的模型，并管理自己模型的可用范围
+ API 用户：通过 API 调用模型，受模型权限控制

### 1.3 当前产品现状
+ 现有系统： 
    - 数据存储: MongoDB system_models 集合，以 model 字段 ("gpt-4o") 作为唯一索引，所有模型配置嵌套在无类型约束的 metadata: Object 中。运行时依赖 Zod Schema 校验，DB 层与运行时存在类型断层。
    - 运行时缓存: 模型加载后写入 global.llmModelMap 等全局 Map，同时以 model 和 name 作为 key，语义混淆。
    - 权限控制: 模型 CRUD 统一校验 authSystemAdmin，非管理员仅能做简单的资源权限过滤，无法区分编辑/删除/使用等操作。
    - 引用点遍布全项目: 应用配置 (AppTTSConfigType.model, SettingAIDataType.model)、工作流节点 (AIChatNodeProps[aiModel])、用量记录 (UsageItemCountType.model)、Open API 等均以 model 字符串引用模型。
+ 三大核心问题

| 问题 | 根因 | 影响 |
| --- | --- | --- |
| 模型标识不稳定 | model 字段作唯一索引，多个自定义模型共用同一 OpenAI model 名时冲突 | DB 写入冲突、全局 Map 覆盖、查找歧义 |
| 缺乏权限控制 | 仅 authSystemAdmin 校验，无细粒度权限 | 无法实现团队私有模型、协作者共享等场景 |
| 数据结构不规整 | 配置放在无类型约束的 metadata: Object 中 | DB 层无字段校验，类型安全差 |


### 1.4 目标
+ 场景目标：
    - 授权团队成员可自主创建模型，无需 root 代为操作，且权限全部可控 — 成功标准：团队成员获得权限后能独立完成模型创建全流程，且可灵活控制权限，模型信息不泄露
+ 系统目标：
    - 建立稳定标识体系 — 引入平台唯一标识 (ObjectId)，model/name 降级为可重复的业务别名
    - 实现细粒度权限控制 — 支持系统模型/私有模型分层，区分可见/使用/编辑/删除权限
    - 规整数据结构 — 模型配置字段从 metadata 中提升为顶层级字段，实现 DB 层类型约束
    - 全接口资源鉴权覆盖 — debug、测试等模型接口按模型权限鉴权；调用日志和监控按系统/当前成员渠道范围鉴权，防止越权访问模型信息与调用数据
+ 设计约束：
    - 系统模型（isSystem: true）不维护 teamId 和 tmbId，全平台共享，不属于任何团队或个人

## 3. Story 详细描述
#### F1. 模型创建权限管控
用户故事：

+ 作为 团队 Owner（root 也是 Owner），
+ 我想要 在团队管理的权限设置中控制「允许成员创建模型」的开关，
+ 以便 我能决定团队中哪些成员可以自主新增和配置模型。

验收条件：

正常场景：

+ 场景1：
    - Given 团队成员 A 没有创建模型权限（默认状态即如此）
    - When 团队成员 A 进入「模型配置」和「模型渠道」页面
    - Then 新建模型和新建渠道的按钮都置灰，鼠标悬浮提示「暂无权限，请先联系管理员获取权限」
+ 场景2： 
    - Given 团队 Owner 进入团队管理-权限设置页面
    - When Owner 为某成员开启「创建模型」权限
    - Then 被授权的成员在「模型配置」和「模型渠道」页面看到新建按钮激活，可新建模型和渠道
+ 场景3： 
    - Given 「创建模型」权限已为某成员开启
    - When Owner 关闭该成员/部门/群组「创建模型」权限
    - If 该成员/部门/群组已有自定义模型
    - Then 该成员已创建的模型和渠道仍然保留，可进行配置，新建按钮置灰

#### F2. root 创建和管理模型及渠道
##### Story F2-S1：root 创建全平台系统模型
用户故事：

+ 作为 平台管理员（root），
+ 我想要 创建全平台系统模型，
+ 以便 为所有团队提供统一可用的基础模型，团队成员无需各自重复配置，或实现企业统一管控诉求。

验收条件：

正常场景：

+ 场景1：
    - Given root 进入「系统模型配置」页面，点击「新建模型」
    - When root 填写模型信息（模型 ID 改为 模型名，别名 改为 可选择模板渲染默认参数配置，取缔之前的内置模型，增加系统模型渠道的选择并提供快速创建入口，去掉自定义请求地址和 Key，配置文件里也同样去掉，保留价格配置）
    - Then 模型创建成功，全平台所有用户均可在可用模型列表中看到该模型，可测试，并能在工作流中选用，但不可启停/编辑/删除

异常场景：

+ 场景1：
    - Given root 新建模型
    - When root 填写的模型别名与其他系统模型重复
    - Then 弹窗确认后提示「模型别名已存在，请更换其他别名」

##### Story F2-S2：root 创建全平台公共渠道
用户故事：

+ 作为 平台管理员（root），
+ 我想要 创建全平台系统模型渠道，
+ 以便 为系统模型提供调用通路，所有使用该上游模型名的用户均可受益。

验收条件：

正常场景：

+ 场景1：
    - Given root 进入「系统模型渠道」页面，点击「新建渠道」
    - When root 填写渠道配置（上游的系统模型名、BaseURL、Key 等），渠道自动标记为「公共渠道」
    - Then 渠道创建成功，所有调用该上游模型名的请求均可通过此渠道路由
+ 场景2：
    - Given root 创建了公共渠道绑定上游模型
    - When 团队成员使用 root 创建的系统模型发起调用
    - Then 调用可正常走该公共渠道，无需成员自行配置渠道

##### Story F2-S3：root 管理系统模型（启用/停用、编辑、删除）
用户故事：

+ 作为 平台管理员（root），
+ 我想要 对已创建的系统模型进行编辑、启用/停用、删除等管理操作，
+ 以便 我能维护系统模型库的健康状态，及时下线不再使用的模型。

验收条件：

正常场景：

+ 场景1：
    - Given root 编辑一个系统模型的配置
    - When 保存修改后
    - Then 所有使用该模型的团队立即生效，使用新的配置进行调用
+ 场景2：
    - Given root 禁用一个系统模型
    - When root 看到提示信息「禁用后，引用该模型的应用/知识库将无法正常工作，请确保业务不受影响」，并填写模型名作为二次确认，点击「确认」后
    - Then 该模型不再出现在可选列表中，已在使用该模型的应用/知识库在调用时收到明确的不可用提示
+ 场景3：
    - Given root 删除一个系统模型
    - When root 看到提示信息「删除后，引用该模型的应用/知识库将无法正常工作，请确保业务不受影响」，并填写模型名作为二次确认，点击「确认」后
    - Then 该模型不再出现在可选列表和模型配置列表中，已在使用该模型的应用/知识库在调用时收到明确的不可用提示

##### Story F2-S4：root 管理公共渠道（编辑、删除）
用户故事：

+ 作为 平台管理员（root），
+ 我想要 对已创建的公共渠道进行编辑和删除管理，
+ 以便 我能维护渠道配置的准确性和安全性。

验收条件：

正常场景：

+ 场景1：
    - Given root 删除一个公共渠道
    - When 该渠道关联了 N 个仅有该渠道一条通路的模型
    - Then 系统提示「以下模型仅关联该渠道，删除后这些模型将无法正常调用，请确保业务不受影响」，填写渠道名作为二次确认，点击「确认」后执行
    - And 依赖该渠道的系统模型发起调用，如果有其他公共渠道支持同一上游模型名，自动切换；否则提示「模型无可用调用的渠道」
+ 场景2：
    - Given root 编辑了公共渠道的 Key（密钥轮换）
    - When 保存修改后
    - Then 后续通过该渠道的调用立即使用新 Key，无需重启或手动刷新

##### Story F2-S5：root 查看模型及模型渠道
用户故事：

+ 作为 平台管理员（root），
+ 我想要 在普通模型管理页查看全平台模型、公共渠道及 root 自有私有渠道，并在 Pro Admin 查看全平台私有渠道，
+ 以便 我能全面掌握平台中已配置的所有模型资源状况，并为系统模型和自有模型的管理决策（启用/停用/删除）提供依据。

验收条件：

正常场景：

+ 场景1：
    - Given root 进入「公共可用模型」及「系统模型配置」列表页面
    - When 浏览模型列表
    - Then 列表展示所有系统模型，每条记录在现有基础上增加模型渠道数量及悬浮查看所有渠道（可用模型也要支持切换模型名和模型 ID 显示）
    - And 「系统模型配置」列表将启用模型排在前面，内部再按照模型提供商字母序排列，并支持分页
+ 场景2：
    - Given root 进入「团队可用模型」及「团队模型配置」列表页面
    - When 浏览模型列表
    - Then 列表展示所有团队成员创建的模型（包括root自己创建的私有模型），每条记录在现有基础上增加创建人、模型渠道数量及悬浮查看所有渠道，并增加按照模型 ID、创建人搜索（可用模型也要支持切换模型名和模型 ID 显示）
    - And 「系统模型配置」列表将启用模型排在前面，内部再按照模型提供商字母序排列，并支持分页
+ 场景3：
    - Given root 进入「系统模型渠道」列表页面
    - When 浏览渠道列表
    - Then 列表展示所有公共渠道，每条记录在现有基础上增加关联的模型数量及悬浮查看所有模型
+ 场景4：
    - Given root 进入「团队模型渠道」列表页面
    - When 浏览渠道列表
    - Then 列表仅展示 root 自己创建的私有渠道，每条记录增加关联的模型数量及悬浮查看所有模型；其他团队成员的私有渠道仅在 Pro Admin 全平台渠道列表可见
+ 场景5：
    - Given root 进入公共或团队的「调用日志」及「监控」页面
    - When 浏览页面
    - Then 公共范围展示系统渠道日志及监控，团队范围展示 root 自有私有渠道日志及监控；调用日志支持按渠道、上游模型、响应状态和时间范围筛选
+ 场景6：
    - Given root 进入 Pro 端模型管理页面
    - When 浏览模型资源相关页面
    - Then 呈现「模型」、「调用日志」及「监控」页面，页面内容与工作台端一致，模型列表及日志列表增加“团队”一列，如果是系统模型，则团队一列显示“系统模型”

Root 自有模型说明：

Root 创建团队内的自有模型，与其他成员场景没有差别，详见成员自主创建和管理模型及渠道

##### Story F2-S6：root 配置系统级默认模型
用户故事：

+ 作为 平台管理员（root），
+ 我想要 为全平台配置一套系统级默认模型，
+ 以便 全平台用户创建应用/知识库可自动使用平台推荐的模型。

验收条件：

正常场景：

+ 场景1：
    - Given root 进入「系统模型配置」页面，点击「系统默认模型」按钮
    - When root 从启用的系统模型列表中分别为各类模型选择指定的默认模型（可选范围为所有已启用的系统模型）
    - Then 配置保存成功，全平台用户创建资源时各场景自动填充为系统级默认模型

异常场景：

+ 场景1：
    - Given root 已配置系统默认 LLM 模型为「gpt-4o」
    - When root 将该系统模型停用或删除
    - Then 系统提示「该模型已被设置为系统默认模型，执行该操作后，系统默认模型将恢复为初始状态，请随后再行设置」，确认后执行
    - And 系统默认配置中对应模型置空，系统自动回退到首个同类型系统模型；

#### F3. 成员自主创建和管理模型及渠道
##### Story F3-S1：用户创建自有模型
用户故事：

+ 作为 获得创建模型权限的团队成员，
+ 我想要 新增自己的 AI 模型，
+ 以便 我采购或部署的模型能接入 FastGPT 供我自己的应用使用。

验收条件：

正常场景：

+ 场景1： 
    - Given 用户 A 已被授予创建模型权限
    - When A 进入「模型配置」页面，点击「新建模型」
    - And 填写模型信息（可选择模板渲染默认参数配置（取缔之前的内置模型），增加自有模型渠道的选择并提供快速创建入口，去掉自定义请求地址和 Key、价格配置）
    - Then 新模型创建成功，出现在模型列表中，创建人显示为 A，默认仅自己可见

##### Story F3-S2：用户创建自有渠道
用户故事：

+ 作为 获得创建模型权限的团队成员，
+ 我想要 创建自己的模型渠道，
+ 以便 为我的自有模型提供调用通路。

验收条件：

正常场景：

+ 场景1：
    - Given 团队成员 A 已被授予创建模型权限
    - When A 进入「模型渠道」页面，点击「新建渠道」
    - And 填写渠道配置信息（自有模型名、BaseURL、Key等）
    - Then 新渠道创建成功，出现在渠道列表中，且只有自己可用
+ 场景2：
    - Given 团队成员 A 创建了自有渠道绑定上游模型
    - When 针对关联模型发起调用
    - Then 调用可正常走该自有渠道

##### Story F3-S3：用户管理自有模型（编辑、授权、启用/停用、删除）
用户故事：

+ 作为 获得创建模型权限的团队成员，
+ 我想要 对已创建的自有模型进行编辑、授权、启用/停用、删除等管理操作，
+ 以便 我能维护自有模型的健康状态，及使用范围等。

验收条件：

正常场景：

+ 场景1：
    - Given 团队成员 A 编辑一个自有模型的配置
    - When 保存修改后
    - Then 所有使用该模型的成员立即生效，使用新的配置进行调用
+ 场景2： 
    - Given 团队成员 A 拥有一个自有模型
    - When A 在「可用模型」及「模型配置」列表中点击「权限设置」
    - And 选择团队成员/部门/群组 B 并确认
    - Then B 可在自己的「可用模型」及「模型配置」列表中看到该模型，并能在工作流中选用，但不可编辑和删除，仅可测试及使用
+ 场景3： 
    - Given 团队成员 A 拥有一个自有模型，该模型已被成员 B 的多个应用使用
    - When A 将成员 B 从授权列表中移除
    - Then 系统提示「移除协作者后，对方正在使用该模型的应用/知识库将无法正常工作，请确保业务不受影响」，填写模型名作为二次确认，点击「确认」后执行
+ 场景4：
    - Given 团队成员 A 停用一个自有模型
    - When 看到提示「停用后，引用该模型的应用/知识库将无法正常工作，请确保业务不受影响」，填写模型名作为二次确认，点击「确认」后
    - Then 该模型不再出现在可选列表中，已在使用该模型的应用/知识库在调用时收到明确的不可用提示
+ 场景5：
    - Given 团队成员 A 删除一个自有模型
    - When 看到提示「删除后，引用该模型的应用/知识库将无法正常工作，请确保业务不受影响」，填写模型名作为二次确认，点击「确认」后
    - Then 该模型不再出现在可选列表和模型配置列表中，已在使用该模型的应用/知识库在调用时收到明确的不可用提示

异常场景：

+ 场景1：
    - Given 团队成员 A 将应用/知识库授权给成员 B，未将其中使用的模型授权给 B
    - When 成员 B 查看或使用授权的应用/知识库
    - Then 成员 B 能够正常使用，但如果修改模型，其可选列表中没有未授权的模型
+ 场景2：
    - Given 团队成员 A 将模型授权给成员 B
    - When 成员 B 查看模型列表
    - Then 成员 B 能够看到和测试授权的模型，但没有编辑、授权、启用/停用、删除权限

##### Story F3-S4：用户管理自有渠道（编辑、删除）
用户故事：

+ 作为 获得创建模型权限的团队成员，
+ 我想要 对已创建的自有渠道进行编辑和删除管理，
+ 以便 我能维护渠道配置的准确性和安全性。

验收条件：

正常场景：

+ 场景1：
    - Given 团队成员 A 删除一个自有渠道
    - When 该渠道关联了 N 个仅有该渠道一条通路的模型
    - Then 系统提示「以下模型仅关联该渠道，删除后这些模型将无法正常调用，请确保业务不受影响」，填写渠道名作为二次确认，点击「确认」后执行
    - And 依赖该渠道的自有模型发起调用，如果有其他渠道支持同一上游模型名，自动切换；否则提示「模型无可用调用的渠道」
+ 场景2：
    - Given 团队成员 A 编辑了自有渠道的 Key（密钥轮换）
    - When 保存修改后
    - Then 后续通过该渠道的调用立即使用新 Key，无需重启或手动刷新

##### Story F3-S5：用户查看模型及模型渠道
用户故事：

+ 作为 获得创建模型权限的团队成员，
+ 我想要 在平台查看所有公共及自有的模型和渠道列表，
+ 以便 我能掌握自己配置的所有模型资源状况，为管理决策（启用/停用/删除）提供依据。

验收条件：

正常场景：

+ 场景1：
    - Given 团队成员 A 进入「可用模型」及「模型配置」列表页面
    - When 浏览模型列表
    - Then 列表展示所有 A 可访问的模型（包括系统模型、自己创建的、其他成员授权给自己的），每条记录在现有基础上增加创建人、模型渠道数量及悬浮查看所有渠道，并增加按照模型 ID、创建人搜索（可用模型也要支持切换模型名和模型 ID 显示）
    - And 「系统模型配置」列表将启用模型排在前面，内部再按照模型提供商字母序排列，并支持分页
+ 场景2：
    - Given 团队成员 A 进入「模型渠道」列表页面
    - When 浏览渠道列表
    - Then 列表展示自己创建的模型渠道，每条记录在现有基础上增加关联的模型数量及悬浮查看所有模型
+ 场景3：
    - Given 团队成员 A 进入「调用日志」及「监控」页面
    - When 浏览页面
    - Then 展示当前成员自有渠道范围内的日志及监控数据，支持按渠道、上游模型、响应状态和时间范围筛选；跨成员全平台数据仅通过 Pro Admin 查看
