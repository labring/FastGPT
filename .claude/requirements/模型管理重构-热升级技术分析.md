# 模型管理重构 — 运行流量不中断的受控升级技术分析

> 状态：**已评审通过（v2），结论已合并回正式设计**（2026-08）：技术设计文档 §9、数据迁移文档 Steps 1-10、需求测试验收文档 §5.3/§5.3a、API 设计文档 §9/§10.2、数据模型文档 §6、缓存文档 §1/§2 均已按本文件结论修订。本文件保留作为受控升级流程的完整论证记录与运维操作手册。
>
> 本文独立分析模型管理重构在运行流量不中断、模型配置写入受控的升级场景下的兼容性、最小实现和运维边界。本文使用“受控升级流程”指代本次发布流程；§5 的“方案 A/B/C/D/E”仍仅表示兼容实现方案，其中“方案 B”特指 API middleware 重写请求体，不表示发布流程。

## 1. 背景

模型管理重构将模型引用从 provider model 名称迁移为 MongoDB ObjectId：

- Workflow input：`model` → `modelId`，以及 embedding/rerank/extension/deep-search 等同类字段；
- Dataset：`vectorModel/agentModel/vlmModel` → `vectorModelId/agentModelId/vlmModelId`；
- App chatConfig：`questionGuide.model/ttsConfig.model` → `modelId`；
- Eval、权限、usage 等关联集合同步补充或切换为 modelId；
- `system_models` 从 `metadata` 嵌套结构迁移为顶层字段，并将模型缓存从 name-keyed map 改为 id-keyed map。

**运行流量不中断的兼容核心思路（评审结论）**：不修改核心业务代码对模型的消费方式，而是把兼容收敛在模型解析边界：

1. **Schema/DB 双字段**：相关集合（如 dataset、workflow node）保留旧 `model` 字段，同时新增必填 `modelId` 字段；
2. **缓存双 map**：`loadSystemModels` 同时构建 `model → modelData` 和 `modelId → modelData` 两个索引；
3. **getters 兼容输入**：所有模型消费方继续使用同一组 `getXXXModel(modelIdOrName)`，getter 内部同时接受 modelId 或 provider model 名；
4. 后续独立版本再移除 `model` 字段与兼容 map。

> 该思路与 API 层 `modelCompat` 的思路一致：拦截现有逻辑并做兼容替换，不破坏核心代码逻辑。区别在于兼容点位于 cache 层（模型解析边界），由 getter 统一承载，而不是在 HTTP middleware 中重写请求体。

## 2. 目标与非目标

### 2.1 本文目标

采用尽可能小的实现，保证：

1. 新 FastGPT 镜像上线、尚未执行迁移脚本时，已有 Workflow、Agent、知识库等运行正常；
2. 迁移按批次执行期间，legacy-only 与已迁移数据可以同时被新镜像运行；
3. 迁移完成后，新格式数据正常运行和保存；
4. 升级失败时，可通过迁移前备份恢复并回滚旧镜像。

“运行正常”至少覆盖：

- Workflow/Agent/LLM 节点执行；
- Dataset search、embedding recall、rerank、训练任务；
- question guide、TTS 等 chatConfig 模型调用；
- 运行过程中的 usage 计费记录。

### 2.2 已确认边界

- **受控升级流程：本次升级不支持旧新 Pod 混合写入模型配置。** 升级开始前必须停止所有旧 Pod 的模型配置创建、编辑、删除和 JSON 导入写入；旧 Pod 全部退出后，才能删除 legacy 全局唯一索引并执行 `initv4170`；
- 升级期间可继续提供运行流量，但模型配置写入必须关闭；迁移通过 CAS 记录的并发冲突仅适用于非模型配置数据；
- 聊天、Workflow 执行、知识库检索等运行流量继续服务；
- 升级失败仍采用“恢复迁移前备份 + 回滚旧镜像”；
- 不要求旧镜像直接读取新版本期间新建或编辑的数据；
- 不修改 `rewriteAppWorkflowToDetail` / `rewriteRuntimeWorkFlow`；
- 不建设长期双写、自动反向迁移或无备份直接回滚体系；
- 缓存构建兼容两种 schema，同时维护 `model → modelData` 与 `modelId → modelData` 两个 map；
- 所有模型使用统一经过 getter 后再使用，getter 兼容 modelId / provider model 名输入；
- 后续独立版本再移除 model 字段与兼容 map，本次不删除。

### 2.3 非目标

以下能力不属于最小方案：

- 新旧实例同时接受模型配置写入；
- 迁移期间继续编辑和发布应用、修改知识库配置或模型配置；
- 不恢复备份直接滚回旧镜像；
- 在本次兼容版本中删除全部 legacy 字段和兼容代码；
- 将 migration handler 自动绑定每个实例的启动流程。

## 3. 当前实现与数据状态

### 3.1 Workflow 状态

| 状态 | 持久化 input | 产生来源 |
|---|---|---|
| W0 legacy | `key: "model"`, `value: "gpt-4o"` | 重构前应用与版本 |
| W1 residue | `key: "modelId"`, `value: "gpt-4o"` | 前端只改 key、未解析 value 后保存 |
| W2 canonical | `key: "modelId"`, `value: ObjectId` | 迁移完成或用户重新选择模型 |
| W3 dual | 同一节点同时保留 legacy 与 canonical input | additive migration 兼容态 |

新 runtime 通过 `getWorkflowNodeRunParams` 按 input key 构造参数。W0 只产生 `params.model`，而新 dispatch 读取 `params.modelId`；W1 虽然 key 正确，但 id-keyed cache 无法用 provider name 查找。

在“getters 兼容输入”方案下：

- W0/W1 都只需要模型解析（model name → modelData），不涉及 key 不一致问题。前端传入 nodes 后，dispatch 按当前 key 取值再经过 getter 即可运行；
- 参数层 key 兼容由 `getWorkflowNodeRunParams` 双字段输出承担（§6.4）：`params.model`（legacy 值）+ `params.modelId`（canonical 值；canonical input 缺失时取 legacy 值）——节点继续读 `params.modelId`，业务代码零改动；
- 迁移脚本不删除 legacy input，因此回滚后旧版本仍能读取 W0/W3。

旧 runtime 在 W2 上通常读取不到 `params.model`，并可能回退到系统默认模型。该行为不一定报错，但会使用错误模型，属于静默正确性问题；回滚场景下需在验收中显式说明。

### 3.2 Dataset 状态

| 状态 | 示例 |
|---|---|
| D0 legacy | `vectorModel: "text-embedding-3-small"` |
| D1 canonical | `vectorModelId: ObjectId` |
| D2 dual | 两个字段均存在 |
| D3 invalid canonical | `vectorModelId` 中仍存 provider name |

新 Dataset schema 和运行路径只读取 `*ModelId`。D0 在新镜像上会得到 `undefined`，训练、检索和数据推送路径中的 `assertModelUsable` 会失败。

“schema 双字段 + getter 兼容”方案要求：

- 所有相关 schema（dataset、workflow-node input）**保留旧 model 字段**，同时**新增 required 的 `modelId` 字段**；
- 读取时取 `modelId`，若 `modelId` 缺失/无效则从 legacy `model` 字段取 provider name，再经 getter 解析；
- 因此 D0 在新镜像上仍可运行；D1 正常运行；D2/D3 由 getter 兼容规则处理；
- 双字段写入规则（新写是否同时写 model）由具体 schema 与保存路径决定，至少保持“modelId 必填、model 可选”。

### 3.3 system_models 状态

旧文档主要把类型、provider、激活状态、默认标记和 request config 放在 `metadata`。新 `loadSystemModels` 直接读取顶层字段并构建 id-keyed maps。

兼容要求：

- `loadSystemModels` 兼容两种 schema：metadata 结构（旧）与顶层扁平结构（新）；
- 同时构建 `model → modelData`（provider model 名/别名）与 `modelId → modelData` 两个 map；
- 默认模型解析顺序：`default_models` 中有效 id → legacy `isDefault*` flags → 既有同类型 fallback。

### 3.4 modelCompat 的能力边界

`withModelIdCompat` / `resolveModelId` 只处理固定 API 路径的入站请求体，不能覆盖：

- MongoDB 中存量 Workflow inputs；
- 内部 Workflow dispatch；
- Dataset 文档运行时读取；
- app detail 出站响应；
- 定时任务和已发布 app_versions。

本方案不依赖 modelCompat 覆盖上述内部路径：模型解析统一收敛在 cache getter 层。~~modelCompat 可继续承担 Open API 外部请求兼容。~~（⚠️ 已修订：双值方案下入站请求体的 legacy name 兼容由「schema 双字段 + handler 读取 fallback + getter」承担，modelCompat 整体移除，见 §6.8 与 §15。）

## 4. 新旧镜像兼容矩阵

### 4.1 当前实现

| 持久化状态 | 旧镜像 | 新镜像 |
|---|---|---|
| legacy-only | 正常 | Workflow/Dataset 运行失败 |
| canonical-only | 可能静默使用默认模型 | 正常 |
| dual | 正常 | 正常，但重复 Workflow key 需确定优先级 |
| canonical key + name value | 通常回退默认模型 | 运行失败 |

因此当前实现无法安全覆盖滚动升级窗口。

### 4.2 双 map + getters 兼容方案实施后

| 持久化状态 | 新兼容镜像行为 |
|---|---|
| legacy-only | getter 按 provider name 解析 modelData，正常运行 |
| canonical-only | 直接按 modelId 查询 |
| dual | 取有效 modelId；modelId 缺失/无效时用 legacy name 解析 |
| canonical key + name value | 按 provider name 解析 |
| 无法解析 | 显式返回模型不存在；不把 name 写入 id 字段；不静默改默认模型 |

注意：该矩阵描述的是**模型值解析**。Workflow 的 input key（`model` vs `modelId`）是独立的另一维度，取决于 dispatch 读取参数的 key 和迁移保留的 key。由于迁移保留 legacy input，且 schema 双字段，回滚后旧版本仍能读取旧结构；升级期间若有新写入，兼容层仍按双字段规则读取。

## 5. 方案对比

### 5.1 方案 A：只修改迁移脚本

做法：迁移不删除旧字段，改为 additive。

不足：新镜像上线但迁移尚未开始时，runtime 仍无法读取 legacy Workflow/Dataset；不满足场景 1。

结论：不可用。

### 5.2 方案 B：API middleware 重写请求体（模型名称 → modelId）

做法：扩展 `MODEL_COMPAT_PATHS`，对 Workflow debug、publish、dataset search 等路径重写 `model → modelId`。

不足：内部调用链（DB → runtime）不经过 HTTP middleware；读取端（app detail、runtime）与定时任务不可达；无法解决 dataset 文档读取和已发布版本。

结论：在双值方案（schema 双字段 + getter 兼容）下，middleware 的请求体重写职责被吸收，**`modelCompat` 及其代码可移除**（见 §6.8 与 §15）。

### 5.3 方案 C：前端 adaptStoreNodeInputs 兼容

做法：加载画布时把 `model` 改成 `modelId`。

不足：运行请求、定时任务、已发布版本、Dataset search 不经过前端；前端也未必具备完整可见模型和权限上下文。

结论：只能改善编辑器显示，不能保障运行。

### 5.4 方案 D：cache 双 map + getters 兼容输入（推荐）

做法：

1. 所有相关 schema 保留旧 `model` 字段，同时新增 required `modelId`；
2. `loadSystemModels` 同时构建 `model → modelData` 与 `modelId → modelData`；
3. 所有模型消费方统一经过 `getXXXModel(modelIdOrName)`，getter 内部兼容 modelId 与 provider model 名；
4. 迁移脚本 additive 补齐 `modelId` 字段，不删除 `model`；
5. 后续独立版本再移除 `model` 与兼容 map。

优点：

- 不修改核心业务代码对模型的消费方式；
- 缓存构建只增加一个 map 和一份 normalization；
- 与 `modelCompat` 思路一致（拦截现有逻辑并做兼容替换）；
- 兼容逻辑集中在模型解析边界，可整体 @deprecated 并在后续版本删除；
- 天然覆盖内部 runtime、dataset、chatConfig、usage 等所有经 getter 的调用。

边界：

- 需要确认 Workflow dispatch 读取 `modelId` 的 key 路径，若存在参数层需要读取 legacy `model` key 的场景，需在参数构造层做 key 兼容或依赖迁移补齐；
- 浏览器端 TTS 直接读 `ttsConfig.modelId`，服务端 getter 无法覆盖，仍需前端 fallback 或 app read 层规范化；
- getter 缺少 teamId/权限上下文，按 provider name 解析私有模型需明确规则（无 teamId 时仅系统模型）。

### 5.5 方案 E：全量双读双写 + 无恢复回滚

做法：所有集合长期保存 legacy + canonical，支持新旧实例同时读写和直接回滚。

优点：兼容能力最强。

缺点：需要改 model、dataset、app、version、eval、permission、defaults 等全部写路径；还要定义双字段冲突优先级和长期清理阶段。相对于当前目标过重。

结论：不采用。

### 5.6 推荐结论

方案 D 是当前目标下的最小正确实现。核心理由：

- 以“所有模型使用都经过 getter”为前提，getter 兼容 modelId/name 输入即可覆盖绝大多数消费路径；
- schema 保留 model + 新增 required modelId，双 map 构建缓存，天然支持迁移前、迁移中、迁移后与回滚；
- 不依赖 HTTP middleware、不修改 dispatch 算法、不建设长期双写；
- 后续版本移除 model 字段即可完成收敛。

## 6. 最小代码改动设计

### 6.1 schema 双字段

相关集合保留旧字段并新增 required `modelId`：

- Dataset schema（`packages/service/core/dataset/schema.ts`）：`vectorModelId`、`agentModelId` 为 required，`vlmModelId` 保持 optional（与旧 `vlmModel` 语义一致，见[技术设计文档 §4.1](./模型管理重构-技术设计文档.md#41-dataset-schema-模型字段)）；`vectorModel`、`agentModel`、`vlmModel` 保留为可选 `@deprecated`。
- Workflow node input：input 结构同时允许 `model` 与 `modelId` 两个 key；编辑器模板以 `modelId` 为准，旧 `model` key 由迁移保留。
- App chatConfig（`questionGuide` / `ttsConfig`）：保留 `model`，新增 required `modelId`（或读取时兼容）。
- Eval / permissions：同样保留旧字段，新增/保留 `modelId` / `resourceId`。
- usage_items：已双写 `model` + `modelId`，保持现状。

schema 双字段的注意点：

- Mongoose `strict` 对 dataset 等 schema 会在写入时丢弃未声明字段。因此保留旧字段必须同时写入 schema 声明（带 `@deprecated`），否则新版本保存会丢失 legacy 镜像；或者接受“新版本写入只写 canonical、legacy 由迁移与旧版本写入补齐”。
- required `modelId` 不能影响存量 legacy-only 文档的读取与校验；required 校验发生在写入路径，读取（lean）不受影响。

### 6.2 缓存双 map 与 normalization

关键文件：

- `packages/service/core/ai/model/utils.ts`
- `packages/service/core/ai/compat/resolveModelId.ts`
- `packages/global/core/ai/model/type.ts`（global cache 类型声明）
- 必要的 model type 定义

`loadSystemModels` 修改：

1. normalization 兼容两种 schema：
   - 顶层扁平字段存在时优先；
   - 顶层缺失时从 legacy `metadata` 补齐；
   - `isSystem` 缺失时由 `isCustom` 和 owner 信息推导；
2. 构建两个 map：
   - `systemModelIdMap`（key = `_id.toString()`）以及各类型 id map（现有）；
   - 新增 `model → modelData` 兼容索引（key = provider `model` 名，必要时含 alias `name`），同一名多个文档时 active/system 优先、first-wins；
3. 默认模型解析顺序：`default_models` 中有效 id → legacy `isDefault*` flags → 既有同类型 fallback；
4. 系统模型在内存中继续清理 team/creator 信息，不要求迁移前先删除数据库字段。

`resolveModelId` 增加兼容索引快速路径，保持 system-first、same-team、active-only 语义。

### 6.3 getters 兼容输入

关键文件：

- `packages/service/core/ai/model/cache.ts`
- `packages/service/support/permission/model/auth.ts`（`getModelById` 消费方）
- `projects/app/src/service/core/app/workflow.ts`（`getChatModelNameListByModules`）

`getLLMModel/getEmbeddingModel/getTTSModel/getSTTModel/getRerankModel/getVlmModel/getModelById` 统一改为：

```text
先按参数查 id map；
未命中且参数不是 ObjectId 时，按 provider model 名查兼容索引；
仍未命中返回 undefined。
```

- 对已经是 ObjectId 的输入，避免按名称再解析；
- 对 `modelId` 字段被误写入 provider name 的情况（W1/D3），可正确解析；
- `isImageEmbeddingModel` 等判定函数同步使用兼容解析；
- 无法解析时仍返回 undefined，由既有 `assertModelUsable` 显式报错，不静默改用默认模型。

前端/服务端读取模型展示（`getChatModelNameListByModules`）也会因 getter 兼容而正确显示旧应用模型名。

### 6.4 Workflow input key 兼容（持久化双 key + 参数传递双字段）

用户场景：前端传入之前缓存的工作流配置（nodes），其中模型信息仍是 `model` 而非 `modelId`。

方案（与 schema 双字段一致地推广到 Workflow input）：

1. **持久化双 key**：node inputs 同时保留 legacy `model` key 与 canonical `modelId` key。`embeddingModel/rerankModel/datasetSearchExtensionModel/datasetDeepSearchModel` 及 `datasetParams` 内嵌模型字段同理。迁移脚本 additive 补齐 `modelId` input，不删除 `model`。
2. **参数传递双字段**：`getWorkflowNodeRunParams`（`packages/service/core/workflow/dispatch/utils/runtime.ts`）构造 params 时同时输出：
   - `params.model` —— legacy input 的值（provider name 或 id）；
   - `params.modelId` —— canonical input 的值；canonical input 缺失时，把 legacy `model` 的值映射到 `params.modelId`；
   - 两者都有时以有效 `modelId` 为准，`model` 作为 fallback 与展示；`modelId` 是 name 值（W1 residue）时交给 getter 按 name 解析。
3. **后台消费**：所有 dispatch 节点继续读 `params.modelId`（getter 兼容 name/id）；需要模型名展示的路径读 `params.model`。节点业务代码零改动。
4. **鉴权**：`extractWorkflowModelIds` / `authModels`（`packages/global/core/workflow/utils.ts:68`、`packages/service/support/permission/model/auth.ts`）必须同步识别 legacy key（`model/embeddingModel/rerankModel/...`），否则老前端只传 `model` 时模型权限校验会漏掉。
5. **前端**：编辑器模板以 `modelId` 为准；画布展示时 legacy key 映射/隐藏 deprecated 副本（`adaptStoreNodeInputs`）；新保存只写 canonical，legacy 仅存量保留 + schema 声明防 strip。
6. **datasetParams**：内嵌模型字段同样保留旧 key 并补新 key，运行时双字段构造。

优先级规则：

- 同 input 双 key：有效 `modelId` 优先，`model` 为 fallback；
- `modelId` 是 name 值（W1 residue）：getter 按 name 解析；
- 双 key 值不一致：以持久化的 `modelId` 为准；若迁移与业务写入并发，由 CAS 记录冲突并重跑迁移。

注意：`params.model` 增加字段不影响节点逻辑（多一个字段）；但 usage 计费/展示若使用 `params.model` 需注意其可能是 name，展示层走 getter 获取 display name 更稳妥。

### 6.5 Dataset 读取兼容

由于 getter 支持 name，Dataset 读取只需保证 `modelId` 字段缺失时能取到 legacy `model`：

- 在 dataset 进入 search/training/collection 等业务逻辑前，统一补一个只读归一化：`vectorModelId = dataset.vectorModelId || dataset.vectorModel`（name 可被 getter 解析）：
  - `packages/service/core/dataset/search/index.ts`
  - `packages/service/core/dataset/training/controller.ts`
  - `packages/service/core/dataset/collection/controller.ts`
  - workflow dataset search / agent dataset sub-runtime
  - usage 计费与 dataset snapshot
- 或者让调用方在传入 getter 前自行 fallback；推荐集中 helper，避免散落。
- schema 双字段后，`dataset.vectorModelId` 对 legacy-only 文档为 undefined，此时使用 `dataset.vectorModel`。

### 6.6 chatConfig runtime fallback

questionGuide/TTS 实际运行入口按以下顺序取模型：

1. 有效 `config.modelId`；
2. `resolveModelId(config.model, teamId)` 或 getter 按 name 解析；
3. 仅当两者均未配置时，使用原有默认模型逻辑。

配置存在但无法解析时显式失败，禁止静默换默认模型。

浏览器端 TTS（`projects/app/src/web/common/utils/voice.ts` 等直接读 `ttsConfig?.modelId`）需要前端极小 fallback，或在 chat init 读取 chatConfig 时由服务端补 `modelId`。

### 6.7 前端显示兼容

`adaptStoreNodeInputs` 只承担画布展示：

- legacy key 映射到当前模板 key；
- 可见模型列表已加载且 model/name 命中时，把 value 显示为 id；
- dual 数据只保留 canonical input 进入画布；
- 新保存只写 canonical；若出现 legacy residue，兼容层仍可读取并由后续迁移重跑补齐。

前端不作为运行兼容的可靠性边界。

### 6.8 modelCompat 移除方案

双值方案下，入站请求体的 legacy name 兼容由 schema 双字段 + handler 读取 fallback + getter 承担，`withModelIdCompat`（`packages/service/common/http/modelCompat.ts`）与 `MODEL_COMPAT_PATHS` 可移除。理由：

- 双值方案本来就在 schema/getter 层支持 name 输入；middleware 在鉴权前重写请求体（`resolveModelId` 无 teamId，只解析系统模型）反而局限：无法解析同团队私有模型；
- 解析下沉到 handler（有 teamId 上下文）后能力更完整；
- 内部调用链（DB → runtime）本就不经过 middleware，双值方案已覆盖。

移除前提（必须同时落实，否则外部调用方传 name 会静默丢失）：

1. **入站 OpenAPI schema 补回可选 legacy 字段**（`@deprecated`），覆盖：
   - `/core/dataset/create`、`/core/dataset/update`、`/core/dataset/createWithFiles`：`vectorModel/agentModel/vlmModel`（含 `datasetParams` 内嵌）；
   - `/core/app/create`、`/core/app/update`、`/core/app/version/publish`：`chatConfig.questionGuide.model`、`chatConfig.ttsConfig.model`（当前 `OpenAPIAppQGConfigSchema`/`AppTTSConfigTypeSchema` 只有 `modelId`，zod 默认 strip 会丢弃 legacy `model`）；
   - `/core/ai/skill/debugChat`：`model`。
2. **handler 读取 fallback**：`*ModelId ?? legacy`（name 交给 getter 解析），覆盖 dataset create/update、app create/update/publish、skill debugChat。
3. **鉴权识别 legacy 字段**：`authModels`/`extractWorkflowModelIds` 同步收集 legacy key（与 §6.4 相同要求）。

移除后行为等价性：

- 外部调用方仍传 `model: "gpt-4o"` → schema 保留该字段 → handler 读 `*ModelId` 为空时 fallback 到 legacy → getter 按 name 解析 → 调用正常；
- 外部调用方已传 `modelId` → 直接走 canonical；
- 响应侧不受影响（`modelCompat` 只处理请求体），“不暴露内部 ObjectId”验收点不变。

## 7. additive migration 设计

### 7.1 通用规则

- 只补 canonical 字段，不 `$unset` legacy（与 schema 双字段一致）；
- 只写成功解析成真实 ObjectId 的值；
- 目标 canonical 已有有效值时不覆盖；
- unresolved、ambiguous、conflicts 明确计数；
- 所有步骤可重复执行，第二次对已完成记录 no-op；
- handler 保持 root-only 手动调用，不自动绑定 pod 启动。

迁移完成前，缓存双 map + getters 兼容已保证运行流量可用；迁移的目的主要是让数据库逐渐收敛到 canonical 形态，降低对兼容层的长期依赖。

### 7.1a 代码现状与需要调整的步骤

当前 `migration.ts` 的实现是破坏式（删除 legacy / 原地 rename key），与双值方案冲突，必须调整为 additive：

| 步骤 | 当前代码（破坏式） | 调整为（additive） |
|---|---|---|
| Step 1 | `dropModelUniqueIndex` 直接删除 | 受控升级流程：关闭模型配置写入并停止旧 Pod 后删除旧唯一索引，再创建新索引 |
| Step 2 `migrateModelData` | `$unset metadata/isCustom/isDefault*/tmbId/teamId` | 全部保留；只从 metadata 补齐缺失顶层字段、补 isSystem 与必填默认值；继续收集 defaults/channel configs |
| Step 4 `migrateDatasets` | `$unset vectorModel/agentModel/vlmModel` | 只 `$set *ModelId`（解析成功时），legacy 字段保留 |
| Step 5 `migrateAppWorkflows` | `migrateInput` 原地 `input.key = modelId`（rename）；chatConfig `delete cfg.model`；datasetParams `delete val[field]` | legacy input 保留，**新增** canonical input（复制并转换值）；chatConfig 保留 `model` 并补 `modelId`；datasetParams 保留旧字段并补新字段；已有有效 canonical 不覆盖；W1 residue 解析 |
| Step 6 `migrateEvaluationData` | `$unset evalModel` | 只补 `evalModelId`，保留 `evalModel` |
| Step 9 `migrateModelPermissions` | `$unset resourceName` | 只补 `resourceId`，保留 `resourceName` |
| Step 7 / 8 / 10 | 已 additive（保留 model + 补 modelId；`$setOnInsert`；幂等创建） | 不变；Step 7 增加 unresolved 统计 |

Step 5 的“保留旧 input + 新增 canonical input”与持久化双 key（§6.4）一致：迁移后的数据同时携带 `model` 与 `modelId`，新老镜像各自按需读取；重复 canonical key 去重，以有效 canonical 优先。

### 7.2 Step 1：索引

- 创建 `teamId_1`、`tmbId_1`、`isActive_1_provider_1` 及新的模型作用域索引；
- 删除旧 global `model_1` unique index 属于受控升级流程，**只能在所有旧 Pod 已停止且模型配置写入已关闭后执行**；
- `initv4170` 执行前必须确认旧镜像不会继续写入，执行后也不得在旧 Pod 上恢复模型配置写入；
- 该步骤不改变读取数据，但会影响回滚后的旧写路径，所以失败回滚必须恢复备份中的索引，并在恢复旧镜像前重新启用旧模型配置约束。

### 7.2a 受控升级流程顺序

1. 备份 `system_models` 数据及索引定义；
2. 关闭模型配置写入入口，至少覆盖模型创建、更新、删除和 JSON 导入；
3. 停止并确认所有旧 Pod 已退出，不允许旧 Pod 继续接受模型配置请求；
4. 部署兼容版新镜像，但先保持模型配置写入口关闭；
5. root 手工执行 `initv4170`，完成索引迁移和数据迁移；
6. 验证迁移结果、索引状态和运行流量后，再开启新版本模型配置写入；
7. 若迁移失败，恢复备份中的索引和数据后再回滚旧镜像。

### 7.3 Step 2：system_models

- 从 metadata 补齐缺失顶层字段；
- 补 `isSystem` 和新 schema 必填默认值；
- 不删除 metadata、isCustom、isDefault*、team/creator、requestUrl/requestAuth；
- 继续收集 defaults 和 channel configs 给后续步骤。
- 缓存双 map 已能兼容两种 schema；此步骤使缓存归一更稳定。

### 7.4 Step 3：name → id map

- active system model 优先；provider model 与 alias 分开建 map；
- 重名 first-wins 但记录 ambiguous；
- 后续迁移必须验证解析结果是 ObjectId，不能把原 name 原样写入 id 字段。

### 7.5 Step 4：datasets

- legacy 存在、canonical 缺失/无效且解析成功时，写 `*ModelId`；
- legacy 字段保留；
- unresolved 不写并计数。
- 若 schema 双字段已落实，此步骤只是把存量 D0 补齐为 D2。

### 7.6 Step 5：apps + app_versions

- legacy input 保留；
- 缺少 canonical input 时，新增 canonical 副本并写 id；
- W1 residue 成功解析后更新为 id；
- 已有有效 canonical input 不覆盖；
- datasetParams 保留旧字段并补新字段；
- chatConfig 保留 model 并补 modelId；
- 去除重复 canonical key，采用有效 canonical 优先。

升级期间模型配置写入关闭；其他业务配置仍可按部署策略写入。为防止迁移与在途请求互相覆盖，apps 使用 `_id + updateTime`、autosave version 使用 `_id + time` 做 CAS；datasets、eval、usage_items、resource_permissions 在写入 canonical 字段时匹配读取快照中的原值或字段缺失状态。条件不匹配时计入 conflict，不覆盖并发写入，重跑迁移即可继续处理。

### 7.7 Step 6：eval

只补 `evalModelId`，保留 `evalModel`；unresolved 不写。

### 7.8 Step 7：usage_items

保留现有 additive 结构：保留 model、补 modelId。增加解析成功校验和 unresolved 统计。

### 7.9 Step 8：default_models

继续 `$setOnInsert` 初始化；本兼容版本不删除 system_models 上的 legacy default flags。

### 7.10 Step 9：权限

只补 resourceId，保留 resourceName；unresolved 不写。

### 7.11 Step 10：Channels

保留现有按配置去重及 `Migrated:` 跨 run 守卫；不删除 legacy request config。

该步骤写入 aiproxy，Mongo 备份恢复不会自动撤销。旧镜像不会读取新 Channel，可保留；如需清理，按迁移响应记录人工删除。

## 8. 配置写入与并发说明

本次改造不新增写冻结拦截、状态开关或 API 拒绝逻辑。双 map + getters + schema 双字段本身覆盖迁移前、迁移中、迁移后的 legacy/dual/canonical 读取；迁移写入通过 CAS 或 canonical 字段快照条件检测并发修改，记录 conflict，不覆盖在途保存，重跑即可继续补齐 canonical 字段。

## 9. 迁移结果和完成条件

不新增长期 migration state 服务。扩展 `initv4170` 返回：

- 每一步 checked/migrated/skipped；
- unresolved 数量及资源 id + 字段定位；
- ambiguous model names；
- app/app_version CAS conflicts；
- legacy-only remaining counts；
- channel created/skipped/failed。

以下条件用于判断迁移是否完成，不作为写入解锁条件：

1. 所有可解析 legacy 引用已存在有效 canonical id；
2. unresolved=0，或已逐条确认并修复/接受隔离；
3. conflicts=0；
4. 迁移第二次执行对已完成记录 no-op；
5. Workflow/Agent、Dataset、questionGuide/TTS 冒烟测试通过。

> 在双 map + getters 兼容下，即使迁移结果仍存在 unresolved（无法解析的模型名），运行流量也不会因为兼容层而中断；unresolved 记录会在具体模型调用时显式报错并进入日志，便于人工修复。

## 10. 发布与回滚流程

### 10.1 发布

1. 备份所有受影响 Mongo 集合，并验证恢复；
2. 在备份副本预跑迁移；
3. 关闭模型创建、更新、删除和 JSON 导入入口，并确认所有旧 Pod 已停止；
4. 部署兼容镜像，但保持模型配置写入关闭；
5. 在尚未迁移的真实数据上完成运行流量冒烟；
6. 手动执行 `initv4170`，完成索引迁移和数据迁移；
7. 验证迁移结果、索引状态和运行流量；
8. 仅在验证通过后开放新版本模型配置写入。

### 10.2 失败回滚

1. 停止新镜像；
2. 恢复迁移前 Mongo 备份；
3. 回滚旧 FastGPT/pro 镜像；
4. 验证已有业务。

本项目没有统一的配置写冻结接口；本次由部署侧在升级前关闭模型配置创建、更新、删除和 JSON 导入入口，并在迁移验证完成后重新开放。若失败回滚选择恢复迁移前全量备份，升级窗口内产生的配置写入会随备份恢复而丢失。运维必须在执行恢复前评估并记录窗口内变更；需要保留这些变更的部署应自行提供增量备份或操作日志回放能力。运行记录是否纳入恢复同样由部署备份策略决定。

> 注意：本方案的读取兼容（双 map + getters + schema 双字段）在回滚场景下能保证“迁移后 Mongo 数据中保留的 legacy 字段”被旧镜像读取；失败回滚仍以备份恢复为准。

## 11. 四个核心场景

### 场景 1：新镜像、尚未执行迁移

前置：数据库为纯 legacy 格式。

预期：

- `loadSystemModels` 兼容 metadata 与扁平 schema，同时构建 model 名与 modelId 双 map；
- 前端或 API 传入的 workflow nodes 中模型信息仍是 `model`（name），后端经 getter 兼容解析；
- getters 对 `modelId`（缺失或为 name 值）与 provider name 均可解析；
- Dataset schema 双字段后，D0 记录仍可运行；
- 已有 Workflow、Agent、Dataset search/training 正常；
- 升级期间模型配置写入关闭；运行流量和非模型配置迁移可继续执行。

### 场景 2：迁移执行中

前置：集合中同时存在 legacy-only 与 dual 数据。

预期：

- 双 map + getters 同时解析两种形态；
- batch 之间运行流量无异常；
- unresolved 不污染 modelId；
- 允许配置写入；CAS 记录并发覆盖风险并支持迁移重跑。

### 场景 3：迁移完成

预期：

- 所有可解析引用都有 canonical id；
- 新 runtime 正常（canonical 优先，legacy 兼容兜底）；
- 验证通过后完成迁移；
- 后续新保存只写 canonical，legacy 字段由后续版本清理。

### 场景 4：升级失败并回滚

预期：

- 停止新镜像并恢复备份；
- 回滚旧镜像后读取原 legacy 数据；
- 已有业务恢复；
- 迁移保留 legacy 字段使旧镜像可读迁移后数据，但失败回滚仍以备份恢复为准。

## 13. 风险与限制

| 风险 | 缓解 |
|---|---|
| 无法冻结模型配置写入或确认旧 Pod 已退出 | 不执行索引迁移；继续提供运行流量，待部署侧完成写入关闭和实例收敛后重试 |
| legacy name 对应多个模型 | deterministic first-wins，同时报告 ambiguous，迁移完成后人工确认 |
| legacy model 已删除 | unresolved 不写 modelId，保持显式错误并人工修复 |
| 鉴权只识别 `modelId` key，legacy `model` key 绕过权限校验 | `extractWorkflowModelIds` / `authModels` 同步识别 legacy key |
| 移除 modelCompat 后外部调用方传 name 被 zod strip | 入站 schema 补回可选 legacy 字段（`@deprecated`），handler 读取 fallback |
| 双 key input 在画布中重复显示 | `adaptStoreNodeInputs` 映射/隐藏 deprecated 副本 |
| 浏览器端 TTS 直接读 `ttsConfig.modelId` | 前端极小 fallback，或服务端 chat init 读 chatConfig 时补 `modelId` |
| getter 无 teamId 上下文，私有模型按 name 解析有歧义 | 无 teamId 时仅解析系统模型；有 teamId 时查询统一索引，重复私有名按 first-wins，不运行时扫描 |
| Step 10 外部 Channel 无法随 Mongo 回滚 | 可保留或按迁移返回清理 |
| 迁移与请求并发 | app/version 更新增加 CAS 作为最后保护 |
| 兼容代码长期残留 | 后续单独 contract release 清理 |

## 15. 与本分支已存在改动的关系

本分支（`refact/platfrom-model-manage`）已有以下相关改动，与本文方案存在交互：

- **`getWorkflowNodeRunParams` 是唯一运行时参数构造点**（`packages/service/core/workflow/dispatch/utils/runtime.ts`），双 key 参数传递只需在此实现：legacy `model` key 映射进 `params.modelId`，同时保留 `params.model`。这是新增行为，不影响该函数对非模型输入的处理。
- **模型鉴权**（`extractWorkflowModelIds` + `authModels`，`packages/global/core/workflow/utils.ts:68` 与 `packages/service/support/permission/model/auth.ts`）只识别 `*ModelId` key。双 key 方案下，legacy `model` key 必须被鉴权同步识别，否则 legacy-only 保存/调试会绕过模型权限校验。这是双 key 方案必须配套的一处改动。
- **前端 `adaptStoreNodeInputs`**（`projects/app/src/web/core/workflow/utils.ts`）：⚠️ 现状核查（2026-08）——该函数**当前不处理模型 key**（仅处理 ifElseList/agent 手动选择/datasetSearchNode），`storeNode2FlowNode` 按模板 `aiModelId` key 匹配 storeInput，legacy `model` key 匹配不上，画布落到模板默认值。目标（§6.7）：legacy key 映射到模板 key（可见模型命中时转 id、无法解析保留 name）、dual 只保留 canonical input 进画布。该改动只影响展示，不做运行可靠性保障。
