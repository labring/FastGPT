# 根因修复规范

适用于修复 bug、处理 review 意见，以及审查修复类改动。修复方按本文修改，审查方（[pr-review](../skills/system/pr-review/SKILL.md)）按本文判定修复是否成立。

## 修复流程

1. **把问题当线索，不当清单**：bug 报告和 review 意见描述的是症状。先复现或推导出触发条件，不以"让这条评论关闭"为目标。
2. **写清根因与不变量**：说明问题由哪一层的哪个契约、状态来源或流程顺序导致，以及修复后应始终成立的不变量。
3. **在归属层修正**：在根因所在层收紧契约、统一入口或修正状态来源，并按[分层架构](./syntax.md#分层架构)放置修改，不在调用方或下游补偿。
4. **排查同类**：检查同一根因影响的全部入口、同类场景，以及其他位置的相同写法，一并修正。
5. **验证**：测试覆盖原问题和同类场景；修复类测试在回退修复代码后应失败。
6. **需要调整设计时先说明**：说明当前设计错在哪里、新方案如何满足不变量，以及对旧数据和调用方的兼容影响；影响较大时先与用户确认。

## 补丁式修复特征

出现以下任一特征，即视为补丁式修复，修复不成立：

- 只针对被指出的输入或场景加特判，同类场景仍会出错。
- 在调用方或下游做补偿，问题所在的归属层没有修正。
- 用吞错、兜底默认值、重试掩盖错误，而不是消除其产生条件。
- 新增标志位、重复状态或旁路分支绕开问题。
- 放宽源头契约（枚举、单位、可选字段）后，在读取、保存、导入、迁移等多处补加换算和兜底，而不是收紧源头契约。
- 同一根因在多个位置分别修补，或上一轮修复后同类问题在新位置出现。

## 合理的局部处理

只有存在明确的外部约束时，才允许在边界做局部兼容，例如已发布版本的存量数据、不可控的第三方接口或旧客户端。此时需要：

- 说明约束来源及其影响范围；
- 把兼容逻辑限制在读取边界或接口边界，不扩散到业务流程；
- 在兼容代码旁注释原因，以及何时可以移除。

## 范围

重新设计只涉及根因相关的模块，不借修复顺带重构无关代码。根因在其他模块或 `pro` 中时，明确指出位置，并在对应位置修复。
