# 根因修复与代码收敛规范

适用于修复 bug、处理 review 意见、迭代更新既有功能，以及审查修复和更新类改动。修复/开发方按本文修改，审查方（[pr-review](../skills/system/pr-review/SKILL.md)）按本文判定方案是否成立、是否出现补丁式代码膨胀。

## 修复与更新流程

1. **把问题当线索，不当清单**：bug 报告和 review 意见描述的是症状。先复现或推导出触发条件，不以“让这条评论关闭”为目标。
2. **写清根因与不变量**：说明问题由哪一层的哪个契约、状态来源或流程顺序导致，以及修改后应始终成立的不变量。
3. **在归属层收敛修正（收敛优先于叠加）**：优先在根因所在层收紧契约、统一入口、删减冲突分支或修正状态来源，并按[分层架构](./syntax.md#分层架构)放置修改；不在调用方或下游打补丁补偿，不靠持续叠加特判与开关完成更新。
4. **按对称链路排查同类**：不要只改被指出的单行或单一路径，同步核对同一数据/状态流经的对称入口——**读与写（列表/详情/新建/增量编辑）、导入与导出、迁移回填前后窗口、正常/取消/超时/重试分支，以及主仓、`pro` 与 SDK 消费方**，一并收口。
5. **裁剪或改方案时同步清残骸**：复审迭代中若移除某分支、收缩功能范围或替换旧写法，同步清理失去调用的重写函数、多余接口/Schema 外壳、死分支、未使用 i18n key 及过时测试与 PR 描述。
6. **验证**：测试覆盖原问题和同类对称场景；修复类测试在回退修复代码后应失败。修复提交同样受[代码规范](./syntax.md)约束，推送前对本轮增量自检高频红线，避免修一处问题又引入新的规范违规。
7. **需要调整设计时先说明**：说明当前设计错在哪里、新方案如何满足不变量，以及对旧数据和调用方的兼容影响；影响较大时先与用户确认。

## 补丁式修复与更新特征

出现以下任一特征，即视为补丁式修改或代码膨胀，修复/更新不成立：

- 只针对被指出的单个输入或测试用例加硬编码特判，正常/常见同类场景仍会出错。
- 在调用方或下游做补偿，本 PR 负责的归属层没有修正。
- 用吞错、兜底默认值或盲目重试掩盖本可消除的根因错误。
- 新增标志位、布尔分叉参数（如 `isXxx`）、重复状态或旁路分支绕开原有逻辑，使代码越改越臃肿。
- 放宽源头契约（枚举、单位、可选字段）后，在读取、保存、导入、迁移等多处补加换算和兜底，而不是收紧源头契约。
- 同一根因在多个位置分别修补，或上一轮修复后同一核心缺陷在正常/常见路径下仍未根除（不含作者已合理收紧边界后、仅在叠加多重极端假设时才出现的低概率边缘情况）。
- 更新或替换既有行为时保留失效的旧分支/旧开关/死代码，持续叠加而不收敛。

## 合理的局部处理与工程防护

以下两类边界处理属于合理设计，不视为“补丁式修复”或“用兜底掩盖错误”：

1. **明确的外部约束兼容**：例如已发布版本的存量数据、不可控的第三方接口或旧客户端。需说明约束来源与影响范围，将兼容逻辑收敛在读取或接口边界，不扩散到核心业务流程，并在代码旁注释原因及可移除时机。
2. **务实的工程防护**：在明确的容量、并发、外部依赖超时或既有组件约束下，采用有界缓冲保护、显式降级、清晰错误边界或调用方隔离来防止故障扩散，只要行为语义明确、不静默破坏核心数据或安全不变量，即属合理方案。

## 范围

- 排查同类与重新设计只覆盖本次根因直接影响的模块，不借修复顺带重构无关代码。
- 根因确在其他模块或 `pro` 中且造成实质缺陷时，明确指出位置并在对应位置修复；若仅涉及复用的既有组件本身可接受的历史边界、且未引发严重后果（安全/越权、数据损坏或丢失、计费错误、主流程崩溃），不借机扩大改造旧组件。
