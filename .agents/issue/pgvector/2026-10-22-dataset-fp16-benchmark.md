# 开发库 FP16 局部索引与百万向量集成测试记录

2026-10-22；代码提交 `39da31d9ed8e03ddcff10f14acfd04c08b23bed0`；[PR #8083](https://github.com/labring/FastGPT/pull/8083)。原始指标见同目录 `2026-10-22-dataset-fp16-results.json`。此次使用真实开发 PG、Mongo 和 Redis，记录用于后续修改方案时复测。

**结论与采用的配置**

业务增删后的团队、知识库 Redis 计数与 PG 实际行数一致。大于 30000 条的知识库，经真实 10 分钟延迟后由 MQ 全局串行构建 FP16 局部 HNSW，Mongo 状态与 PG 目录核验一致。已有有效索引不会重建，后续写入由 PG 增量维护。

4 核 PG 上，同机保持 20 个请求并发、8 个活跃 PG 连接时，跨 4 库百万条约 395 QPS，平均 50.6 ms，P95 74.3 ms。20 个活跃连接约 339 QPS；并非连接越多吞吐越高。生产应用连接池仍保持原默认值，本次只在测试进程调整连接数。

从开发电脑经过约 18 ms RTT 访问 Mac mini，包含计数路由和 Mongo 回查的完整向量召回，两轮默认 10 连接均约 121 QPS、平均 165 ms。此数字包含本地模拟 embedding HTTP 和 token worker，不包含真实模型网络、HTTP API 鉴权、全文检索或最终业务答案生成。

`ef_search=100` 的跨库 Recall@100 为 99.92%。200/400/800 在本批样本上没有改善召回率，继续增大会增加开销。该结论仅适用于此批合成数据、这 100 个查询和当前参数，不能直接当作生产容量承诺。

**环境与数据**

- 数据库：Mac mini 上现有开发实例，PostgreSQL 15.14 / pgvector 0.8.0，`postgres.public.modeldata`；Mongo `fastgpt`；现有 Redis。
- PG 容器：4 核 CPU、16 GiB 内存，禁用容器 swap；`shared_buffers=4GB`、`maintenance_work_mem=4GB`、`effective_cache_size=12GB`、`work_mem=16MB`、`max_wal_size=8GB`、`max_parallel_maintenance_workers=2`。两个并行维护辅助进程加一个主进程属于同一个构建任务。
- 按用户确认移除了开发库旧的全局 FP32 `vector_index`，保留原始向量和普通索引。PG 参数和资源限制保留于开发库，没有修改部署 YAML。
- 新增 4 库，每库 250000 条、每库 16 个文档，共 1000000 个 FP32 `vector(1536)` 与一一对应的 Mongo 数据块。大批量夹具用 binary COPY + Mongo insert_many；增删功能样例另走真实业务服务，未调用外部收费 embedding。
- 数据构造：NumPy `default_rng(20261022)` 生成 1024 个归一化 1536 维簇中心；各批独立种子 `2026102200 + group * 100000 + offset`，`offset` 每批递增 1000；向量为 `0.75 * center + sqrt(1 - 0.75**2) * normalized_noise` 后归一化，按 FP32 写入。
- 100 条查询用 `default_rng(2026102299)`、簇序号 `(arange(100) * 37) % 1024`，同样混合归一化噪声；这些查询未插入数据集，避免向量本身命中的偏差。
- `LIMIT=100`；每个 ready 大库独立取 100 个候选，FP32 重排后统一合并取 100；精确对照用原始 FP32 全量距离计算。所有测试均检查结果数量为 100；所有性能样本无错误。
- 索引参数 `m=16, ef_construction=128`；`hnsw.iterative_scan=relaxed_order`、`hnsw.max_scan_tuples=100000`。其他参数沿用应用实现。
- 基准使用热缓存：每组 100 个不同查询，按闭环并发重复运行，20 并发组持续至少 30 秒；提高 ef 的开发网络组持续至少 20 秒；单并发组至少 10 秒。精确对照各执行 100 条，不与建图重叠。
- 业务集成在本机调用真实服务；未启动整个新版本 Web 应用或执行浏览器/HTTP 鉴权流程。PG 纯查询基准在 Mac mini 上执行本次代码生成的同一查询构造器和相同事务参数，排除开发网络、Mongo、Redis、embedding。

**真实集成检查**

- 业务 `createDatasetData` 写入正文、答案与 Mongo 全文记录：生成 2 条向量，团队和知识库缓存均与 PG 一致。
- 业务修改替换旧向量，业务删除清理 Mongo、全文和向量；验证计数恢复 0，零值可以缓存命中。
- 统一向量入口：插入、单 ID 删除、ID 列表删除、按文档删除、按知识库删除；逐步核对两级 Redis 计数和 PG 实际行数，删除一个库不影响另一个库。
- 30000 条不投递，30001 条投递；连续 100 次同库通知只保留一个延迟任务，时间戳不变（100 次业务通知约 349 ms）。缓存命中本身不重复通知。
- 没有缩短首次构建的 10 分钟延迟：首次 25 万条任务在约 600088 ms 后启动，30001 条验证任务约 600066 ms 后启动。
- 两个实际 worker 进程同时运行；监测 PG CREATE INDEX 主进程及 `pg_stat_progress_create_index`，并发构建数最大为 1。不能把两个并行维护辅助进程误算为三次建索引。
- 逐步观测 pending → building → ready，目录 `indisvalid/indisready` 均为 true；终端日志每 5 秒输出真实阶段、blocks、tuples 与耗时。
- 再次执行已就绪索引的任务时 OID 不变；混合大库与无索引库分组查询返回 100 条。
- 25 万条库索引就绪后，再通过业务服务插入数据：新数据立即可召回，文档白名单过滤有效；调用真实 `delCollection` 后计数恢复 250000，Mongo 数据块和文档被删除，索引 OID 不变。
- 构建与查询期间未出现超出 maintenance_work_mem 的 graph spill NOTICE；容器 swap 为 0，OOM 事件为 0。构建时观察 PG 容器约 8.16 GiB 内存使用，4 GiB 构建预算没有挤爆 16 GiB 容器。

**计数路由开销**

**修复、校验与复测资料**

实际原生 Node ESM 启动暴露 pg 的 CommonJS 导出互操作问题：命名导入 escapeLiteral、命名空间访问 Pool 都可能失败。已统一使用 pg 默认导入，提交 `39da31d9ed`。相关 3 文件 44 个局部测试通过；TypeScript 与 upstream/main 同为 76 条已有诊断，新引入 0 条；未手动运行全量仓库测试。

开发业务测试使用 Node 24.16.0。此机 Node 25.2.1 在 macOS 下的 availableMemory 数字明显偏小，阻止文本 worker 的资源准入；切换到项目支持的 Node 24 完成测试，未修改业务内存保护。

复测原件保存在 Mac mini：`/Volumes/code/dev/FastGPT/local/fastgpt-dev/benchmarks/fp16-20261022/`，包含 run manifest、原始向量查询样本、精确参考 ID、各轮指标、实际运行脚本、查询构造器 bundle 和修改前 PG 配置。数据库口令只由本地开发 .env 读取后通过标准输入传递，没有写入这些原件。

后续修改只需保留当前 4 库数据，用新代码重新生成查询构造器，再运行相同的 100 条查询、相同 LIMIT / ef / 并发 / 连接数。比较前确认没有并行建索引、VACUUM 或批量写入；应用侧和 PG 同机侧指标分开比较。大批量合成夹具不包含百万条全文分词索引，此测试不评价全文检索、语义模型质量、HTTP 鉴权或计费。
