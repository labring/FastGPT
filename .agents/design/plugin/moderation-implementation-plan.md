# FastGPT 内容审查插件接入计划

> 状态：阶段二（管理侧闭环与管理端 UI）已全部实现并通过测试，待进入阶段三业务调用锚点设计。
> 范围：FastGPT 主仓；Marketplace/API 和插件 SDK 若需配套改动，按任务说明协调相应仓库。

## 概述

插件侧已提供独立的 `moderation` 类型及同步文本审查接口：通过 `getModeration` 读取插件详情、`checkModeration` 调用审查，并返回标准化的 `ModerationResult`（总体 `verdict`、`provider`、命中明细 `hits` 等）。FastGPT 当前管理和插件市场主要按 `tool` 建模，尚未接入内容审查类型。

本计划分阶段完成 FastGPT 管理侧发现/安装、配置和测试调用；设计并接入明确的业务调用锚点；展示多个审查视角的独立结果；并使插件 Marketplace 能展示、发布、下载和安装内容审查插件。首版按**同步文本审查**规划，不包含图像/音视频、异步回调或自动化审核策略。

## 当前基线与影响范围

- FastGPT 后端已统一创建 `FastGPTPluginClient`，但 FastGPT 依赖的 `@fastgpt-plugin/sdk-client` 版本与包含 moderation 方法的 SDK 版本需要在实现前核实、对齐。
- 现有系统插件管理页、配置表单和列表类型主要依赖 System Tool 契约；内容审查不应伪装成可运行的 tool 或工具集。
- FastGPT 自带的 `projects/marketplace` 当前将包索引、上传、列表及下载统计限定为 `tool`；仅修改主应用卡片不足以完成市场接入。
- `packages/test/moderations/moderationTest` 可作为本地联调插件来源；不需要在本计划中重新实现 provider 或插件生命周期。

## 设计原则与建议

1. **作为独立插件类型贯穿全链路。** 管理、安装、配置、调用、市场展示均保留 `moderation` 类型；共用通用的包、版本和来源能力时，不能把审核插件送入 tool 的输入输出或运行逻辑。
2. **以插件返回的标准结构为准。** 每次审查保留插件/provider 标识、总体裁决及逐项命中；`hits` 是明细，不代替总体裁决。Provider 返回的 `verdict: error` 和插件调用/传输失败应分别呈现。
3. **不隐式制定放行策略。** 本次接入负责调用和展示，不根据标签、命中分数或多个插件结果自行推导“通过/拦截”。若产品需要统一聚合或自动阻断规则，应作为明确、可配置的产品策略单独定义。
4. **调用锚点先评审再实现。** 建议首个业务锚点采用显式、可追踪的工作流审核步骤，便于用户控制审核时机和后续分支；应用级自动前置/后置审核可作为备选，但需另外确定覆盖范围、失败策略和兼容性。该建议不是已批准的需求结论。
5. **测试调用不泄露密钥。** 测试输入、插件 secrets 和响应都通过服务端调用链处理；前端只接收渲染所需的数据，不将 secrets 写入日志、URL 或客户端持久化状态。

## 插件卸载与恢复统一（已确认）

- [x] Plugin Server：同 source、pluginId、version、etag 安装幂等；增加不依赖上传的恢复接口，复用文件并注册运行时；prune 后明确失败。
- [x] FastGPT 系统工具：卸载先禁用 system 安装，再设 Offline；恢复先激活远端，再设 Normal；保留凭据与配置。
- [x] FastGPT 审核插件（最新设计）：管理列表隐藏已卸载插件，不提供后台独立恢复弹窗；通过重新上传 pkg 或插件市场重新安装恢复，保留配置且不自动启用审核。
- [x] pkg 上传确认与市场安装：仅恢复安装成功项的本地状态，重复 active 上传不得降为 pending。
- [x] 定向验证：插件仓库/用例/路由/客户端测试，FastGPT 状态更新与上传确认测试，类型检查；不执行 prune 或全量测试。
- [ ] 联调验收：同时部署新 Plugin Server 和 FastGPT 后，浏览器验证两类插件卸载、后台恢复、同包上传及市场恢复。

### 状态边界

Plugin Server 安装状态按 source 隔离，system 卸载不影响团队安装；插件本体和运行时仅在无人引用时禁用。直接恢复必须在文件和安装记录仍存在时完成，清理后要求重新上传。所有远端调用成功后才能更新 FastGPT 状态，失败可重试。系统工具管理员仍可查看已卸载工具并恢复；内容审核策略页隐藏已卸载插件，只通过上传或市场重新安装恢复。业务侧不可用。

## 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| SDK client 版本未包含 moderation 方法/类型 | FastGPT 无法直接以类型安全方式调用 | Task 2 前核实发布版本；必要时先协调 SDK 版本升级，不复制一份并行契约 |
| tool 与 moderation 共享现有管理/市场模型 | 类型错配可能导致工具节点误调用审查插件，或市场 API 校验失败 | 类型显式区分；对 tool 的安装、解析、列表和调用增加回归覆盖 |
| “多视角”含义和失败策略未定义 | UI 或调用链可能擅自聚合、错误放行/阻断 | Task 1 评审确认；默认展示独立结果，不创造业务策略 |
| Marketplace 发布流程仍只接受 tool，且现有索引/下载统计以 tool ID 为主键 | UI 能力完成但 moderation 包无法发布，或跨类型 ID 产生数据冲突 | Task 6 同时核实按类型隔离的索引键、下载统计、包上传和发布端；如涉及旧 MongoDB 索引，按项目索引维护规范登记并测试；外部仓库改动单列确认 |
| secrets 或审查文本出现在日志/客户端状态 | 凭据和用户内容泄露 | 服务端测试调用、最小化响应、日志脱敏，并为安全边界增加测试 |

## 开放问题

1. **管理范围：** 首期只面向系统管理员管理的全局插件，还是同时支持团队安装与团队配置？本计划暂按系统管理员范围拆解。
2. **调用锚点：** 是否接受“先做显式工作流审核步骤”的建议？若优先应用级自动审核，需要确定适用应用/请求类型、顺序、关闭方式和失败策略。
3. **多视角定义：** 是对同一内容并行调用多个 moderation 插件，还是展示单个插件中的多个命中类别？本计划暂按多个独立插件调用规划。
4. **业务处理策略：** `suspected`、provider `error` 和调用失败分别由工作流/调用方处理，还是需要 FastGPT 统一提供策略配置？本计划不默认自动拦截或放行。
5. **Marketplace 发布：** moderation 插件的上架主体、发布仓库和首批市场内容是否确定？测试用 moderation 包不等同于可发布的正式市场插件。
