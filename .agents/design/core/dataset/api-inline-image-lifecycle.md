# 直接写入正文的图片转存与集合级生命周期设计

状态：已实现，本地回归与本机 dev 验证通过；全量真实模型用例受外部 AI Proxy 连接阻断。关联：[PR #8171](https://github.com/labring/FastGPT/pull/8171)、[Issue #6567](https://github.com/labring/FastGPT/issues/6567)。

## 1. 目标与范围

手动新增、编辑分块与 `pushData` 都会直接接收 `q/a`。其中的 Base64 图片可能作为正文进入长度检查、落库和训练，造成正文膨胀。
本方案只在这些直接写入入口提取、校验并转存图片，只替换图片地址，保留分块边界和周围 Markdown/HTML。

文件上传、解析、预览产生的图片已经由 `fileId` 派生目录管理，继续使用原链路，不改为 `chunkImagePrefixId`，也不重复转存。
`chunkImagePrefixId` 只为直接写入时新增的正文图片按需创建；普通文件导入不会初始化此字段。

本次采用的生命周期是：**图片引用保留在分块正文中，图片资产归集合；删除集合或知识库时统一回收。**
集合只增加一个稳定的 `chunkImagePrefixId`，不在 data 或 training 上增加图片关联列表。

| 操作                   | 新增的正文关联图片       | 现有独立图片数据的 `imageId`                  |
| ---------------------- | ------------------------ | --------------------------------------------- |
| 编辑正文，移除图片引用 | 保留对象                 | 沿用现有行为                                  |
| 删除单个分块           | 保留对象                 | 沿用现有单图删除行为，见第 8 节的命名空间边界 |
| 删除集合               | 删除所属图片目录         | 沿用现有图片集合清理                          |
| 重训、同步后重建集合   | 保留目录归属，不回收对象 | 沿用现有流程                                  |
| 删除知识库             | 按知识库前缀统一清理     | 沿用现有行为                                  |

本次处理手动新增、编辑和 `pushData` 直接提交的 `q/a`，包括失败训练任务单条编辑中的正文修改；不迁移历史文档图片。
纯索引编辑、无正文变更的训练重试、模型增强和文件解析不触发新增图片上传。
上述入口以外的训练、索引链路只保留必要的新图片目录归属校验，不新增关联字段同步，也不引入最后引用扫描、引用计数或历史记录回收。

## 2. 改动前已核对的现有实现

以下为已核对的入口和所属模块，完整实施落点见第 10 节：

| 手动新增     | `projects/app/src/pages/api/core/dataset/data/insertData.ts`：直接写入正文并生成索引，包含手工录入或标注写入                                            |

| 文档图片     | `packages/service/common/s3/sources/dataset/index.ts`：从源文件 `fileId` 推导解析图片目录                                                               |

| 集合删除     | `collection/controller.ts`：删除源文件及解析目录；图片集合另行查询分块的 `imageId`，不扫描正文                                                          |
| 分块删除     | `projects/app/src/service/core/dataset/data/data.ts`：清理单图 `imageId`，不处理正文图片                                                                |

因此不能简单把所有文档图片从 `fileId` 切到当前 `collectionId`：预览可能没有集合，重训和同步也会改变集合 ID。
本次只为新转存图片补充稳定的集合资源归属，原有文件解析、缓存和图片路径保持兼容。

## 3. 数据模型

### 3.1 集合：`chunkImagePrefixId`

新增一个集合级可选字符串字段 `chunkImagePrefixId`，作为该逻辑集合通过直接写入新增的正文图片的稳定目录标识。
名称中的 `chunkImage` 表示目录存放直接写入分块正文的图片；字段放在 collection 上，不放在单个 chunk 或 training 上。

```ts
// 集合业务字段示意；实际类型从 Zod schema 推导。
const collection = {
  _id,
  datasetId,
  fileId,
  chunkImagePrefixId // 手动写入或 pushData 新增正文图片的稳定目录标识
};
```

- 第一次通过手动写入或 `pushData` 转存新图片时，原子初始化为当时集合 `_id` 的字符串；并发请求获取同一个已落库值。
- 文件解析和图片上传集合的原有图片不使用此字段；尚未发生直接写入转存的集合不创建字段，旧集合无需批量回填。
- 字段初始化后保持不变，不允许由外部创建、更新接口传入。
- 重训、同步在重建集合时显式继承该字段；新集合 `_id` 可以变化，资源目录保持稳定。继承值从删除/重建的同一事务内读取最新集合，不使用较早的鉴权或远端抓取快照，避免漏掉此期间发生的首次图片上传。
- 独立新建或复制为另一个逻辑集合时不得继承此字段；如果未来提供图片复制能力，应复制对象并替换引用。
- 普通集合创建路径只允许服务端受控的重建分支继承字段，不能无条件传播任意 `...collection`。

这里额外保存目录标识的原因是：分块可以全部删除，当前集合 `_id` 也可能被重建，但图片仍需有可追踪的回收归属。
例如集合从 A 重训为 B 时，两者沿用同一个图片目录标识 A；删除 B 仍能找到原目录。即使 B 的分块已经全部删除，
集合上保存的目录标识也不会丢失。
不为本需求重构全部集合创建、预览流程，也不引入跨集合共享目录。

### 3.2 分块、任务与现有图片字段

不新增分块顶层 `relatedImgId`、`imageIds` 或类似关联列表。正文中的 S3 key 已经表达引用关系，且本方案不按引用数量回收，
持久化第二份列表既不参与清理决策，也会增加训练、QA 拆分和编辑时的同步负担。

- data/training 继续使用现有 `q/a` 和单图 `imageId`，schema 不增加关联字段。
- `imageDescMap` 仍只承担图片描述映射。
- 集合已有的 `metadata.relatedImgId` 是旧 Mongo 图片兼容字段，保留原含义和清理逻辑。
- 当前引用只在校验归属、判断本请求哪些上传被接收时临时提取，不写入 Mongo。

### 3.3 索引和迁移

集合新字段为可选，查询以既有集合 `_id` 和所属范围为入口，不新增图片反向查询索引。
保留 `fileId`、`imageId`、`metadata.relatedImgId` 及其既有索引，不登记新的废弃索引，也不需要启动迁移。
已核对集合与 TTL schema 的既有索引；新增字段不替换已有索引，没有新增废弃索引或迁移任务。

## 4. 存储目录与归属

新图片统一通过 `createOpaqueS3FileKey` 生成 key：

```text
dataset/{datasetId}/chunk-images/{chunkImagePrefixId}/file/{随机图片ID}.png
```

图片写入 private bucket。`datasetId` 和 `chunkImagePrefixId` 只能来自服务端已鉴权、已落库的集合。
删除时构造以下完整 prefix，保留结尾 `/`，避免相近标识之间的前缀误匹配：

```text
dataset/{datasetId}/chunk-images/{chunkImagePrefixId}/
```

历史文档继续使用原有目录：

```text
dataset/{datasetId}/file/{源文件随机ID}.pdf
dataset/{datasetId}/parsed/{源文件随机ID}/{图片随机ID}.png
```

两类目录按图片的产生入口区分，不能仅凭集合是否有 `fileId` 决定：文件集合手动追加、编辑或经 `pushData` 写入新图片时，
源文件解析图仍归 `fileId`，这次直接写入的新图片归 `chunkImagePrefixId`，二者可以同时存在。

同一个集合内允许多分块共享新图片；同一 `pushData` 请求内相同 data URL 只上传一次。
不同请求不新增内容哈希去重，不提供跨集合共享生命周期。

对新命名空间，写入时验证 key 中的 `datasetId/chunkImagePrefixId` 与目标集合一致。将其他集合的新图片 key 作为
正文、普通链接、显式 `imageId`、自定义索引或源文件 `fileId` 重新导入时应拒绝；不能仅验证属于同一个知识库。
如果未来支持跨集合引用，需要先提供复制资产或明确的共享所有权机制。
历史文档 key 沿用既有授权和清理规则，不在本次收紧全部旧路径。

## 5. 直接写入入口与转存流程

统一转换函数接入以下 API 边界，不在所有调用 `createDatasetData` 或训练处理器的路径上无条件转存：

| 入口                                         | 本次行为                                                                       |
| -------------------------------------------- | ------------------------------------------------------------------------------ |
| `data/insertData`                            | 手动新增或标注写入：转换输入 `q/a` 后执行原有查重、数据写入和索引生成          |
| `data/update`                                | 手动编辑：先合并最终 `q/a`，仅对新提交的内嵌图片转存，两条索引保存路径都接入   |
| `data/pushData`                              | 转换本批 `q/a`，保持用户分块，再按原模式落库或进入训练队列                     |
| `training/updateTrainingData`                | 仅单条任务实际修改 `q/a` 时转换；批量重试、未修改正文和 rebuild 重试不触发上传 |
| `collection/create/text`、文件上传/解析/预览 | 保持现有源文件 `fileId` 链路，不生成新目录标识，不重复上传已有解析图片         |
| 图片集合上传、独立图片 `imageId`             | 保持现有上传和单图数据语义，不改为正文图片目录                                 |

### 5.1 统一转存步骤

三个分块写入入口统一调用同一个 `normalizeDatasetDataImages` 业务封装，失败任务正文编辑也复用它，不各自实现扫描、替换或上传。
底层复用边界如下：

| 能力                                  | 复用方式                                                                                                          |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Markdown/HTML 图片扫描                | 直接复用 `matchDocumentImages`，不另写节点扫描正则                                                                |
| Markdown 地址反转义                   | 直接复用 `unescapeMarkdownImageUrl`                                                                               |
| Base64 data URL 识别、MIME 与负载提取 | 从现有 `parseMarkdownBase64Images` 的内嵌识别逻辑提取共享纯函数，由旧转换器和新封装共同调用，保持旧调用方识别行为 |
| 节点地址替换、保留周围文本            | 复用扫描结果的 `item.replace(nextKey)` 和偏移切片，不重建整篇 Markdown                                            |
| MIME/扩展名与文件内容校验             | 复用 `normalizeMimeType`、`resolveMimeExtension` 和 `validateUploadFile`/底层上传策略，不自建另一套文件类型检测   |
| 随机 key 与对象上传                   | 复用 `createOpaqueS3FileKey` 和 `uploadImage2S3Bucket('private', ...)`                                            |

共享识别与严格校验分开：新入口补充必要的 Base64 编码完整性校验；`Buffer.from(..., 'base64')` 本身不能视为严格合法性校验，
旧转换器也不能因本次抽取而隐式改变失败语义。实际内容校验完成后以 buffer 上传，避免重复解码。
新封装只编排集合 prefix、请求内去重、严格失败处理和临时上传清理；不直接套用会清理正文、吞掉上传失败的 `parseMarkdownBase64Images`。
临时记录必须在对象写入前登记，因此不使用现有上传函数“上传完成后才创建普通 TTL”的分支代替本方案登记顺序。

1. 复用各入口现有的 `parseApiInput`、集合或分块写权限、额度和显式 `imageId` 校验，不改变对外请求、返回结构。
2. 检查待处理文本是否包含内嵌图片；需要上传时取得集合稳定的 `chunkImagePrefixId`。
3. 复用 `matchDocumentImages` 和 Markdown 地址反转义，识别 `q/a` 中的 Base64 图片。
4. 校验 Base64、MIME、实际内容与现有上传策略；生成随机 key，并在写对象前登记临时清理记录。
5. 上传图片，只替换原图片节点的地址；同请求复用重复图片。不直接调用会清理正文、吞掉上传失败的旧转换器。
6. 对替换后的最终 `q/a` 校验新命名空间的集合归属，不新增分块关联字段。
7. 进入原有写入事务：`pushData` 基于替换后正文过滤、预落库和入队；手动新增、编辑按原入口写入数据和索引。
8. 同一实际保存或入队事务将本请求使用的新图片提升为集合资产，即移除其未被清理领取的临时记录。
9. 未被接收的分块、被过滤内容独占的图片和失败请求残留的上传，保留临时记录到期清理。

新增的图片上传和内容检测放在可重试事务之外，事务重试不得重复执行转存；不借本需求重构原有索引外部 IO。
QA 模式即使尚未创建 data，只要训练任务已接受相应引用，也要完成图片提升，不能等训练结束再取消临时清理。
临时提取实际保存或接收正文引用的本请求新 key，用于决定提升哪些上传；`pushData` 以过滤后的正文为准。
该集合仅存在于本次事务上下文，不写入 data/training。
不得因不再保存图片列表，就将本请求所有上传无条件转为永久对象。

上传出错使请求失败，不静默删除正文图片。事务返回提交结果不确定时不能仅凭异常立即删除本请求对象；
先按临时记录的实际状态处理，避免删除已经随成功事务提升的图片。
上传重试必须有明确的总截止时间，不能无限重试到临时清理窗口之外；实施时核对实际 S3 客户端超时与取消行为，
本实现为每次图片上传设置 120 秒截止时间，远短于 3 小时临时窗口。AWS/MinIO/R2 使用可取消的单次 PUT，COS 取消对应任务，OSS 使用独立连接池到期关闭连接。
保留 TTL 处理存储端已接收但客户端超时的情形，不把“超时抛错”等同于存储端必定没有写入。

### 5.2 手动新增和编辑的提交边界

- `insertData` 先沿用原有正文格式化，再转存 Base64，原有查重、索引生成和数据写入使用替换后的正文。
- `update` 按实际提交字段与当前分块合并最终 `q/a`；未提交字段和原有 S3/HTTP 图片引用保持原值，不因保存而重传。
- 完整索引保存和系统索引保存都要在各自 Mongo 事务内提升本请求上传，不能在 API 返回前单独清 TTL，避免数据回滚而图片已永久保留。
- 失败训练任务的正文编辑遵循相同的上传在事务外、任务修改和图片提升在同一事务内的约定。
- 更新后的正文用于返回预览，不能继续拿转存前的 `nextQ/nextA` 签名或响应；保留原有索引生成和计费语义。
- 单纯引用、移除或修改已有文件解析图不创建 `chunkImagePrefixId`，不更改其所属 `fileId` 或目录。

### 5.3 与删除集合并发

实际保存或入队的事务必须读取并真实更新当前集合文档，验证集合仍存在、所属范围和 `chunkImagePrefixId` 一致。
更新现有 `updateTime` 时要单调推进，确保与删除、重建集合竞争同一文档写锁，不能只做事务外 `exists` 检查。

- 写入先提交：删除集合读取到稳定目录，随后清理所有图片。
- 删除或重建先提交：旧集合上的保存或入队失败，临时图片不提升，最终由临时清理兜底。
- 删除目录后才完成的在途失败上传：仍保留逐对象临时记录，不能仅依赖已经执行过的目录删除。
- 有事务写冲突时沿用 `mongoSessionRun` 重试；外部上传结果保留复用。

## 6. 训练、编辑与归属校验

| 写入位置                       | 处理约定                                                                                     |
| ------------------------------ | -------------------------------------------------------------------------------------------- |
| 预创建 data、创建 training     | 保持现有数据结构；在实际接收的事务中提升本请求使用的新图片，拒绝其他集合的新 key             |
| QA 生成多个子分块              | 沿用现有正文生成、落库；无需拆分或透传图片列表。父任务已接收的图片保留到集合删除             |
| auto/image/imageParse 阶段切换 | 正文变化时校验新 key 归属；正文不变时无需新增图片状态维护                                    |
| 最终索引写回                   | 校验新 key 归属；不重新提取上传文件解析图或正文里已有的图片                                  |
| 两种 data 编辑                 | API 边界对手动提交的新 Base64 转存，最终保存事务内提升图片并校验归属，保留原有索引和全文语义 |
| 失败训练任务编辑               | 仅正文修改接入转存；在事务内读取当前任务、合并部分字段后保存，不能忽略未提交的 `a`           |
| 自定义索引编辑                 | 只校验新 key 归属，不存图片列表，不做引用增减和回收                                          |
| 删除部分或全部分块             | 不删除新目录图片，不删除集合的 `chunkImagePrefixId`                                          |

新 key 引用提取与归属检查作为可复用纯函数组织；检查对象是受支持语法中的引用，不是持久化资产清单。
语法需要覆盖 Markdown 图片、普通链接、HTML img 和 Markdown 地址转义，复用预览已有的提取语义，
保持原有签名、替换、来源过滤行为不变。

历史数据无需关联字段回填。编辑移除引用或 QA 不再输出图片时，对象继续留在集合目录，因此历史记录和已删除分块
无需参与回收判定。Pro 的增强阶段与同步调用方仍需核对归属校验、稳定目录继承和实际删除行为，但不新增列表透传。

## 7. 清理的事务与失败边界

只增加图片上传是不够的：上传完成前进程可能退出，集合删除后也可能暂时无法向 Redis 入队。
本方案复用现有 `s3_ttls`、到期 cron 和 S3 删除 worker，保存四类短期清理记录，不保存永久逐图归属，也不扫描正文引用。

### 7.1 最小扩展

在现有 S3 TTL 类型和 schema 中新增可选字段，普通对象和 Multipart 的既有含义保持兼容：

```ts
type S3LifecycleCleanupFields = {
  cleanupType?:
    | 'collectionImageUpload'
    | 'collectionImagePrefix'
    | 'datasetPrefix'
    | 'datasetFile';
  cleanupClaimed?: boolean; // 仅用于临时图片上传的清理领取
};
```

| 类型                    | `minioKey` 的含义           | 创建、移除时机                                           |
| ----------------------- | --------------------------- | -------------------------------------------------------- |
| 字段缺失                | 原有对象 key                | 保持当前逻辑                                             |
| `collectionImageUpload` | 本次上传的完整图片 key      | 上传前登记；保存或入队成功事务移除，或物理删除成功后移除 |
| `collectionImagePrefix` | 已验证的集合图片目录 prefix | 删除集合或清空库事务内登记；物理清理成功后移除 |
| `datasetPrefix` | 已删除知识库的完整 `dataset/{id}/` | 实际删除库的事务内登记；覆盖新旧对象，物理清理成功后移除 |
| `datasetFile` | 清空但保留知识库时的旧源文件 key | 清空事务内登记；源文件和其解析目录都删除成功后移除 |

新分支不允许与 Multipart 同时出现。继续使用既有到期、bucket/key 索引，不增加每张图片到正文的索引。
创建、领取、提升这些记录的方法放在 entity；S3 读写和流程协调放在 service，不增加通用任务平台或事务回调框架。
通用 `removeS3TTL` 只处理原有类型，新类型必须走专用提升、完成操作，避免旧的单图落库路径绕过领取状态直接删记录。

### 7.2 临时上传到期

临时上传使用现有三小时窗口，但成功提升和到期领取必须竞争同一条记录：

- 到期任务通过原子更新确认记录仍存在、确已到期，再设置 `cleanupClaimed: true`；领取成功才能入对象删除队列。
- 实际保存或入队事务只允许移除 `cleanupClaimed !== true` 且尚未到期的本请求临时记录，匹配数量不足则回滚业务写入。
- 已领取的对象不再提升；请求失败后重新上传使用新 key。不能在 cron 已取得删除权后重新取消清理。
- cron 读取的旧快照不能直接作为删除依据。已提升而消失的记录领取失败，不会被旧快照误删。
- 这四种新清理记录在队列接受后仍保留，worker 确认物理删除成功才删除记录；队列、存储失败都可重试。
- bucket 不可用时保留新记录，不能进入旧逻辑中删除普通孤立 TTL 记录的分支。

上述领取只处理未接收上传的短期清理；图片成功保存或入队后不再有逐对象清理记录，不存在续期和周期性引用查询。

### 7.3 集合目录删除

集合删除事务在删除集合文档前，根据其可信 `datasetId/chunkImagePrefixId` 写入到期的 prefix 清理记录。
事务回滚时清理记录一起回滚；事务提交后才允许向 Redis 派发任务。

- `delCollection` 将新记录 ID 随内部删除结果返回；持有最外层事务的调用方在 `mongoSessionRun` 成功返回后尝试派发。
- 派发失败不丢失 Mongo 记录，现有到期 cron 再次派发；提交后进程退出同样由 cron 兜底。
- 不扩展 `mongoSessionRun` 为通用 after-commit 框架，不在可重试回调中直接删除新目录。
- worker 对新命名空间按 key 删除时要求存在已领取的临时记录；按集合 prefix 删除时要求存在对应删除意图。
- worker 物理删除成功再移除匹配的记录。重复派发和重复执行幂等；旧的无关对象、文件解析目录仍沿用原逻辑。

清理记录只允许服务端从授权范围构造。worker 不接收客户端提供的任意 prefix。
既有 cron 当前按小时触发，因此正常提交后立即尝试入队，异常恢复可能延迟到下一轮 cron；本方案不保证同步物理删除。

## 8. 各删除入口的明确变化

### 8.1 单个分块删除

不从分块正文提取 key 并删除关联对象，也没有额外列表需要维护；集合目录仍然存在，最后一个分块被删也不会丢失回收依据。

现有独立图片数据的普通 `imageId` 保持原有删除行为。但新命名空间图片即使出现在所属集合的 `imageId` 中，
也服从集合生命周期，不能被原有单图删除分支立即物理删除。该分支需要识别新 key 并跳过对象删除。
不能把普通正文关联图片一概塞入旧 `imageId` 后复用单图删除。

### 8.2 集合删除

正常删除（`delImg: true`）登记该集合的 prefix 清理意图，无论集合是否有 `fileId`、是否还存在 data、训练是否完成。
不汇总剩余分块正文作为完整资产清单，也不要求集合为 `type = images`。

旧源文件、文件解析图片、旧 Mongo 关联图片、图片集合单图的清理路径继续兼容；对新命名空间统一通过目录意图处理，
避免再由逐 key 分支提前清理。重训、同步的保留资源路径不得登记 prefix 删除意图。

### 8.3 知识库删除与清空

`delDatasetRelevantData` 根据知识库是否继续存在，保存不同的清理范围：

- **实际删除库**：与集合、知识库文档删除同事务保存 `datasetPrefix`，范围严格为 `dataset/{datasetId}/`。
  新正文图片、旧源文件、解析图和已无集合记录的库内对象都被覆盖，无需扫描分块。
- **清空但保留库**：与旧集合删除同事务保存其 `collectionImagePrefix` 和 `datasetFile`。
  worker 删除旧源文件后继续清理其解析目录；不登记整个库目录，避免延迟重试误删后续新导入的文件。

最外层事务提交后用记录 ID 派发；Redis 不可用、提交后进程退出或存储删除失败时，记录继续存在，
由现有 cron 补投。实际物理删除成功后才移除记录，不能把“队列已接受”视为“文件已删除”。
未接收上传的临时 TTL 独立保留，以回收目录删除之后才完成的在途上传。

通用源文件接收/取消临时清理仅操作旧类型 TTL，不能按同 key 删除新的 `datasetFile` 清理意图。
本改动不重构向量、全文等跨系统删除一致性。

### 8.4 团队、账号和免费账号清理入口

| 入口 | 汇入路径 |
| --- | --- |
| 单个/批量知识库或文件夹删除 | `deleteDataset → Dataset 删除队列`，worker 遍历子库 |
| 团队删除、账号所属团队资源清理 | `Team 删除队列 → deleteTeamAllDatasets → Dataset 删除队列` |
| 自助账号注销、管理员删除账号 | 账号 finalizer 为 owner 团队提交正常 Team 删除任务，再走上述路径 |
| 免费账号资源清理 | 满足既有清理条件后调用 `deleteTeamAllDatasets` |
| 网站库配置更新触发清空 | 直接调用 `delDatasetRelevantData`，保留库并限制在旧资源范围 |

这些入口共享最终的持久化清理登记和 S3 队列。即使账号、团队元数据先被删除，Dataset/S3 worker
仍可凭任务中的范围完成清理，不依赖再次查询用户或团队。
非 owner 成员注销沿用资源移交给团队 owner 的规则，不删除共享团队的知识库。

**完成口径**：目前账号 finalizer 的 residual 检查只确认 Mongo 业务资源和会话残留，不等待 S3 物理删除。
`Dataset delete completed` 表示数据库删除流程完成；免费账号日志改为 `cleanup scheduled`。
S3 待清理范围可通过未完成的清理记录追踪，但尚未接入账号注销的统一物理完成统计。

## 9. 重训、同步与兼容

1. `reTrainingCollection`、`syncCollection` 保存旧集合的 `chunkImagePrefixId`，在新集合创建事务中显式继承。
2. 上述流程使用保留资源语义，不登记新目录清理。事务失败时旧集合和字段一起恢复。
3. Pro 外部数据源同步的实际删除分支要登记清理，保留资源的重建分支要继承标识；两者不能共用一个无条件删除行为。
4. 有 `fileId` 的集合也可以因手动新增、编辑或 `pushData` 拥有新目录：源文件解析图按旧路径管理，直接写入新转存图按新目录管理。
5. 文档解析预览继续使用源文件派生目录，不要求提前创建 collection，也不搬运现有 rawText 缓存中的图片引用。
6. 新字段缺失时沿用原行为；存量 S3 key 和旧 Mongo 图不靠猜测归属批量迁移。
7. 若已经部署过 PR 的 `inline-images` 永久归属记录，不能直接移除其清理分支；需先另行设计存量承接。
   本方案默认替换尚未发布的 PR 实现，不把 GitHub PR 处于 open 状态当作“生产必定无数据”的证据。
