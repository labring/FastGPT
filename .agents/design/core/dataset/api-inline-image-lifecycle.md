# 直接写入正文的图片转存与集合级生命周期设计

状态：已按精简方案实现，并通过本轮局部回归和本机 dev 验证。关联 PR #8229 / Pro #1242。

## 1. 本次收敛的结论

业务层只增加集合的 `chunkImagePrefixId`，负责图片归属、重建继承和删除范围。
S3 TTL 只管理临时对象；S3 删除队列只执行 `bucketName + key/keys/prefix`。
移除 `cleanupType`、`cleanupClaimed`，S3 TTL schema 和类型恢复为 main 原样。
移除 S3 worker 对知识库 key、集合目录、业务清理记录的识别。
不把目录删除任务存入 `s3_ttls`，不新增逐图归属表、Mongo 清理任务表或另一套补投框架。

用户确认的到期处理顺序：**先提交删除任务，确认队列接收成功，再移除 TTL；提交失败保留 TTL。**
这里的成功是 Redis 接受任务，实际对象删除沿用现有 worker 和队列重试。

沿用现有 TTL 的并发语义，不为保存与到期回收的边界竞争增加领取状态、锁或专用状态机。

## 2. 约束与职责

| 层                 | 负责                                                              | 不进入这一层的内容                                   |
| ------------------ | ----------------------------------------------------------------- | ---------------------------------------------------- |
| Dataset 业务层     | 扫描和转存 Base64、目录归属、接受哪些图片、重训继承、确定删除范围 | 通用存储重试策略                                     |
| S3 TTL             | 临时对象 key、过期时间、取消临时回收                              | collection/dataset 类型、目录清理意图、永久图片归属  |
| S3 删除队列/worker | 执行 key/keys/prefix 删除，沿用现有幂等和失败重试                 | 判断图片属于哪个集合、查询知识库表、完成业务清理记录 |

通用 TTL 调度和删除 worker 不导入 `core/dataset`，不通过 `dataset/.../chunk-images/...` 正则选择清理行为。
目录构造与新 key 归属判断集中到 `core/dataset/data/inlineImages` 或集合业务模块。
已有的文件 source 适配器、通用 key 编码和存储 SDK 继续复用。

## 3. 保留的业务设计

### 3.1 集合只有一个稳定目录字段

```text
dataset/{datasetId}/chunk-images/{chunkImagePrefixId}/file/{随机图片ID}.png
```

- 第一次通过直接写入转存 Base64 时，原子初始化 `chunkImagePrefixId`，并发首传使用同一值。
- 普通文件上传、解析和预览继续使用原 `fileId` 派生目录，不创建新字段、不重复上传。
- 文件集合手动增加正文图片时，两种目录可以共存。
- 重训、同步在删除/重建的同一事务内读取最新目录标识并继承；不使用早先的鉴权快照。
- 编辑移除引用、删除一个或全部分块都保留目录；删除集合才回收。
- data/training 不新增 `relatedImgId`、`imageIds` 等列表；独立图片的 `imageId` 和旧 `metadata.relatedImgId` 保持兼容。
- 新命名空间的跨集合引用由业务层拒绝，客户端不能指定 `chunkImagePrefixId`。

### 3.2 写入入口

| 入口                                 | 处理                                                              |
| ------------------------------------ | ----------------------------------------------------------------- |
| `data/insertData`                    | 转换本次 q/a，再进入原有保存和索引流程                            |
| `data/update`                        | 合并最终 q/a，转换新 Base64；完整索引和系统索引两条保存路径都接入 |
| `data/pushData`                      | 保留用户分块；按实际过滤后的正文确认哪些新上传被接收              |
| `training/updateTrainingData`        | 只有单条任务修改正文时转换；纯重试和批量重试不转换                |
| 文件上传/解析/预览、文本文件创建集合 | 保留原 fileId 链路                                                |

扫描复用 `matchDocumentImages`；Base64 data URL 识别提取共享纯函数；复用地址反转义、节点替换、MIME/内容校验和上传。
只替换图片地址，保持正文、空白、标题、metadata 和分块边界。无效内容或上传失败使请求失败，不静默移除图片。

## 4. 上传和实际写入

1. 业务层鉴权、校验 Base64 内容，并取得稳定目录。
2. 为每个新 key 创建普通 S3 TTL，只写 `bucketName/minioKey/expiredTime`，不写业务类型。
3. 上传对象；同请求去重。上传置于 Mongo 可重试事务之外，保留 120 秒实际取消传输的截止时间。
4. 进入原有保存/入队事务，按正常业务规则校验集合存在及新 key 归属。
5. 根据实际保存或接收的正文选择本请求的新 key，复用原有 TTL 移除能力并传入同一 session。
6. 本请求应取消的 TTL 数量不匹配时，回滚本次业务写入；已经永久化的旧引用不要求存在 TTL。
7. 数据与 TTL 取消一起提交。QA 入队已经接受图片，不等最终训练完成。

失败、被过滤内容独占的图片保留普通 TTL，到期后提交删除队列。
事务提交结果不确定时，不凭 API 异常立即删除对象；以数据库的最终提交状态为准。
临时 key 列表只存在于请求上下文，不写入分块或训练任务。

## 5. TTL 到期：入队确认后移除

### 5.1 普通对象的流程

```text
扫描到期 TTL
    ↓
提交现有 S3 删除任务 { bucketName, key }
    ├─ 失败：保留 TTL，下一轮重新提交
    └─ 队列确认接收：按 _id 移除 TTL
                         ↓
                  worker 执行，失败走现有重试
```

不新增领取步骤。入队失败或 bucket 暂不可用时保留 TTL。队列已接受但移除 TTL 失败时，后续重复提交沿用已有幂等 jobId。
Multipart 继续使用既有 abort 分支，不混入知识库判断。

S3 worker 不再查询 TTL，也不承担移除 TTL 的回调。删除失败由现有 BullMQ 策略处理：
默认 10 次指数退避尝试，失败任务最多保留 10,000 条；这不是无限期重试或 Redis 数据丢失后的恢复保证。

### 5.2 本次采用的边界

临时 TTL 为 3 小时，单次图片上传截止时间为 120 秒，正常请求中的保存远短于临时窗口。
本次按现有 TTL 机制处理，不额外实现保存与到期回收的原子互斥，也不针对该边界引入新字段或锁。
时间差使正常请求与到期回收相遇的机会较低，但不构成严格的并发安全保证；本方案不宣称消除旧快照等边界竞争。

## 6. 集合、知识库删除

### 6.1 删除范围由业务层确定

| 操作               | 交给 S3 的内容                                                           |
| ------------------ | ------------------------------------------------------------------------ |
| 删除部分或全部分块 | 不提交正文图片删除任务；普通独立 imageId 沿用原行为                      |
| 删除集合           | 集合稳定图片目录 prefix；源文件、解析图和独立图片沿用原清理范围          |
| 重训、同步保留资源 | 不提交图片目录删除，继承稳定目录                                         |
| 实际删除知识库     | 完整 `dataset/{datasetId}/`，覆盖新旧对象和无集合记录的库内资源          |
| 清空但保留知识库   | 旧集合图片目录、旧源文件 key；源文件删除沿用解析目录清理。禁止总目录删除 |

业务层构造可信完整 prefix，包含结尾 `/`。S3 worker 只执行任务，不解析其业务含义。
独立图片删除路径对新正文图片目录的跳过也放在 Dataset 业务层，不能再由通用 worker 兜底。

### 6.2 事务和派发边界

集合删除、保留库清空时，从事务内真实集合取得旧资源范围，经内部返回值带给最外层调用方。
事务成功提交后调用现有 S3 队列；事务回滚时不派发。新资源范围不写入 TTL。
重训/同步实际删除分支同样处理，保留资源分支只继承目录。
入队失败不得只记录日志后声称清理完成，应向调用方暴露失败；已有父队列可据此重试。

已有 Dataset 删除 worker 可以复用原 `deleteTime`：最终移除知识库文档前先确认总目录任务已成功提交，
使入队失败时库 ID 和既有删除任务上下文仍可重试；不新增业务 schema。

**保留的可靠性边界**：集合/保留库清空的数据库事务与 Redis 入队不是原子操作。
移除上一版的 Mongo 清理意图后，不再保证“数据库已提交、进程在入队前退出”一定自动补投。
接口返回入队失败也不等于数据库已经回滚；已有父任务重试若要重用旧资源范围，必须保留其快照，不能靠已删除集合重新推导。
如果未来需要覆盖这段窗口，应单独设计业务删除任务或通用可靠队列，不在 S3 TTL 中补业务状态。
本次不新增这种机制，也不使用事务内提前入队或延迟一秒来冒充提交后保证。

### 6.3 所有清理入口

| 入口                              | 路径                                               |
| --------------------------------- | -------------------------------------------------- |
| 单个/批量知识库、文件夹及子库删除 | Dataset 删除队列 → 业务层构造库 prefix → S3 队列   |
| 团队删除、账号所属团队清理        | Team 删除 → deleteTeamAllDatasets → 同上           |
| 自助注销、管理员删号              | owner 团队删除 → 同上；非 owner 资源仍按原规则移交 |
| 免费账号清理                      | 满足既有条件后 deleteTeamAllDatasets → 同上        |
| 网站库配置变更清空                | 旧集合范围 → S3 队列，保留后续新导入               |

“已安排清理”和“S3 已物理删除”仍分开表述，账号注销完成不等待 S3 物理删除。
