## 1. 本轮结论

本轮只设计**系统管理员添加和管理系统模型**，不考虑团队成员安装模型。

已确认：

1. Plugin 中的 model 不再自动成为已安装模型，只作为创建模板。
2. 新部署的管理员模型列表默认为空。
3. 管理员可以“从模板新建”或“从空白新建”模型。
4. 从模板新建支持多选，下一步统一配置渠道，不逐个编辑模型参数。
5. 从空白新建先选择模型类型，再打开模型配置弹窗。
6. 模型配置列表增加“模型渠道”列，系统管理员页面删除“可用范围”列。
7. 渠道选择只在点击确认后生效，取消或关闭弹窗不产生变更。
8. 模型配置弹窗增加“是否启用”。
9. **零渠道模型允许保存。**
10. **本轮保留 `requestUrl` 和 `requestAuth` 字段及其配置入口。**
11. **Plugin 模型模板每次使用时实时拉取，不做服务端缓存、全局缓存或客户端持久化缓存。**
12. Plugin 模板不要求稳定 `templateId/templateVersion`，安装完成后也不维持模板与模型实例的持续关联。
13. **MongoDB 内的批量模型创建采用事务级全成全败；渠道与 MongoDB 之间不做分布式事务或失败补偿。**
14. **新建模型默认不启用，即 `isActive` 默认值为 `false`。**
15. **system scope 不允许出现相同 `model` 的模型，即使 `type` 不同也不允许；模板候选需要过滤已安装项，服务端和数据库仍需兜底。**
16. **渠道与 `requestUrl/requestAuth` 共存时保持当前代码中的调用优先级，本轮不修改运行时路由规则。**
17. **是否启用与是否存在有效调用方式相互独立；无渠道、无有效请求地址的模型也允许保存并启用。**
18. **模型创建完成后即与模板解绑，已安装模型不再返回或派生 `isCustom`；所有模型采用相同的编辑和删除规则。**
19. **提交时后端重新拉取模板；任一所选 `{ type, model }` 已不存在则整批报错，模板参数变化不报错并使用提交时的最新参数创建。**
20. **当前模型列表直接按 MongoDB `_id` 倒序读取，新建模型排在最前；运行时不再按 `modelId` 二次排序，后续可增加独立 `order` 字段接管顺序。**
21. **旧 `system_models` 始终按 `model` 合并到 `ai_models`：同名时保留新表 `_id` 并由旧表配置覆盖，旧表独有模型新增，新表独有模型保留。**
22. **管理员“模型提供商”删除“可用模型”Tab，默认进入“模型配置”；旧 `modelTab=model` 链接回退到模型配置。**

## 4. 核心概念

### 4.1 模型模板

模型模板是 Plugin 某次实时请求返回的一条 model 数据，只用于填充创建参数。

模板不是：

- 已安装模型；
- 可用模型；
- 默认模型；
- 工作流可引用对象；
- 数据库中的长期实体。

本轮不为模板设计稳定业务身份，不保存 `templateId` 或 `templateVersion`。

### 4.2 模型实例

管理员确认创建后，FastGPT 才生成系统模型实例：

```ts
type SystemModelDocument = {
  modelId: string;
  scope: 'system';
  type: ModelTypeEnum;
  provider: string;
  model: string;
  name: string;
  isActive: boolean;
  requestUrl?: string;
  requestAuth?: string;
  pricing?: ModelPricing;
  config: ModelConfig;
};
```

约束：

- `modelId` 是模型实例的唯一业务身份。
- `modelId` 只存在于已持久化模型和更新/读取流程中，由 MongoDB 创建模型后生成。
- 新建弹窗状态、新建表单类型、新建请求 DTO 和创建服务入参中都不得定义或携带 `modelId`，包括可选字段和 `undefined` 占位。
- system scope 内 `model` 唯一，不同 `type` 也不允许复用同一标识。
- 模板选择键只在一次创建流程内有效，不能代替 `modelId`。
- 模板创建完成后，实例与模板解绑。
- Plugin 后续返回内容变化，不自动修改已安装模型。
- 模型实例继续存储在 `ai_models`，本轮只有 system scope。

### 4.3 模型渠道

模型与渠道是多对多关系：

- 一个模型可以关联多个渠道。
- 一个渠道可以支持多个模型。
- 模型页面和渠道页面必须看到同一份关联结果。
- 本轮沿用 AIProxy 当前的 `channel.models: string[]`，使用模型的 `model` 字段建立关联。
- 因为渠道先于 MongoDB 模型创建，绑定阶段还没有已持久化的模型实例可供查询。

AIProxy 的渠道数据是本轮模型—渠道关系的事实源，FastGPT 的 `ai_models` 不再保存一份 `channelIds`。模型列表中的渠道数量通过 AIProxy 渠道数据反向计算。

## 5. Plugin 模板实时拉取

### 5.1 拉取时机

每次管理员点击“从模板新建”时：

1. 前端请求管理员模板接口。
2. FastGPT 实时调用 Plugin 的模型列表接口。
3. FastGPT 对 Plugin 响应执行 Schema 校验和规范化。
4. 接口直接返回本次模板列表。
5. 弹窗关闭后丢弃本次模板数据。

不执行：

- 服务启动时预拉取模板；
- 定时刷新模板；
- 写入 MongoDB；
- 写入进程全局变量；
- 写入 Redis；
- 写入浏览器 localStorage；
- 使用模板 version 做客户端复用。

弹窗打开期间可以在 React state 中保留本次响应，这属于单次交互状态，不是模板缓存。

### 5.2 提交时校验

由于模板没有稳定 ID，管理员打开弹窗后，Plugin 列表可能发生变化。提交安装时不能直接信任客户端上传的完整模板对象。

推荐流程：

1. 客户端提交本次选择的临时键，例如 `{ type, model }`。
2. 服务端再次实时拉取 Plugin 模板。
3. 服务端按临时键匹配当前模板并重新校验。
4. 任意一个临时键在当前模板列表中不存在时，整批安装失败，不创建任何模型或渠道绑定。
5. 模板参数与管理员最初看到的内容不同时不报错，也不要求重新选择。
6. 创建数据以提交时服务端重新拉取的最新模板内容为准。

`{ type, model }` 只是一次请求中的匹配键，不落库、不承诺跨时间稳定。

### 5.3 Plugin 不可用

- Plugin 的 Provider 元数据加载是 FastGPT 正常启动的硬依赖；Plugin 在启动阶段不可用时，
  FastGPT 不进入可用状态，由启动失败和运维告警暴露问题，不提供本地 Provider 回退。
- 打开模板弹窗失败时，展示可重试错误。
- 不回退到旧模板缓存，因为本轮明确不缓存。
- FastGPT 已正常启动后，单次模型模板列表请求失败只影响模板创建入口；已安装模型目录的
  重新加载和运行不依赖本次模板列表响应。
- Plugin 不可用不能清空、禁用或修改已安装模型。

## 6. 管理员模型列表

### 6.1 空状态

全新数据库中没有已安装模型时：

- 页面正常打开，不把空列表视为系统异常。
- 显示清晰的空状态和“添加模型”按钮。
- 添加按钮包含“从模板新建”“从空白新建”。
- 默认模型配置允许为空，不能因无模型阻止系统启动。

### 6.2 表格字段

按 Figma 最终批注：

- 删除“可用范围”。
- 增加“模型渠道”。
- 渠道列显示当前关联数量。
- 点击数量打开渠道关联浮窗。
- 保留既有模型名称、Provider、类型、价格、启用状态、测试和操作列。

Provider 筛选只展示当前已安装模型列表实际出现的 Provider；模板弹窗则使用本次 Plugin 响应中的完整 Provider 集合。

### 6.3 渠道关联浮窗

- 管理员模型列表接口返回本次页面使用的完整渠道快照与各模型绑定；列表内打开关联浮窗时直接使用该快照，不再二次请求渠道接口。
- 编辑弹窗内的关联入口使用模型详情接口返回的最新完整渠道信息，同样不再二次请求渠道接口。
- 勾选变化先保存在浮窗本地状态。
- 点击取消、点击关闭或离开页面不提交变化。
- 点击确认后一次替换完整渠道集合。
- 成功后关闭浮窗并刷新渠道数量。
- 失败时保留浮窗和本地选择，展示错误，允许重试。

### 6.4 现有“新建覆盖默认模型”缺陷

当前管理员从空白新建模型时存在一个与 Provider 无关的缺陷：只要该模型类型已有默认模型，新建操作就可能误更新默认模型。

现有调用链：

1. `ModelConfigTable.tsx` 的 `onCreateModel` 读取 `defaultModels[type]`，用于复用默认模型参数。
2. 创建草稿通过 `...defaultModel` 展开整个运行时模型对象，因此同时继承了默认模型的 `modelId`。
3. 表单虽然清空了 `model` 和 `name`，但没有清除 `modelId`。
4. `AddModelBox.tsx` 提交时通过 `modelId ? putSystemModel(...) : postSystemModel(...)` 判断编辑或创建。
5. 因为创建草稿错误携带旧 `modelId`，前端调用更新接口，把原默认模型文档更新成新模型。
6. 默认模型配置继续引用同一个稳定 ID，因此新模型取代原模型的默认位置，原模型从列表中消失。

例如默认 LLM 是 `deepseek-v4-flash`，新建 LLM `test` 时，实际执行的是更新 `deepseek-v4-flash` 对应 `_id`，而不是插入新文档。相同 DeepSeek Provider 不是触发条件，只是让现象更容易被理解为 Provider 覆盖。

目标约束：

- 创建和编辑使用两个独立控制器、两个独立提交函数和两个独立接口，不能通过表单数据里是否存在 `modelId` 选择分支。
- 创建控制器的状态类型中不得出现 `modelId`；不是提交前删除，也不是设置为 `undefined`，而是类型和运行时对象都不存在该属性。
- 创建草稿可以复制默认模型的能力参数，但必须使用字段白名单生成，不得展开整个默认模型对象，也不得复制 `modelId`、avatar、运行时标记等实例身份字段。
- 创建数据优先使用明确字段白名单生成，避免整个运行时模型对象被展开进表单。
- 创建控制器只能调用创建接口；更新控制器必须从表单数据之外显式接收目标 `modelId`，并且只能调用更新接口。
- 创建接口不得接受 `modelId`；请求出现该字段时应校验失败，不能静默剔除后继续处理。
- 更新接口不得执行 upsert，也不能在找不到目标 `modelId` 时退化成创建。
- 新建成功后数据库模型数量增加，原默认模型文档和默认模型 ID 不得变化。

## 7. 从模板新建

### 7.1 第一步：选择模板

- 实时拉取 Plugin 模型模板。
- 支持按模型类型和 Provider 筛选。
- 支持多选。
- 根据当前已安装模型过滤掉相同 `model` 的模板，不进入可选列表。
- 前端过滤只改善交互，提交时服务端必须重新校验，数据库必须有唯一索引兜底并发创建。
- 未选择模板时“下一步”不可用。

### 7.2 第二步：统一配置渠道

- 展示上一步选择的模型摘要。
- 显示当前可选渠道。
- 一次选择的渠道统一应用到全部待创建模型。
- 不在此步骤逐个编辑模型名称、参数、价格或请求配置。
- 允许不选择任何渠道并提交。
- 点击“上一步”保留模板选择。
- 点击取消不创建模型，也不写入渠道关联。

### 7.3 确认创建

提交内容：

```ts
type InstallModelsFromTemplatesBody = {
  templateKeys: Array<{
    type: ModelTypeEnum;
    model: string;
  }>;
  channelIds: Array<string | number>;
};
```

服务端：

1. 再次实时拉取并校验模板。
2. 校验管理员权限、模型冲突和渠道合法性。
3. 为每个模板创建独立模型实例和 `modelId`，`isActive` 统一默认为 `false`。
4. 建立所选渠道关联；空数组表示零渠道。
5. 全部成功后刷新模型列表并展示成功提示。

从模板创建后不提供“恢复模板默认值”，因为实例不与动态模板保持长期关联。

### 7.4 渠道优先、MongoDB 后写入

本轮不实现 MongoDB 与 AIProxy 之间的分布式事务。提交顺序固定为：

1. 在任何写入前完成模板存在性、模型重复、参数和渠道合法性校验。
2. 读取所选渠道的最新 `models`，把本批模型的 `model` 合并进去并去重。
3. 逐个调用当前 AIProxy 渠道更新接口，先完成全部渠道绑定。
4. 只有所有渠道更新请求都成功，才开始写入 MongoDB。
5. 在单个 MongoDB 事务中批量创建全部模型，统一使用 `isActive: false`。
6. MongoDB 事务成功后返回创建成功并刷新模型列表。

一致性边界：

- MongoDB 内部仍然全成全败；任一模型重复或写入失败时，整批模型都不创建。
- 多个渠道通过现有单渠道接口逐个更新，因此渠道之间也可能部分成功。
- 渠道更新部分失败时不创建 MongoDB 模型，也不回滚此前已更新成功的渠道。
- 渠道全部成功但 MongoDB 事务失败时，不回滚渠道中的模型名。
- 上述失败可能暂时留下“渠道已声明支持某个模型，但 FastGPT 尚未安装该模型”的数据，本轮明确接受这种不一致。
- 管理员重新提交相同模型时，渠道模型数组必须去重，避免失败重试产生重复项。
- 零渠道创建直接跳过渠道步骤，进入 MongoDB 批量创建事务。
- 当前锁定的 AI Proxy v0.6.5 不提供模型绑定的差量更新接口，FastGPT 必须通过完整渠道
  `PUT` 更新 `models`，并原样透传该接口支持的其他可变字段。
- 渠道管理页的普通编辑和优先级修改同样属于完整 `PUT`，必须复用同一组完整字段；不能只
  提交页面可编辑字段，否则会把 AI Proxy 中的高级配置覆盖为零值。
- v0.6.5 的渠道更新请求结构未暴露 `balance_threshold`，但其数据库更新又会写该字段，
  因而任意完整 `PUT` 都可能把既有阈值重置为零。FastGPT 无法通过现有 API 原样透传，
  这是上游接口限制；在 AI Proxy 修复或提供差量接口前，受影响渠道存在非零阈值时拒绝
  修改模型绑定，避免无提示的数据破坏。
- AI Proxy 完整渠道更新没有版本号、ETag 或 CAS；服务端并发覆盖属于已接受的跨系统风险。
  管理页面必须在一次关联写入完成前禁用同页重复提交，避免由单页面主动制造并发请求；
  多标签页、多节点和外部调用的并发不在本轮解决。
- 模型创建失败后不自动删除或回滚渠道。失败时无法安全证明渠道仅由本次请求创建，也无法
  排除并发成功请求已使用该渠道；盲目补偿可能删除合法配置或绑定。
- MongoDB 写入成功后，运行时模型缓存刷新仍可能失败并使接口返回错误；此时数据库事实
  已经变更，不能回滚。用户重试和短暂缓存不一致属于本轮接受风险，后续若需要更强一致性，
  应通过可观测版本、重试或异步刷新机制单独设计，而不是把缓存刷新伪装成数据库事务。

## 8. 从空白新建

### 8.1 选择模型类型

点击“从空白新建”后先选择模型类型，例如：

- LLM
- Embedding
- Rerank
- TTS
- STT

选择后打开该类型对应的模型配置弹窗。

### 8.2 配置弹窗

弹窗根据模型类型展示对应字段，至少包含：

- 模型名称与显示名称；
- Provider；
- 类型专属能力参数；
- `requestUrl`；
- `requestAuth`；
- 平台价格配置；
- 是否启用；
- 模型渠道。

已确认规则：

- 渠道初始为空。
- 渠道不是保存模型的必填条件。
- 用户可以在零渠道状态下确认保存。
- `isActive` 初始值为 `false`，管理员仍可在创建弹窗中主动修改。
- `requestUrl/requestAuth` 本轮继续保留。
- 提交时校验 system scope 的 `model` 不重复，不同类型也不例外。
- 点击确认后才创建模型并提交渠道关联。
- 点击取消不保存任何字段或渠道变化。

创建弹窗只维护创建字段。可复用默认模型参数时，应先通过白名单函数生成不含实例身份的创建初值：

```ts
type CreateSystemModelFormData = {
  model: string;
  type: ModelTypeEnum;
  provider: string;
  name: string;
  isActive: boolean;
  requestUrl?: string;
  requestAuth?: string;
  pricing?: ModelPricing;
  config: ModelConfig;
  channelIds: Array<string | number>;
};
```

该类型不得增加 `modelId?: string`。创建成功后接口可以在响应中返回新生成的 `modelId`，但它不能出现在创建请求和创建前的表单状态中。

### 8.3 零渠道语义

“允许零渠道保存”只决定配置合法性，不保证模型可以成功调用。

模型是否实际可调用取决于是否存在有效连接方式，例如：

- 已配置可用的 `requestUrl/requestAuth`；
- 已关联可用渠道；
- 或现有运行时支持的其他默认路由。

如果模型没有任何有效连接方式：

- 仍允许保存；
- 仍允许启用，启用状态与连接配置相互独立；
- 模型测试应返回明确的“未配置有效调用方式”错误；
- 不能把网络失败或未找到渠道包装成模型能力错误。

## 9. 编辑模型

- 创建和编辑复用只包含可持久化配置字段的通用表单，但不复用请求 Schema、目标身份或带条件分支的提交函数。
- 编辑控制器从弹窗外部接收必填 `modelId`，表单字段本身不负责决定目标模型身份。
- 编辑弹窗继续展示 `requestUrl/requestAuth`。
- 编辑弹窗包含“是否启用”和渠道选择。
- 对已有渠道的关联与取消关联在弹窗中暂存，点击确认后才生效。
- 取消编辑不会更新模型配置，也不会更新已有渠道绑定；在子弹窗中确认新建的渠道属于独立资源，创建成功即写入 AIProxy 并与当前模型关联，不随父模型弹窗取消而回滚。
- 模板创建的模型与空白创建的模型使用相同编辑能力。
- 不提供“恢复模板默认值”。

列表启用开关与编辑弹窗中的“是否启用”必须复用同一后端校验和更新服务，避免产生两套规则。

### 9.1 客户端组件边界

客户端按交互职责拆分，避免再次形成同时管理弹窗、表单、请求分流和渠道状态的巨型组件：

| 组件 | 职责 | 明确不负责 |
| --- | --- | --- |
| `AddModel` | 聚合“从模板新建”和“从空白新建”；负责模板选择、模型类型选择和创建弹窗状态 | 编辑既有模型、根据 `modelId` 判断提交分支 |

管理员“模型提供商”不再提供“可用模型”Tab；“模型配置”列表展示“模型渠道”列，不展示协作者/可用范围列。团队模型权限页仍属于本轮范围外，保留其既有协作者能力。

本功能涉及的模型新增、编辑、渠道关联、渠道编辑、渠道测试、默认模型、JSON 配置和日志详情弹窗统一使用 `@fastgpt/web/components/v2/common/MyModal`，不再引入旧版 `common/MyModal`。操作按钮通过 `footer` 传入，禁止继续内嵌 Chakra `ModalBody` 或 `ModalFooter`。v2 modal 的 body 使用可收缩的 flex 高度，上下间距放在滚动容器外侧的 margin 中，避免重复 padding、滚动时上下留白失效或内容进入标题和 footer 区域。PC 端正文上下间距使用 Chakra spacing `6`（24px），左右间距使用 `8`（32px）。

模型配置页只有在管理员模型列表首次请求且尚无可展示数据时显示整表 loading；模型详情和模型更新在各自操作控件上反馈。首次 loading 期间不显示空状态，模型请求完成后才使用 `EmptyTip` 表达真正的空列表。管理员模型列表接口在服务端读取一次 AIProxy 渠道快照，顶层返回全部脱敏渠道摘要，并在每个模型的 `channels` 字段返回已关联渠道摘要；客户端首次进入页面不再单独请求渠道列表。

全局 Layout 的管理员模型缺失检查在模型配置页不再重复请求管理员模型列表；该页面以自身列表请求为唯一首屏模型数据源。进入其他页面时仍保留一次模型缺失检查及跳转提示。

点击编辑时先同步打开编辑弹窗，不能等待详情请求完成后才挂载弹窗。模型详情接口一次返回完整模型参数、全部脱敏渠道展示信息以及各渠道的 `isAssociated` 状态；编辑弹窗内的轻量表格和关联已有渠道弹窗只消费该响应，不再从模型列表透传渠道，也不再二次请求渠道接口。渠道展示信息仅包含 ID、名称、协议名称、协议图标和状态，不向客户端额外暴露 API Key 等鉴权字段。

“已关联渠道”区域遵循 Figma：标题展示关联数量；右侧依次提供“新增渠道”“关联已有渠道”“渠道管理”三个入口，下方使用固定表头的紧凑表格展示渠道名、协议类型、状态和取消关联操作。新增渠道复用既有渠道配置弹窗的紧凑新增态：统一使用 v2 `MyModal` 的 `sm` size，当前模型由入口固定且不可修改，只保留渠道名、协议类型、当前模型、模型映射、代理地址和 API 密钥；渠道管理页的完整新增/编辑态使用同一弹窗的 `lg` size 并保持原能力。关联已有渠道复用 `ModelChannelModal`；渠道管理跳转至当前模型提供商页面的渠道 Tab。普通关联和取消关联仍属于模型编辑草稿，只有保存模型才提交；新增渠道本身是独立资源，创建成功即生效并返回精确渠道 ID，父弹窗直接合并该 ID，不通过刷新前后列表差集推测。

模型配置表使用固定行高的虚拟滚动，只渲染视口及 overscan 范围内的模型行；完整过滤、启用数量和 Provider 统计仍基于内存中的全量模型数据。筛选条件变化时滚动位置回到顶部，表头保持吸顶，未渲染区通过上下占位行维持正确滚动高度。

管理员模型列表保持服务端 MongoDB `_id` 倒序，不在客户端按 Provider 或模型标识二次排序，保证新建模型始终显示在前；后续如需自定义顺序，再引入持久化 `order` 字段统一控制。

虚拟表格使用固定列布局：模型 ID/名称列占用剩余宽度，计费、模型渠道、启用状态和操作列使用固定宽度，避免虚拟窗口切换不同内容时浏览器重新计算列宽导致表头抖动。模型类型不单独占列，而是作为模型 ID/名称列标签区的第一个标签展示。窄屏通过表格最小宽度和横向滚动保证固定列不被挤压。

管理员模型配置表仅在 Plus 版本展示计费列；末列明确显示“操作”表头，不能只保留无标题的操作图标。虚拟列表占位行的列数需随计费列是否展示动态变化（包含独立选择列后，Plus 6 列、非 Plus 5 列）。保存模型及启动构建运行时模型时统一归一化计费梯度；价格按 `priceTiers`、旧 `inputPrice/outputPrice`、旧 `charsPointsPrice` 逐级解析，当前级为空或只有一档双零时继续回退。所有级别均无有效价格时才返回空数组并在列表显示 `-`，避免迁移后的双零分项价格吞掉有效综合价格。

### 9.2 保持现有调用优先级

本轮只调整管理员配置交互，不重新设计模型运行时路由。根据当前代码，继续保持：

1. LLM 使用用户自带 OpenAI Key 时，用户 Key 的 base URL 和 key 优先，模型的 `requestUrl/requestAuth` 不覆盖它。
2. 管理员显式指定渠道进行模型测试时，测试请求临时移除模型的 `requestUrl/requestAuth`，并通过 `Aiproxy-Channel` 强制使用所选渠道。
3. 未使用用户 Key、也未显式指定测试渠道时，各模型类型继续按当前实现优先使用模型级 `requestUrl/requestAuth`。
4. 没有适用的模型级请求配置时，继续回退到当前全局 OneAPI、AIProxy 或 OpenAI base 配置。

各模型类型对 `requestAuth` 单独存在时的历史处理可能不同，本轮不顺带统一；测试应验证行为没有因添加渠道交互而改变。

## 10. 停止自动预装

当前 `packages/service/core/ai/config/utils.ts` 中的 `syncPreinstalledSystemModels` 会在启动和定时刷新时，把 Plugin 模型自动写入 `ai_models`。

本轮需要：

- 删除启动和定时任务中的自动预装调用。
- Plugin 模型列表只在管理员打开模板入口和提交模板安装时实时拉取。
- `loadInstalledModels` 只加载数据库中明确存在的模型实例。
- 删除从模板创建的模型后，刷新 Plugin 或重启服务不能将其重新安装。
- Plugin 模板变化不能自动修改已安装模型。

模板拉取与已安装模型加载必须彻底解耦。

## 11. API 方案

所有新增或修改的 API 必须使用 Zod 定义输入输出，并在 NextJS API 边界通过 `parseApiInput` 校验。

### 11.1 实时模板列表

```text
GET /admin/settings/model/templates
```

- root 鉴权。
- 每次请求实时调用 Plugin。
- 不支持 version 协商。
- 不读取或写入模板缓存。
- 返回规范化、可用于本次选择的模型模板列表。

### 11.2 从模板批量创建

```text
POST /admin/settings/model/createFromTemplates
```

- root 鉴权。
- 接收临时模板键和统一渠道集合。
- 服务端再次实时拉取 Plugin 校验。
- 先通过当前 AIProxy 渠道更新接口写入模型名，再创建 MongoDB 模型。
- 所有新模型统一以 `isActive: false` 创建。
- 所有渠道更新成功后，使用单个 MongoDB 事务创建整批模型。
- 跨 AIProxy 和 MongoDB 的失败不执行补偿或回滚。

### 11.3 从空白创建

```text
POST /admin/settings/model/create
```

- 使用独立 `CreateSystemModelBodySchema` 和独立创建服务。
- 创建请求和内部创建数据类型都没有 `modelId` 字段，Schema 应拒绝额外传入的 `modelId`。
- 只能调用 MongoDB create/insert 能力，不能复用 update/upsert 完成创建。
- `requestUrl/requestAuth` 继续保留在请求 Schema。
- `channelIds` 允许为空数组。
- `isActive` 默认值为 `false`，空白创建时允许管理员在弹窗中主动修改。
- 后端不能因为零渠道直接拒绝保存。
- 后端不能因为没有其他有效调用方式拒绝保存或启用。
- 后端校验 system scope 的 `model` 唯一，数据库 `{ scope, model }` 唯一索引负责并发兜底。
- 创建成功响应可以返回 MongoDB 新生成的 `modelId`。

### 11.4 更新已有模型

```text
PUT /admin/settings/model/update
```

- 使用独立 `UpdateSystemModelBodySchema` 和独立更新服务。
- MongoDB `modelId` 是更新接口的必填目标标识，与可编辑 `modelData` 明确分开。
- 模型调用标识 `model` 创建后不可变：编辑表单只读展示，`modelData` 协议不包含该字段，更新接口拒绝客户端注入；渠道替换接口也不接收新的 `model`。
- 配置文件导入命中本实例有效 `modelId` 时，以数据库中的 `model` 为准，只更新其余可编辑参数；输入配置中的 `model` 即使缺失、为空或类型错误也会被忽略，不参与完整校验、更新及停用集合计算。外部 `modelId` 仍按输入中的非空 `model` 创建或更新。
- 更新接口只能执行带 `{ _id: modelId, scope: system }` 条件的 update。
- 找不到目标模型时返回不存在错误，禁止 `upsert: true`，禁止转调创建服务。
- 更新接口不能被创建控制器引用。

### 11.5 渠道绑定

模型渠道浮窗与模型配置弹窗复用同一替换能力；查询直接使用管理员模型列表或模型详情接口返回的渠道快照：

```text
PUT /admin/settings/model/channel/replace
```

不保留单独的渠道绑定查询接口，避免出现第三份渠道取数路径。

## 12. 升级兼容

### 12.1 已有模型

“默认空模型”只针对全新数据库。已有部署升级时：

- 保留当前 `ai_models` 中的所有系统模型和 `modelId`。
- 保留现有默认模型引用。
- 不自动删除此前由 Plugin 预装的模型，因为无法证明它们未被使用。
- 停止升级后的再次自动预装。

### 12.2 requestUrl/requestAuth

本轮不删除、不迁移这两个字段：

- 数据库 Schema 保留。
- 创建和编辑 API 保留。
- 管理员配置 UI 保留。
- 运行时继续遵循既有行为。
- 不新增清理历史数据的系统迁移。

### 12.3 Plugin 模板来源

现有模型无需回填 `templateId/templateVersion`：

- 不建立模板与实例的长期外键。
- 不以当前 Plugin 列表判断历史模型是否应删除。
- 不提供自动同步或恢复模板默认值。

### 12.4 `system_models` 迁移判定

停止 Plugin 自动预装后，旧模型迁移仍需兼容升级期间 `ai_models` 已存在模型的场景。迁移规则为：

1. 系统迁移 Runner 仍然只根据静态注册表和 `system_migration_states` 判断任务是否需要执行，不能用业务表是否为空代替迁移任务状态。
2. 全量读取并校验 `system_models`，旧表是同名模型 canonical 配置的权威源。
3. 在事务内读取最新的 system scope 目标快照；同名模型保留新表 `_id` 并由旧表配置覆盖，确保已经回填的业务引用不失效。
4. 旧表独有模型沿用旧 `_id` 新增；新表独有模型保留，不做删除。
5. 已有且仍有效的默认模型优先，旧表默认标记只补齐缺失或失效槽位。
6. 模型更新、新增和默认模型合并位于同一个 MongoDB 事务中；任一步失败全部回滚。
7. 迁移不删除 `system_models`，避免升级过程产生不可恢复的数据删除。

Plugin 在这个迁移中的边界：

- 删除迁移完成后的 `syncPreinstalledSystemModels`，迁移不得再把 Plugin 模型写入新表。
- 旧表为空时无需拉取 Plugin 模板；存在旧数据时可使用实时模板修复历史损坏字段。
- 模板只参与旧记录转换，不直接产生待迁移或预装模型。
- 已安装模型缓存的重新加载与 Plugin 模板解耦。
- 若决定进一步删除迁移对 Plugin 修复能力的依赖，必须先确认所有受支持旧版本的
  `system_models` 都能仅凭自身字段通过新 Schema 校验；现有测试已经覆盖了依赖模板修复损坏旧记录的场景，因此当前不直接删除该兼容能力。

当前任务登记版本为 `4.17.0`，仓库尚无 `v4.17.0` 发布标签，可以在正式发布前直接收敛
`20260903_migrate_legacy_system_models` 的实现和阶段定义。一旦该任务随正式版本发布，不能再
修改其 ID、顺序或既有执行语义；后续修复必须在注册表末尾追加新任务。

发布约束：迁移执行期间不允许管理员或旧版本节点继续修改模型。常规滚动升级下可能遗漏
迁移快照之后写入旧表的数据属于本版本已接受风险，不在迁移任务内增加双写或写入栅栏。

## 13. 模板并发变化规则

模板在选择后发生变化的处理策略已经确认。

具体场景：

1. 管理员打开模板弹窗，看到并选择 `model-a` 和 `model-b`。
2. 管理员进入渠道选择步骤。
3. 此时 Plugin 的模板列表发生变化，例如 `model-b` 被删除，或者它的默认参数被修改。
4. 管理员点击确认时，服务端按已确认规则再次实时拉取模板，因此发现当前模板与管理员选择时看到的内容不一致。

处理规则：

- 如果 `model-b` 已不存在，整批失败，`model-a` 也不创建，提示存在已失效模板并要求重新选择。
- 如果 `model-b` 仍存在但默认参数发生变化，允许继续创建，不把参数变化视为并发冲突。
- 模型实例使用提交时后端最新拉取到的 `model-b` 参数，而不是弹窗初次打开时的旧参数。
- 服务端只按临时键 `{ type, model }` 判断模板是否存在，不要求比较整个模板对象。
- 模板缺失检查、模型重复检查和其他创建校验必须全部在写入前完成。

## 14. 验收标准

### 14.1 模板与空模型

- 全新数据库启动后，管理员模型列表为空。
- 启动、定时任务和 Plugin 刷新不会向 `ai_models` 自动写入模型。
- 每次打开“从模板新建”都会实时请求 Plugin。
- 关闭后重新打开会再次请求，不复用上一次结果。
- Plugin 必须在 FastGPT 启动阶段可用；启动完成后的单次模板请求失败不得改写已安装模型。

### 14.2 从模板新建

- 模板支持多选。
- 点击下一步进入统一渠道配置。
- 不出现逐个模型参数编辑。
- 渠道允许为空并可成功保存模型。
- 创建的模型统一默认不启用。
- 已安装的相同 `model` 模板不会出现在候选列表中。
- MongoDB 中任一模型创建失败时整批 MongoDB 事务回滚。
- 渠道更新与 MongoDB 创建之间允许出现不一致，不要求跨系统回滚。
- 提交时服务端重新拉取并验证模板。
- 任一所选模板已不存在时整批失败。
- 模板仍存在但参数变化时继续创建，并采用提交时的最新参数。
- 创建后每个模型都有独立 `modelId`。
- Plugin 后续变化不会自动修改已安装模型。

### 14.3 从空白新建与编辑

- 先选择模型类型，再打开配置弹窗。
- `requestUrl/requestAuth` 正常展示、保存和回显。
- 渠道初始为空，零渠道可以保存。
- 弹窗包含是否启用。
- 是否启用默认关闭，但允许管理员主动打开。
- 没有任何有效调用方式时仍允许保存和启用。
- 相同 `model` 无法重复创建，即使 `type` 不同。
- 存在同类型默认模型时，新建仍调用创建接口，不得更新默认模型原记录。
- 新建模型后原默认模型继续存在，默认模型 ID 保持不变。
- 新建表单状态和创建请求中完全不存在 `modelId` 属性。
- 即使人为向创建请求注入 `modelId`，创建接口也应校验失败。
- 编辑始终调用独立更新接口；创建始终调用独立创建接口，两者不能依赖可选字段动态分流。
- 编辑模型时模型 ID 只读，更新请求只提交可编辑参数，不能携带或修改 `model`。
- 取消弹窗不会保存参数或渠道变化。
- 创建完成后，无论模型来自模板还是空白创建，后续都进入独立的编辑弹窗和更新接口。

### 14.4 模型与渠道联动

- 模型表增加“模型渠道”列并显示绑定数量。
- 系统管理员表格不再显示“可用范围”。
- 点击渠道数量可编辑关联。
- 点击取消不生效，点击确认后一次生效。
- 模型页与渠道页展示一致的绑定关系。
- 模型测试在没有有效调用方式时返回可理解的配置错误。
- 添加渠道交互后，用户 Key、显式测试渠道、模型请求配置和全局配置的现有优先级不变。

### 14.5 模型批量操作

- 表格最左侧增加独立的固定宽度复选框列，复选框不放入模型 ID/名称单元格；全选只覆盖当前筛选结果。虚拟占位行列数按选择列及 Plus 计费列动态计算（Plus 6 列、非 Plus 5 列）。
- 选中至少一个模型后，使用通用 `FloatingActionBar` 展示已选数量及“批量启用”“批量停用”“批量删除”。
- 行选择能力由通用 `useTableMultipleSelect.getRowSelectionProps` 提供：进入多选状态后，点击行内非交互区域可切换该行选中状态；复选框、复制、渠道、启停开关及操作按钮等热区保留原交互，不触发行选择。未进入多选时可继续执行调用方传入的原行点击行为。
- 单模型完整编辑仍使用 `PUT /admin/settings/model/update`；单个开关与批量启停统一使用 `PUT /admin/settings/model/updateStatus`，请求体为 `modelIds + isActive`。单个开关传单元素 `modelIds`，避免把完整模型参数混入状态操作。
- `DELETE /admin/settings/model/delete` 扩展 `modelIds` 请求体，同时兼容旧版单 `modelId` query。
- 批量启停和批量删除都在 MongoDB 事务内校验并操作全部目标；任一模型不存在则整批失败。批量删除同时删除对应模型权限记录。
- 每次批量操作完成后只刷新一次系统模型缓存和管理员列表，并清空已选项。

### 14.5 升级兼容

- 已有部署升级后保留全部现有模型和 modelId。
- 现有默认模型和工作流引用不受影响。
- 现有 `requestUrl/requestAuth` 数据和运行行为不受影响。
- 删除模板来源模型后，重启不会重新安装。
- `ai_models` 已有同名 system 模型时保留其 `_id`，其余配置由旧表覆盖。
- 旧表独有模型新增，新表独有模型保留；默认标记在同一事务内合并。
- 迁移不写入 Plugin 模型，旧表为空时也不请求 Plugin。
- 管理员在任务完成后删除全部模型，不会导致旧 `system_models` 被重新迁入。
