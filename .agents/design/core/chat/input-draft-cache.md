# 按会话保留输入草稿

## 1. 需求与已确认规则

实现分支为 `codex/chat-input-drafts`，在独立 worktree 开发和验证。

用户已确认：

1. 会话分别保留输入文字和附件。
2. 附件只恢复上传成功的文件；待上传、上传中、上传失败的文件不属于持久化草稿。
3. 从最后一次修改开始保留 1 小时，编辑会续期。
4. 发送失败沿用当前恢复规则：占用了主输入框、且未收到回复时恢复输入；已收到部分回复时不恢复。
5. 草稿按 `tmbId + appId + chatId` 隔离。

实现采用的配套规则：

- 沿用 `sessionStorage`，支持同一标签页内切换会话和刷新后的恢复。
- 一个标签页合计最多保留 10 份非空草稿，超限淘汰最后修改时间最早的一份。
- 切换、查看、刷新恢复、刷新预览链接不算修改，不延长草稿有效期。
- 文字编辑、已上传附件新增或移除、发送失败恢复，算一次草稿内容修改。
- 文字为空但有已上传附件，仍是一份非空草稿。
- 清空全部文字和附件、发送被正式接受、删除对应会话后，删除对应草稿。
- 草稿过期约束的是缓存恢复；不通过定时器强行清空用户正在操作的输入框。

## 2. 改动前的实现与问题证据

### 2.1 已经有按 chatId 分开的存储键

`projects/app/src/components/core/chat/ChatContainer/ChatBox/hooks/useChatInputForm.ts`：

- 61–69 行：在 `useForm.defaultValues` 中读取 `chatInput_${chatId}`。
- 74–86 行：监听文字和 `chatId`，防抖 300ms 后写入或删除对应键。
- 115–129 行：`resetInputVal` 更新文字、附件，删除当前键并调整 textarea 高度。

因此，“缓存只存一份”不是准确的实现描述。实际问题是缓存已分会话，但当前表单没有在会话变化时恢复对应草稿。

### 2.2 会话切换复用表单，旧文字会覆盖新草稿

`AppChatWindow.tsx` 的 280–298 行渲染同一个 `ChatBox`，没有用会话身份改变 React key。
`ChatBox/index.tsx` 的 786–794 行也继续渲染同一个内部组件。

同时，`ChatBox/index.tsx` 的 412–425 行在会话切换时只重置了问题引导、冲突状态和 `chatStarted`，没有恢复 `input/files`。

推导链路：

1. 进入 A，表单初始化并读取 A 的草稿。
2. 用户输入 A 的内容，防抖写入 A 的键。
3. 切到 B，React 继续复用表单；`defaultValues` 不会重新初始化表单值。
4. 表单仍持有 A 的内容，但保存 effect 的 `chatId` 已变成 B。
5. 300ms 后，A 的文字被写入 B 的键，覆盖 B 原有草稿。

已用真实 `useChatInputForm`、React、react-hook-form、ahooks 和 JSDOM 做内存复现；只单独加载了无关依赖的项目枚举声明，没有模拟表单或防抖行为：

```text
A 输入：A original draft
B 原缓存：B original draft
切到 B 后的表单值：A original draft
等待防抖后的 B 缓存：A original draft
```

这验证了表单恢复与存储身份错位的问题；没有执行浏览器端完整 UI 验收。

### 2.3 当前没有有效期、容量控制和附件恢复

缓存值只有文字，没有时间戳；不存在 1 小时过期和 10 份限制。
`files` 的默认值固定为空数组，保存 effect 也没有监听附件。

当前存储键只包含 `chatId`，缺少团队成员 `tmbId` 和应用 `appId`。
本需求按用户确认的 `tmbId + appId + chatId` 隔离草稿。

### 2.4 当前发送清理时机与失败恢复

`useChatGenerate.ts` 的 785–786 行在发送流程已建立本轮消息、调用 `onStartChat` 之前清空输入。
889、927 行分别处理生成冲突和未收到回复的失败恢复。
`utils/generate.ts` 中的恢复条件为 `clearInput && !responseText`。

还有两个与新草稿机制直接相关的边界：

- `resetInputVal` 在 textarea 尚未挂载时直接返回，导致数据清理依赖 DOM 是否存在。
- `ChatInput.tsx` 的 168–174 行调用发送后立即 `clearFiles()`，而变量校验在异步发送流程内部；校验拒绝发送时也可能先清空附件。

## 3. 从状态所有权设计

把输入草稿定义为“属于指定团队成员、应用和会话的、尚未发送的可序列化内容”。

分清三个对象：

| 对象 | 内容 | 生命周期 |
| --- | --- | --- |
| 会话草稿 | 文字、已上传文件引用、修改时间、版本 | 最后修改后 1 小时，合计最多 10 份 |
| 当前表单 | 当前会话正在展示和编辑的内容 | 随当前输入区挂载和会话切换变化 |
| 发送快照 | 本轮实际提交的身份、文字、附件、草稿版本 | 从提交到成功、失败或取消 |

表单是当前会话草稿的编辑视图。发送和上传回调必须携带原始所有者，不能根据回调完成时的当前会话决定写入位置。
上传中的 `File`、进度、控制器和任务 ID 属于运行状态，不进入持久化草稿。

## 4. 存储模型与限制

### 4.1 草稿标识

逻辑键由以下字段组合，用 JSON 数组编码，避免分隔符歧义：

```text
[tmbId, appId, chatId]
```

缓存模块直接接收这三个字段，不增加其他隔离维度。
任一字段未就绪时不读写草稿，不用空值或其他身份字段代替。
可编辑的新会话必须提前有稳定 `chatId`，复用现有 `getNanoid`/会话 store 能力。
现有聊天运行时的 `sourceKey` 继续用于运行状态，本次草稿键使用上述三个字段。

### 4.2 一个版本化存储项

新增 `fastgpt_chat_input_drafts_v1`，其结构为：

```text
version
entries[]
  identity
    tmbId
    appId
    chatId
  revision
  text
  files[]
    key
    name
    type
  updatedAt
  expiresAt = updatedAt + 60 * 60 * 1000
```

正式实现时用 Zod 定义运行时校验，并从 schema 推导类型。
附件仅在有 `key` 和上传成功 `url`、且没有错误时进入快照；`status === 1` 也代表上传中，不能独立作为成功条件。

不保存 `rawFile`、图片 base64 `icon`、进度、错误、AbortController 或 field array 生成的 ID。
图片恢复后用新预览 URL 显示，普通文件按文件名重建图标。
恢复时重建前端文件 ID/删除定位 ID，避免旧上传任务误命中新文件项。

### 4.3 每次操作都执行同一套规则

读取和写入通过统一存储模块执行：

1. 安全解析、校验结构；异常数据按空缓存处理。
2. 剔除 `now >= expiresAt` 的记录。
3. 内容没有变化时保留原修改时间；恢复和导航不生成新的修改时间。
4. 内容变更时更新对应会话；完全空的草稿直接删除。
5. 按 `updatedAt` 排序，保留最近修改的 10 份；同时间使用稳定排序。
6. 更新存储；访问失败或配额不足不阻断输入和发送，使用当前页面的内存副本保留切换恢复能力。

文字保存保留原文，包括换行和空格；发送前的 trim 沿用现有行为。
防抖只合并写入，`updatedAt` 取实际内容变化时间，不取防抖落盘时间。
持续输入可设置最大等待时间，防止只有尾随防抖时长期不落盘。

读取、写入时统一剔除过期记录；过期草稿不再恢复。没有为活动输入框增加强制清空的定时器。

旧 `chatInput_*` 没有身份和时间戳，也可能已经被串写，无法可靠补齐归属和有效期。
建议新版首次启用时清理这个已确认由 FastGPT 创建的旧前缀，不自动迁移到新身份；不清空其他 sessionStorage 项。

## 5. 会话切换和附件恢复

在 `useChatInputForm` 内显式处理 `tmbId/appId/chatId` 组合变化。
仅给整个 ChatBox 增加 key 会同时重建生成、恢复、音频和滚动状态，影响范围更大，也仍需解决切换前的防抖保存。

切换 A → B 的顺序：

1. 保存旧身份 A 的最新内容快照及实际修改时间，取消 A 的待执行防抖。
2. 更换当前表单的所有者；使旧异步回调失效。
3. 读取 B 的有效草稿，把文字和附件列表明确恢复到 B。
4. 无有效草稿时设置空文字、空附件，不能保留 A 的字段。
5. 恢复期间暂停自动保存；完成后只监听真实内容修改。
6. 调整 textarea 高度；DOM 不存在只跳过高度计算，不跳过数据操作。

普通卸载、刷新前同步 flush 最近一次快照，并取消计时器。
登出或删除会话属于主动清理，必须先使旧保存任务失效，避免卸载 flush 把刚删除的草稿写回来。

附件恢复是异步操作。文字可以先恢复，附件以可见的恢复状态展示，相关文件确认可用前禁止发送。
按 `{identity, revision}` 检查回写：切到其他会话、移除附件、清空或发送后，旧预览响应不能重建文件项。
确认文件已不存在或已失效时移除该附件并提示重新选择；暂时网络失败保留引用并允许重试。

只恢复已上传附件也需要隔离旧上传流程：

- 切换和卸载时取消旧会话的未完成上传，旧结果不得追加到新会话。
- `FileReader` 异步准备文件后追加列表也要检查原会话是否仍有效。
- 继续保留 `uploadId` 检查，并加上会话身份检查；单独检查列表里是否存在同一 ID 不足以表达所有权。
- 上传完成后立即更新草稿，避免完成后很快刷新导致附件尚未落盘。

## 6. 附件续期是必要的后端配合

### 6.1 当前实际生命周期

当前链路：

1. `S3ChatSource.createUploadChatFileURL` 默认传入 1 小时，见 `packages/service/common/s3/sources/chat/index.ts` 的 175 行。
2. `S3BaseBucket` 创建上传访问能力时写入 `MongoS3TTL.expiredTime`；单文件和 Multipart 均有临时 TTL。
3. 对话保存通过 `persistChatFiles` 删除这些 TTL，附件转为随会话持久化。
4. 清理任务扫描过期 TTL，普通文件提交删除队列；实际删除可能晚于到期时间。
5. 现有 `presignChatFileGetUrl` 只校验权限并生成预览链接，没有续期临时文件 TTL。

反例：10:00 上传附件，10:50 修改文字。
草稿按用户要求有效到 11:50，但附件临时 TTL 仍为 11:00。
重新签发 URL 不会使已经删除的对象恢复，因此只修改前端缓存无法满足已确认需求。

### 6.2 建议批量准备草稿附件的接口

新增 `POST /api/core/chat/file/prepareDraftFiles`，职责是校验草稿附件、按剩余保留时间续期临时对象、返回新预览链接。

请求业务字段：

- 复用现有 App 聊天鉴权 target，传入 `appId` 和必要的鉴权上下文；服务端从鉴权结果获取 `tmbId`，不信任客户端声明的成员身份。
- `chatId`。
- `keys`：去重后的附件 key 数组，限制为现有文件数量上限。
- `remainingMs`：这份快照距离过期的剩余毫秒数，范围为 `(0, 1h]`。

响应按文件返回可用状态、新预览 URL、临时对象实际到期时间或持久化标识；明确区分对象已失效与临时服务异常。
客户端使用快照剩余时间计算请求，不在恢复时重新赋值 1 小时；预览 URL 的变化不算草稿内容修改。

服务端约束：

1. 使用 `authChatTargetCrud` 鉴权，并逐个复用 `isAuthorizedChatFileS3Key` 验证来源、用户、会话归属。
2. 确认对象已经上传完成，Multipart 未完成记录不允许作为可恢复附件续期。
3. 到期时间由服务端按有界剩余时间计算，原子更新时只允许续期尚未过期的普通对象 TTL。
4. 使用只向后延长的更新，避免乱序请求把较新的期限缩短；不使用 upsert 复活已删除的 TTL。
5. TTL 不存在时，不能直接推断为持久化。需确认文件已经被该会话保存认领；已清理、等待删除或无法证明归属的对象不能重新建 TTL。
6. 使用当前数据库时间检查续期资格，避免请求中间的异步等待使过期对象被复活。
7. 与清理路径统一时间和条件边界；清理不可仅凭旧扫描快照排队删除已续期文件，提交删除前须核对当前到期条件。
8. 发送保存与续期竞争时，以保存认领为准；续期不能给已持久化附件重新挂上删除期限。

以上不需要修改当前 MongoDB 字段或索引定义；实现中若新增状态字段，应按仓库要求重新检查 Schema、历史索引及相应测试。

新增 API 按 `api-development` 规范完成 Zod 请求/响应类型、OpenAPI 路由与字段说明。
API 入参用 `parseApiInput`，实际响应用对应 schema 校验。

### 6.3 调用时机和失败行为

文字或已上传附件变更时，防抖保存本地快照，并合并同一会话的附件准备请求。
附件上传完成、切换离开、附件草稿恢复和正式发送前应同步检查最新快照需要的文件能力。
仅剩文字的草稿不调用该接口。

缓存可以先保存引用，但在续期或预览准备未确认成功时，不把附件当作可靠可发送状态。
临近附件到期时不能无限等待长防抖；需及时请求，失去资格后明确提示重新上传。
网络失败不清文字，不虚报附件续期成功；刷新离开无法完成请求时，只能在回来后重新校验对象。
持续离线不能保证远端临时文件存活，这是对象已被服务端清理后的真实限制。

缓存淘汰和发送清理只移除本地引用，不直接删除 S3 对象。
未发送文件继续由 TTL 清理；已进入聊天记录的文件继续由对话生命周期管理。

## 7. 发送清理与失败恢复

把清理收敛到发送正式接受的位置，继续沿用 `clearInput` 的现有含义。
快捷回复、推荐问题和历史重试默认不占用主输入框，不删除用户正在编辑的独立草稿。

发送顺序：

1. 捕获发送快照的 `tmbId/appId/chatId`、文字、附件和版本。
2. 完成变量、空内容、生成状态及附件可用性校验；拒绝发送时保留草稿。
3. 正式接受本轮发送后，取消该快照对应的保存任务，同步清理对应缓存。
4. 仅在当前表单仍属于该身份且版本未被用户修改时，清空文字和附件。
5. 移除 `ChatInput.handleSend` 中未经发送接受就执行的附件清理，把数据清理交给同一提交边界。
6. 请求失败时按现有条件恢复发送快照，作为新的未发送草稿保存；不覆盖期间新写的草稿。

清理必须与防抖取消、版本检查一起完成。仅 `removeItem` 后依靠后续 effect 清空，可能被旧计时器重新写回。
`resetInputVal` 应承担表单赋值和 DOM 调整；草稿删除、内容替换和发送失败恢复分别使用明确语义，避免所有非空赋值也先删除草稿。

跨会话失败回调最多恢复原会话的缓存，不写入当前其他会话的表单。
用户主动离开导致的 abort 沿用当前行为，不额外恢复。

变量校验、附件准备和音频初始化的异步等待结束后，均重新确认发送快照仍属于当前成员和会话。
主动清理使用代次使旧回调失效，代次不会在失效记录淘汰后复用；因此很晚的失败回调也不能复活已删除的草稿。

改动前分析已完成：

- 静态核对表单初始化、会话切换、发送、上传和 S3 临时文件保存/清理链路。
- 内存运行真实输入 hook，复现 A 覆盖 B 草稿，并验证现有 reset 只删除当前存储键。
- 运行 `generate.test.ts`、`uploadTask.test.ts`，2 个局部文件共 20 项通过，确认现有失败恢复和上传任务判定规则。

实现的局部验证覆盖以下场景：

| 场景 | 验收结果 |
| --- | --- |
| A → B → A，双方均有文字和成功附件 | 分别恢复，不串写、不覆盖 |
| 输入后 300ms 内切换、卸载或刷新 | 最新内容保存在原会话 |
| 第 59 分钟修改，然后查看/刷新 | 修改会续期，查看/刷新不续期 |
| 距离最后修改恰好 1 小时 | 缓存失效，不能恢复 |
| 写入第 11 份，重复编辑已有会话 | 保留最近修改 10 份，重复编辑不增加份数 |
| 只有已上传附件、移除最后一个附件 | 能恢复附件；完全空后删除草稿 |
| 上传中切换、FileReader 迟到 | 新会话不出现旧文件，未成功附件不持久化 |
| 恢复文件时切换、删除、发送 | 迟到响应不重新追加附件 |
| 开始发送、发送前变量校验失败 | 接受发送才清理；拒绝发送仍保留文字和附件 |
| 发送清理时已有待执行防抖 | 清理后不复活已发送草稿 |
| 未回复失败、已有部分回复失败 | 前者恢复文字和附件；后者不恢复 |
| 发送后输入新草稿，旧请求失败 | 保留新草稿，旧快照不覆盖 |
| A 发送后切到 B，A 失败 | B 的输入和缓存不受影响 |
| 推荐问题、重试、快捷回复 | 不清除主输入框独立草稿 |
| 同 chatId，不同 tmbId 或 appId | 严格隔离 |
| tmbId、appId 或 chatId 尚未就绪 | 不读写草稿，不与其他会话共用空值键 |
| 缓存损坏、storage 不可用、textarea 未挂载 | 输入、清理、发送不依赖存储或 DOM 成功 |
| 上传 50 分钟后编辑，原上传已满 1 小时 | 续期后的附件仍可预览和发送 |
| 同时续期、清理、发送保存 | 已续期对象不误删，持久化对象不重新加 TTL，过期对象不复活 |
| S3 对象消失、续期暂时失败 | 前者提示重选；后者保留引用并可重试 |
