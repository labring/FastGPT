# FastGPT 版本文档

## 调用与范围

仅手动调用，例如：

- `$fastgpt-release-docs 4173`
- `使用 fastgpt-release-docs 更新 v4.17.3 文档，对比上一正式版本。`
- `$fastgpt-release-docs v4.17.3，目标 ref 使用当前分支。`

本 Skill 的产物是版本中文源文、对应英文 MDX，以及必要的同目录导航更新。调用本 Skill 不代表要求修改产品代码、切换分支、创建 worktree、提交、推送或创建 PR；这些动作按本次用户要求执行。

优先使用当前 FastGPT 仓库；当前目录不是该仓库时，使用用户指定的 FastGPT 仓库目录。先阅读仓库适用的 `AGENTS.md`，检查工作区，保留用户已有修改。不要因文档任务强制清理、重置或切换工作区。

## 1. 确认版本、文件与比较范围

### 版本与文件

- `v4.17.3`、`4.17.3` 和 `4173` 均可表示 V4.17.3。
- 简称通过已有文档的 basename、frontmatter 和 Git tag 交叉确认，不按固定字符位置硬拆版本号；无法唯一确定时只询问版本歧义。
- 优先定位已有页面。通常对应 `document/content/self-host/upgrading/4-17/4173.mdx` 与 `4173.en.mdx`；新页面沿用同系列目录和命名规则。
- 阅读目标版本、上一版本中文说明与同目录 `meta.json` / `meta.en.json`，保留既有 frontmatter、组件及人工编辑决策。
- 尚未正式发布的版本在 frontmatter 的 `upgradeTags` 数组中标注开发状态：中文用 `开发中`，英文用 `In dev`。更新已有页面时，将旧的 `进行中` / `In progress` 替换为对应新标签，保留其他升级标签。

### 人工编辑优先

更新既有版本文档时，以当前文档及历史人工修改为编辑基线，只增量补充本轮新变化，不从代码差异重新生成整篇。人工决定哪些内容需要发布、如何表述和归并，优先于本 Skill 的默认结构、排序和 AI 候选清单。

- 写入前同时检查中英文页面的未提交 diff（含暂存区）及 `git log --follow -p -- <文档路径>`，识别历次删除、精简、改写、合并和顺序调整。提交作者可能同时用于人工与 AI 提交，不能仅凭作者身份判定；归属不明的既有删改也先保留。
- 人工删除的条目视为明确排除，不视为文档遗漏。即使代码、PR、旧稿或英文旧文仍有依据，也不得在下次扫描时自动恢复；不得通过换标题、换章节、改写措辞或并入其他条目重新引入同一事项。只有用户明确要求恢复时才补回。
- 人工精简或改写后，不自动补回被删细节，也不撤销人工合并、范围限定和排序。后续同一领域出现独立的新用户变化时，仅补充新的差异，不借此恢复已排除的旧内容。
- 若人工表述与当前实现存在事实冲突，说明具体冲突和代码依据，保留原文等待用户决定；继续处理不受影响的内容，不以事实复核为由静默覆盖人工修改。
- 同步翻译时遵循中文人工删改，不从英文旧稿反向补回已删除的中文内容；英文自身的人工润色在不与中文事实冲突时也应保留。

### 比较范围

1. 用户指定比较基准或目标 ref 时，以其为准。
2. 未指定基准时，查找低于目标版本的最近一个正式发布 tag，按版本顺序判断，排除预发布 tag；不要直接将补丁号减一。例如存在 `v4.17.2` 时，V4.17.3 通常以它为基准。
3. 目标版本已有正式 tag 时，默认比较到该 tag。尚未发布且没有目标 tag 时，默认比较到最新 `upstream/main`；缺少该 remote 时检查实际发布仓库的 main，不把任意同名分支当成上游。
4. 按需刷新选定 remote 的 main 与版本 tags，只更新引用，不 checkout 或 rebase。若上一正式版本缺失，先检查远端；仍无法确定时询问比较基准，不自行猜测。
5. 开始分析前固定两端 commit SHA，并向用户简要说明版本、比较范围和目标文档。当前分支或未提交的产品改动仅在用户要求时纳入，不把无关工作区改动混入版本范围。

使用提交记录发现线索，使用两端最终代码差异确认事实：

```bash
git log --oneline <base-sha>..<target-sha>
git diff --stat <base-sha> <target-sha>
git diff <base-sha> <target-sha> -- <related-paths>
```

不要只依赖 PR 标题、commit message 或已有版本文档。阅读相关实现、配置、迁移、接口合约及必要的局部测试，核实最终用户行为。被撤回、覆盖且不再生效的改动不列为发布内容。

### Pro 子模块

主仓库范围包含 Pro 变更时，同时分析两个版本实际引用的子模块提交：

```bash
git ls-tree <base-sha> pro
git ls-tree <target-sha> pro
git -C pro diff --stat <pro-base-sha> <pro-target-sha>
git -C pro log --oneline <pro-base-sha>..<pro-target-sha>
```

继续读取相关 Pro diff，不使用当前 Pro 分支或 Pro 最新 main 替代版本指针。必要时获取对应提交对象，不改子模块 checkout。有权限或对象缺失时，说明未核实范围，不补写推测的商业版能力。区分商业版、开源版与外部服务能力。

## 2. 从改动中归纳版本主题

先形成“用户变化 → 适用范围 → 边界/升级动作 → 代码证据”的候选清单，通常保留在工作上下文中，不额外生成分析报告。

- 以功能和用户结果为单位归并，不以 PR 或提交为单位列举。同一功能跨多个 PR 的实现、兼容与修复，整理成一个完整条目。
- 相同领域但结果无关的事项仍分开，不为减少条数而把互不相关的问题堆成长段。
- 一个主题原则上只放一个最合适的章节，不在「升级脚本」「配置变更」「优化」间重复整段说明；升级指南仅保留必须执行的操作与风险。
- **严格过滤对外部用户无感知的内部杂项**：删除合并记录、纯测试补充、临时调试、未开发完成或未对外开放的能力、内部辅助模块（如内部加载器、仅用于测试的实验性适配层），以及仓库研发协作资产（`.agents/skills/` 技能增改、PR 审查/创建/回移脚本、内部 CI 回移或预览流程等）——这些内容一律不写入任何章节（包括「🛠️ 代码优化」）。
- **过滤细碎微调**：无实质用户感知的边角 UI 调整（如分隔线、轻微样式微调）和“无需操作”的温和提示不单列条目。
- 更新既有版本文档时遵循“人工编辑优先”，在保留人工决策的基础上归并本轮新发现，不把有意删除的内容列为待补项。

### 同版本开发过程中的修补不单列

- 对修复候选核对上一正式版本的实现，并沿相关代码历史确认能力和问题的首次引入范围。不能仅凭 `fix` 提交标题，或描述中的“旧版”“历史”字样，就认定为已发布版本的问题。
- 同一目标版本内新增功能的完善、缺陷修补和兼容调整，不单独写成“修复”或另换分类重复列举；在对应功能条目中直接描述最终交付行为，不记录本版本开发过程中的中间缺陷。开发过程中引入又消除、相对上一正式版本没有用户可见变化的回归也不写。
- 首次对外发布的全新功能（例如全新 CLI、SDK 或新体系，即使上一版本存在未对外发布的内部包或过渡代码），本版本内围绕该功能的缺陷修补、错误提示完善与行为收口，一律归并到对应「新增内容」的最终交付描述，不得在「优化」或「修复」中出现“修复 `<新功能>`…”等条目。
- 只有上一正式版本已存在、在本版本得到解决的问题，才作为跨版本修复候选。引入范围暂未核实时继续查证，不把未经核实的事项当作历史修复发布；用户已明确确认的分类和排除决定按“人工编辑优先”保留。

## 3. 中文组织与写作规则

### 章节

新建文档默认使用以下结构；更新既有文档时，人工结构调整优先。`## 重要说明` 仅在本轮存在下线项或硬兼容影响时保留；`## 升级指南` 按实际涉及项保留子章节（`### 镜像更新` 保留供发布阶段填写），其余顶层章节有内容才保留：

1. **重要说明**：前置高风险与破坏性信息，包含 `### 下线配置/功能` 和 `### 兼容说明`，让升级者在操作前第一时间看到必知边界。
2. **升级指南**：依次为 `### 部署模板变更`、`### 配置变更`、`### 镜像更新`、`### 升级脚本`。各子章节聚焦必须执行的动作、迁移顺序与关键前提，不把几十条零散环境变量堆成流水账。
3. **🚀 新增内容**：之前不能做、现在新增且已正式交付的产品级能力；已有功能扩展出新能力也归入新增，不另设“补充”，不列纯底层 SDK 细碎方法或未完工功能。
4. **⚙️ 优化**：用户可直接感知的产品功能、交互与使用体验改善。不放以“修复……问题”为主的缺陷条目；若机制改造同时修复历史故障，按用户主要感知二选一——以解决异常/错乱为主的放「🐛 修复」，以交互/体验升级为主的放「⚙️ 优化」并写成正向改进表述。纯底层算法、内置 Prompt、运行态底座升级归入「🛠️ 代码优化」，不混入本节。
5. **🐛 修复**：上一正式版本已存在、在本版本解决的问题，说明触发场景与修复后的结果；同版本新功能的修补不单列。
6. **🛠️ 代码优化**：面向系统稳定性、效率与维护性的底层工程改进，如架构重构、依赖安全升级、编译/CI 提速、队列/缓存机制、切分算法效率、内置 Prompt 调优、运行态/沙盒底座升级等；不包含仓库内部研发技能或协作流程。

### 重要说明与升级指南结构

默认按以下标题及顺序编写，无内容的可选子章节可省略；已有人工作出的结构调整按前述规则保留：

```markdown
## 重要说明

### 下线配置/功能

### 兼容说明

## 升级指南

### 部署模板变更

### 配置变更

### 镜像更新

### 升级脚本
```

- **下线配置/功能**：用简洁短句列出本版本停止生效的配置项或移除的运行态/功能，避免淹没在长段配置说明里。
- **兼容说明**：**高信噪比原则**——只保留会真实影响外部 API 调用方、自动化脚本、Nginx/网关规则、导出文件解析、工作流运行结果或沙盒路径的破坏性变更及明确适配动作。不列前端自用/后台管理端内部接口改参、不列“无需任何操作”的温和说明，也不重复普通修复。
- **部署模板变更**：集中说明 Docker Compose / K8s 模板、默认镜像源、默认中间件/存储替换、独立库与健康检查等部署拓扑调整，从「配置变更」中拆出便于运维核对。
- **配置变更**：当大批旧 ENV 迁入后台表单或集中维护时，优先用顶部 `<Alert>` 一句话说明并链接到对应环境变量文档，正文**只列必须由管理员手工配置、或原配置文件/机制发生破坏性变化的少数核心项**，不逐个罗列已自动迁移或无须人工干预的环境变量。
- **镜像更新**：编写前期通常留空，由发布人在最后 release 阶段人工填写。不根据目标版本、依赖版本或已有旧版说明自动推导镜像 tag，也不自动填“待发布”等占位内容。保留发布人已经填写的内容；用户明确提供镜像信息并要求写入时再补充。
- **升级脚本**：描述本轮相对上一版本新增或调整的升级脚本。核对脚本实现、注册信息及实际触发机制，明确区分自动执行与手动触发（`manual: true`），说明任务名称、作用、前置依赖、切换/回滚边界及失败重试方式。不重复罗列未变化的历史任务，不把手动脚本写成自动执行。确认本轮没有升级脚本时可写“本轮无升级脚本”。

英文版沿用中文最终结构（包括人工调整）与镜像留空状态，标题翻译交给 `doc-i18n`。

### 统一领域标签

新增、优化、修复及代码优化的条目前加单一领域前缀，形式为 `**[工作流与 Agent]**`。同一套标签贯穿各章节，不混用重要程度、实现手段和问题性质作为分类。

| 标签           | 主要范围                                        |
| -------------- | ----------------------------------------------- |
| 工作流与 Agent | 辅助生成、节点执行、条件、变量引用、交互续跑    |
| 对话体验       | 输入草稿、消息展示、Markdown、Mermaid、加载状态 |
| 知识库与文件   | 解析、上传、导入导出、训练、检索、同步          |
| 工具与渠道     | MCP、HTTP 工具、系统插件、飞书、企业微信等渠道  |
| 团队与权限     | 成员、授权、权限继承、登录与账号安全            |
| 模型与计费     | 模型、模型渠道、价格、积分、套餐、开票          |
| 系统与运维     | 部署、沙盒、升级任务、日志、监控、资源限制      |

按主要用户入口或影响选一个标签。例如工作流选择器的交互修复仍归“工作流与 Agent”，不因为是 UI 改动就归“对话体验”。工程优化中借助请求 profile 定位系统瓶颈归“系统与运维”。

### 排序与粒度

- 重要内容在前，小改动在后。优先考虑用户影响、覆盖范围、安全与数据风险，再考虑功能重要性；不按 PR 编号、提交时间或文件路径排序。
- 同标签条目相邻。每个章节先按该领域最重要改动的影响决定领域组顺序，再在组内按重要程度排序；上表不是固定排序。
- 不使用“核心、体验、补充”作为并列标签。需要概括大版本时，可在开头精选 2–3 项已证实的版本亮点，不能把所有事项都标为重要。
- 同一个结果由多个 PR 完成时合并成一条，保留影响使用的条件与限制。例如“工具名重复、参数先于名称到达、并行参数混淆”可归并为模型原生工具调用流兼容性条目，而不是按三个 PR 写三条。
- **修复章节主动按子模块归并，避免逐 PR 铺陈过细**：同一领域下属于同一子模块或强关联根因的小修复（如工作流记忆隔离与合并、多节点共用沙盒锁/文件/技能冲突、编辑器多处弹窗与输入 UI 细节、对象存储代理上传/流兼容/404、文件名解析与编码、下载短链格式与有效期、同版本数据库兼容、日志筛选与来源统计等）应归并为一条，用 1–2 句讲清核心场景与结果；涉及安全风险、破坏兼容或独立排障动作的修复仍可单列。不把毫无关联的表单、权限或工具问题机械硬拼。
- 通常一条用 1–2 句讲清“变化、用途或触发条件、关键边界”。小改动简写，较长操作说明放升级指南或链接到功能文档，不为每条补充实现原理。

示例形式：

```markdown
## 🚀 新增内容

1. **[工作流与 Agent]** 支持通过自然语言创建或修改工作流，确认方案后生成候选版本并应用到画布。
2. **[对话体验]** 支持恢复会话输入草稿，切换会话或刷新后继续编辑。

## 🐛 修复

1. **[工作流与 Agent]** 修复未填写说明的表单提交时误报 dataId 重复的问题，恢复后继续执行同一轮工作流。
```

示例只说明排版与归并方式，不作为任一版本的事实来源。编号在每个章节内连续，排序、合并后重新编号。

## 4. 中文完成后调用 doc-i18n

先完成中文内容的事实复核、归并、分类与排序，再加载并执行 `$doc-i18n`，明确只翻译本版本的中文页面和必要导航。

- 使用当前 FastGPT 仓库内 `.agents/skills/doc/i18n/SKILL.md`；若路径变动，通过仓库技能目录定位同名 Skill，不复制另一套翻译规则。无法找到时完成并保留中文，向用户说明缺少翻译依赖，不冒充已执行该 Skill。
- 按该 Skill 读取共享翻译规范与术语库，再更新对应 `.en.mdx`；英文保留中文章节、分类、条目归并关系及重要性排序，行文采用自然英文。
- 同步检查 `meta.json` / `meta.en.json`，保持页面引用一致；核对英文站内链接的 `/en/` 前缀及目标页面。
- 中文后续发生实质修改时，再同步对应英文，避免两版事实、范围或条目数量漂移。

## 5. 验证与交付

- 对照固定的比较范围及人工编辑基线复核：人工排除的内容未被补回，改写、精简与合并未被撤销，其余重要变化无遗漏，无未经证实内容；同类改动已归并，领域成组，重要在前，每条一个领域标签，章节编号连续，人工定稿顺序优先。
