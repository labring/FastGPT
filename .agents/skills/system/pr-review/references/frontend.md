# 前端组件与性能

用于 React 组件、hook、状态、表单、样式和列表改动。跨端类型与 i18n 规则统一见 [工程与类型](engineering.md)。

## 组件与交互一致性

- 使用函数式组件和 Hooks，组件职责及弹窗、表单、列表布局与同模块一致；Props 类型的安全性按工程与类型参考核对。
- 本地状态、全局 Zustand store、react-hook-form 表单状态及复杂状态逻辑的组织，应结合已有用法和状态归属判断；不因改动较小就强行更换状态管理方式。
- 样式优先使用 Chakra UI props 和断点，自定义主题样式沿用 `styles/theme.ts`；避免无理由改为内联 style，同时保留虚拟列表定位等必要的库接口用法。
- 列表 key 应稳定且对应实际项，避免状态或复用关系因排序、插入、删除而错配。

## 渲染、引用与计算成本

- 对复杂列表、图表、编辑器等有实际重复渲染成本的组件，结合触发状态和 props 判断是否需要 `React.memo`；不把缺少 memo 本身当成缺陷。
- 对象/函数引用影响 memo 子组件或 effect 等依赖时，检查引用稳定性及依赖是否正确；普通 props 不一律要求 useMemo/useCallback。
- 父回调使用 useCallback 后，若仍在 map 中传 `() => handleClick(item.id)`，子组件拿到的函数仍会变化。确需稳定引用时，可传 itemId 与稳定回调，由子组件处理点击；无需为此机械重构所有列表。
- 排序、筛选或其他计算是否需要 useMemo，依据输入规模、计算成本及重复频率判断，不能只凭数组条数或出现数组方法就要求缓存。
- 大列表按同时渲染的节点数、单项复杂度和实际交互成本评估虚拟化，不使用统一条数作为必须优化的门槛。

性能发现应说明具体状态变化、重复工作或交互影响，并区分实测与推理；不能用缺少缓存 API 代替性能证据。
