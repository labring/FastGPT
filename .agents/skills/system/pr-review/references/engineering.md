# 工程与类型

适用于模块、依赖、TypeScript、API/schema 和 i18n 改动。规则原文以 [代码规范](../../../../code/syntax.md)（分层架构、目录结构、禁止 re-export、类型推导、Zod Schema 与 OpenAPI 风格、可选 session）和根 `AGENTS.md`「API 路由」为准，此处只列审查时需要追踪的边界与使用方。

## 模块与依赖

- 核实 schema、entity、service、纯工具及上层协调的真实职责，避免业务规则混入数据访问或 UI/API 胶水代码。
- 依赖方向：前端不能引入服务端模块；`projects/app` 服务端可用全部 packages，但不能据此放宽客户端边界；sandbox、mcp_server 等独立项目避免引入无关依赖。
- 新代码按 [分层架构](../../../../code/syntax.md#分层架构) 核对：原子层和实例业务层是否 import 了其他实例，跨实例能力是否由上层以函数注入，是否新增了只做透传的编排层。按真实职责和依赖方向判断，不因文件名就判错；存量代码未被本次改动加重时不要求迁移。
- 公共逻辑按业务归属和复用需求放置；只有通用基础能力适合下沉 common。
- 移动定义时核对全部使用方，不留下转发层；写操作的 session 是否沿调用链透传到实际写入。

## 接口与类型契约

- 检查 any、过宽 object/{}、双重断言或无根据的 `as` 是否绕过真实约束；未知外部数据用 unknown，通过 schema 或类型守卫收窄。
- 非空断言要追到上游校验或明确不变量，不能仅凭注释认定非空。
- 每个新的信任边界（HTTP 入参、队列消息、模型/工具输出）都要有运行时校验；可信内部数据不要求每层重复解析。
- 按客户端实际传参核对兼容解析、字段元信息及响应结构；对外契约的向后兼容按主 skill「兼容性与升级」判断。
- 若仓库已将静态 OpenAPI 文档或翻译产物改为手工维护（无 CI 门禁），不因常规业务 PR 未附带生成产物而判定违规。
- 请求校验错误的处理边界见 [Zod 请求入参错误处理设计](../../../../design/api/zod-request-parse-error-handling.md)。

## 国际化

- 用户可见文本使用 t，服务端使用 i18nT；key 带命名空间，动态文本通过插值传参，并检查各语言包完整。
- 调用处必须保留静态字面量 key，例如 `t('ns:literal_key')`；不要使用 ``t(`ns:key_${value}`)``、`t(prefix + value)`、`t(variableKey)` 或 `t(condition ? 'ns:a' : 'ns:b')`，避免清理脚本误删和运行时裸显 key。
- 有限枚举通过显式分支或静态映射组织，最终翻译调用仍须使用字面量 key。
