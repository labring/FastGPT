# 方案设计审查

每次审查必读（纯文档、纯依赖升级等无行为变化的 PR 只核对第 3 步中适用项）。目标不是挑出与审查者偏好不同的写法，而是判断方案能否长期、正确、低成本地承载需求，并让作者理解背后的设计原则。

本文负责**模块级与跨模块**的设计判断：职责归属、分层依赖、数据与状态、契约、失败语义和演进成本。函数与文件级的实现质量见 [代码质量审查](code-quality.md)，修复类是否命中根因见 [根因修复规范](../../../../code/root-cause-fix.md)，规则原文以 [代码规范](../../../../code/syntax.md) 为准，此处不复制。

## 1. 先建立问题模型

阅读 PR 实现细节前，只依据需求说明、旧代码（`git show $MERGE_BASE:<path>`）和同类实现写下问题模型，避免被 PR 的写法锚定：

| 要素 | 需要回答 |
| --- | --- |
| 业务概念与归属 | 涉及哪些实例（拥有独立 `schema.ts` 的业务对象），每条新规则天然属于哪个实例或用例 |
| 权威数据与派生数据 | 哪份数据是唯一可写来源，哪些是缓存、快照或可推导结果，谁负责保持同步 |
| 不变量 | 变更后必须始终成立的约束，例如"版本号单调递增""计费与实际消耗一致""删除后不残留引用" |
| 入口与消费者 | 所有会触发该行为的入口（页面、API、worker、workflow、迁移、导入）和读取结果的消费者 |
| 规模与频率 | 数据量级、调用频率、是否在请求热路径或长任务中 |
| 变化轴 | 结合需求、同类模块的演进史（`git log`）判断哪些规则最可能继续变化、由谁变化 |

## 2. 独立推导参考方案

基于问题模型，用 `rg` 查找仓库中解决同类问题的现有实现，再写出审查者会采用的参考方案：逻辑放在哪一层、数据如何流动、对外契约是什么、失败时如何收尾。至少同时考虑：

- **复用现有能力**：现有函数、schema、组件或流程能否直接满足需求。
- **更简单的方案**：更少的层、状态、参数或配置能否达到相同效果。
- **在根因层修改**：问题是否应由更上游的契约或状态来源消除。

参考方案只用于发现差异，不要求 PR 与之一致。

## 3. 对照评估

逐项对比 PR 方案与参考方案，只记录有实质差异的项：

| 维度 | 检查要点 |
| --- | --- |
| 归属与分层 | 逻辑是否位于业务归属层；是否符合[分层架构](../../../../code/syntax.md#分层架构)的依赖方向和[函数注入](../../../../code/syntax.md#跨实例依赖通过函数注入)；业务规则是否混入 API、UI 或数据访问层 |
| 内聚与耦合 | 一个模块是否只有一个变化原因；同一业务规则是否只有一个来源；新增依赖是否让无关模块必须一起修改；跨仓库（main/pro）、前后端的边界是否清晰 |
| 数据与状态 | 是否引入第二份可写来源或需要手动同步的派生状态；写入路径是否收敛；事务边界是否由发起组合的层负责，`session` 是否透传到实际写入 |
| 契约与边界 | 输入输出、默认值和可选字段在源头定义；信任边界有运行时校验；错误语义（业务拒绝 / 系统故障）明确；对外契约变化可兼容 |
| 失败与并发 | 多步流程的顺序、幂等、重试、部分失败和副作用清理是否保证不变量；并发写是否有冲突控制 |
| 演进成本 | 以变化轴上**已有证据**的下一个合理需求为例，推演需要修改几处、是否要同步多处；不为没有证据的未来需求要求扩展点 |
| 简单性 | 删除测试：去掉某个层、状态、参数、配置或抽象后是否丢失能力；只有一个实现的策略/工厂、只做透传的编排层、只为单一调用方存在的通用配置都要说明理由 |
| 可测试性 | 核心业务规则能否在不 mock 大量依赖的情况下单独验证；纯计算是否与 IO 分离 |
| 规模匹配 | 算法、查询和资源占用是否匹配第 1 步的规模，细节见 [数据与性能](data-performance.md) |

## 4. 判定

把每个差异归为以下一类：

| 类型 | 判定 | 级别 |
| --- | --- | --- |
| 方案缺陷 | 不变量可被真实路径破坏；需求内入口未覆盖；同一规则多源维护；违反分层或依赖规则；失败后数据不一致；复杂度明显超出问题所需且可指出能删除的部分 | 必须修复 |
| 有更优方案 | PR 方案没有缺陷，但存在更简单、更内聚或更易测试的设计，且收益能具体说明 | 非阻塞建议 |
| 等价取舍 | 两种方案各有代价且无明显优劣 | 不列为发现，必要时在"实现方案"中说明 |

"扩展性不足""不够优雅"等判断必须给出具体的变化场景或维护成本；只有偏好时不列为必须修复。不得为提高严重程度虚构触发路径。

## 5. 写给作者

方案类发现按以下结构写，让作者能把原则迁移到下一次设计：

1. **原则**：违反的设计原则或规范条款（如"单一可写来源""实例业务层不 import 其他实例"）。
2. **表现**：本 PR 中的具体位置和写法。
3. **后果**：用一个真实场景说明会出什么问题或增加什么维护成本。
4. **推荐设计**：逻辑应放在哪里、数据如何流动；必要时附调用关系或不超过 15 行的代码骨架，不替作者重写完整实现。

## 常见反模式

| 反模式 | 典型表现 | 推荐方向 |
| --- | --- | --- |
| 下游补偿 | 调用方或读取端兜底换算、特判，源头契约未修正 | 收紧源头契约，读取边界只做有期限的历史兼容 |
| 规则散落 | 同一判断在 API、前端、worker 各写一份 | 由归属层统一维护规则，API 和 worker 调用该业务能力，前端通过接口使用服务端结果 |
| 跨实例直连 | `service.ts` 直接 import 其他实例的 entity/service | 由编排层组合，或以最小函数签名注入 |
| 透传层 | 新增只转发参数的 orchestration/helper | 上层直接调用已有能力 |
| 布尔参数分叉 | 为复用给函数加 `isXxx` 标志，内部按标志走两套逻辑 | 拆成两个职责明确的函数，共享真正相同的部分 |
| 状态镜像 | 冗余字段或前端 state 复制权威数据并靠代码同步 | 读时推导，或明确唯一写入入口 |
| 投机抽象 | 只有一个实现的策略、工厂、插件化配置 | 先写直接实现，出现第二个真实场景再抽象 |
| IO 与规则交织 | 查询、计算、写入混在一个大函数中，无法单测规则 | 抽出纯函数承载规则，外层只编排 IO |
