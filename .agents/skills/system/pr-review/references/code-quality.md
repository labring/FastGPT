# 重复、冗余与可维护性审查

每次审查必读。质量问题不以运行时失败为前提，但必须有可核对的代码证据和具体维护影响。本文件提供检查方法；现行规则以适用的 `AGENTS.md` 和 [代码规范](../../../../code/syntax.md) 为准，不在这里复制一套规范。

## 从需求和已有能力建立对照

对本次新增、修改或复制的实现按业务职责归组，先说明每组必须保留的输入输出、状态变化、权限、错误和兼容约定，再检查实现是否需要这么多代码和维护点。

1. 用 `rg` 搜索行为名称、关键字段、错误码、schema 和调用入口；先查所属业务域及共享包，沿引用扩展到相关主仓库/pro 路径。不同命名也可能表达同一规则，不能只搜新函数名。
2. 阅读候选定义、调用方和旧版本；比较默认值、空值、异常、副作用、权限/信任边界、事务和运行环境，确认现有能力能否满足本次契约。
3. 记录检索范围、实际候选及其适用或不适用的原因。未搜到候选时如实描述范围，不据此断言全仓库没有重复。
4. 对确认的问题给出最小修正方向：直接复用、删除无效层、合并同一规则来源、局部提取或恢复正确的业务归属。不得以“去重”为理由要求无关模块重构。

## 必查内容与证据

| 方向 | 重点检查 | 成立前需要核实 |
| --- | --- | --- |
| 业务逻辑重复 | 复制现有工具/组件/hook；多个分支重复拼装、过滤或状态转换；main/pro 重复同一规则 | 两处完整定义与调用链；相同业务语义；复用后依赖方向和环境合法；同一规则调整为何需要同步多处 |
| 契约重复 | 已有业务 schema 又手写同构 schema/type；同一枚举、默认值或字段映射多处维护；无意义 schema alias | 是否属于同一契约及来源；是否可推导/组合；边界特有兼容是否需要独立 wrapper |
| 无效步骤 | 相同结果的分支、重复 parse/序列化/拷贝、重复 catch/log、传参和返回值原样转发的包装 | 是否增加校验、转换、隔离、上下文或错误策略；删除后是否改变异常、副作用、顺序、对象身份或可变性 |
| 多余状态与遗留 | 可直接派生的状态却通过 effect 同步；变更后遗留的变量、参数、文件、旧路径或兼容分支 | 全部消费者、注册表、动态入口和旧数据来源；派生状态是否实际保存了快照、用户草稿或异步生命周期 |
| 抽象与职责 | 多层转发、单一场景提前引入策略/工厂/通用配置；为复用而叠加布尔参数；UI/API 内复制业务规则；helper 作用域过大 | 当前真实使用场景；新增抽象解决什么问题；简化后能否保留合理测试接缝、职责边界与可读性 |
| 测试与文档 | 相同输入路径和断言重复测试；断言复制实现；mock 掉被测行为；同一规则复制到多份文档形成独立维护源 | 用例是否验证不同边界或集成关系；重复内容是否为必要的独立预期、生成产物、多语言内容或面向不同读者的说明 |

行数、相似度、函数个数只能用于定位候选，不能单独作为发现。较长但职责一致的流程不必拆成碎片；简短但复制关键业务规则的实现仍可能必须修复。只有一个调用方也不意味着抽象必然多余，需核对它是否承担明确的边界职责。

## 判断是否影响通过

**必须修复**：满足主 skill 的明确规范违规条件，或同时满足以下质量证据：

- 问题由本次新增或加重，能够定位到实际实现、重复来源及消费者。
- 能指出具体成本，例如同一业务规则现在必须在两个位置同步修改、同一状态出现多份可写来源，或没有边界职责的转发层让调用链增加跳转；不必等到行为已经分叉或线上故障。
- 存在范围可控的修正方向，能说明它如何保留现有契约和必要边界，且不会引入更大的耦合；已核对可能的业务、兼容或框架约束。

**非阻塞建议**：收益有限、存在同样合理的设计取舍，或只是命名/排版等偏好且无明确规则要求。说明收益与取舍，不能因“质量问题”标签自动升级。

**待确认**：无法证明语义相同、入口不可达或边界冗余时，列出缺少的证据；关键缺口按主 skill 判断 `blocked`，普通疑问不自动阻塞。没有依据时不建议删除代码。

同一问题同时涉及功能、质量和规范时作为一个发现，合并依据并按实际影响排序，不重复计数。明确规范违规可以要求修复，但不能为了提高严重程度虚构数据损坏或安全风险。

## 防止误判的对照

| 场景 | 审查判断 |
| --- | --- |
| 新 API 将现有业务 schema 字段原样复制一份，并手写相同结构的 type；无特殊边界需求 | 即使校验和测试通过，也应指出规范违规及双重维护，建议复用 schema 并推导类型 |
| 两个入口复制同一套配额计算规则，已有可合法复用的纯函数 | 定位两处规则和现有函数，核实默认值及单位后要求复用，不必先证明计算结果已经不同 |
| 字段看似相同，但 API 接收原始输入、内部 schema 表达规范化后的数据 | 先比较转换与兼容语义，不能直接认定两份 schema 冗余 |
| 两层都有校验，但分别跨越 HTTP 和独立队列消费者的信任边界 | 分别核实输入来源，不能为去重删掉独立入口校验 |
| 新增 `export { X } from './x'`，理由只是旧代码也这样写、编译能通过 | 引用当前禁止 re-export 条款，判为必须修复，不降为个人风格建议 |
| 测试输入相似，但一个验证纯计算，另一个验证权限拒绝发生在写入之前 | 验证目标不同，保留；测试的独立预期不应复用被测实现来“去重” |
| 无关旧函数违反规范；本次没有复制、改动或加重它 | 不作为本 PR 的当前缺陷，也不要求顺带全量清理 |

最终将检查依据压缩进主报告的“代码质量”和“仓库规范与风格一致性”，详细问题只在“重要发现”展开；不要另写一份重复的质量报告。
