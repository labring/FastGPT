# 代码质量审查

每次审查必读，依次完成 A 重复与冗余、B 通用质量、C 项目规范三部分。质量问题不以运行时失败为前提，但必须有可核对的代码证据和具体维护影响。

本文聚焦**函数与文件级**实现；职责归属、分层依赖、数据流、抽象层次是否必要等模块级问题按 [方案设计审查](architecture.md) 判断。

## A. 重复与冗余

### 从需求和已有能力建立对照

对本次新增、修改或复制的实现按业务职责归组，先说明每组必须保留的输入输出、状态变化、权限、错误和兼容约定，再检查实现是否需要这么多代码和维护点。

1. 用 `rg` 搜索行为名称、关键字段、错误码、schema 和调用入口；先查所属业务域及共享包，沿引用扩展到相关主仓库/pro 路径。不同命名也可能表达同一规则，不能只搜新函数名。
2. 阅读候选定义、调用方和旧版本；比较默认值、空值、异常、副作用、权限/信任边界、事务和运行环境，确认现有能力能否满足本次契约。
3. 记录检索范围、实际候选及其适用或不适用的原因。未搜到候选时如实描述范围，不据此断言全仓库没有重复。
4. 对确认的问题给出最小修正方向：直接复用、删除无效层、合并同一规则来源、局部提取或恢复正确的业务归属。不得以“去重”为理由要求无关模块重构。

### 必查内容与证据

| 方向 | 重点检查 | 成立前需要核实 |
| --- | --- | --- |
| 业务逻辑重复 | 复制现有工具/组件/hook；多个分支重复拼装、过滤或状态转换；main/pro 重复同一规则 | 两处完整定义与调用链；相同业务语义；复用后依赖方向和环境合法；同一规则调整为何需要同步多处 |
| 契约重复 | 已有业务 schema 又手写同构 schema/type；同一枚举、默认值或字段映射多处维护；无意义 schema alias | 是否属于同一契约及来源；是否可推导/组合；边界特有兼容是否需要独立 wrapper |
| 无效步骤 | 相同结果的分支、重复 parse/序列化/拷贝、重复 catch/log、传参和返回值原样转发的包装 | 是否增加校验、转换、隔离、上下文或错误策略；删除后是否改变异常、副作用、顺序、对象身份或可变性 |
| 多余状态与遗留 | 可直接派生的状态却通过 effect 同步；变更后遗留的变量、参数、文件、旧路径或兼容分支 | 全部消费者、注册表、动态入口和旧数据来源；派生状态是否实际保存了快照、用户草稿或异步生命周期 |
| 测试与文档 | 相同输入路径和断言重复测试；断言复制实现；mock 掉被测行为；同一规则复制到多份文档形成独立维护源 | 用例是否验证不同边界或集成关系；重复内容是否为必要的独立预期、生成产物、多语言内容或面向不同读者的说明 |

行数、相似度、函数个数只能用于定位候选，不能单独作为发现。较长但职责一致的流程不必拆成碎片；简短但复制关键业务规则的实现仍可能必须修复。

## B. 通用质量

以"半年后由另一位工程师修改这段代码"为标准，检查新增和修改的代码：

| 方向 | 重点检查 | 成立前需要核实 |
| --- | --- | --- |
| 命名与表达 | 名称表达业务含义而非实现细节；数值带单位（`timeoutMs`、`sizeBytes`）；布尔量用 `is/has/should` 等可判真假的形式；同一概念全链路同名；避免无意义缩写和单字母变量 | 名称是否会让读者误解语义、单位或真假方向；与所在模块既有术语是否一致 |
| 函数设计 | 一个函数只做一件事，内部保持同一抽象层次；嵌套过深时用提前返回；参数个数按项目规范 | 拆分后是否真正降低理解成本，而不是把连续流程切成碎片 |
| 副作用与可变性 | 修改入参、共享的默认对象或模块级可变状态；函数名看起来只读却写库、发请求或改全局状态 | 调用方是否依赖原对象；副作用是否在名称、签名或注释中显式 |
| 常量与魔法值 | 业务含义的数字、字符串、状态值散落在多处 | 是否已有对应枚举或常量；只出现一次且含义自明的字面量不要求提取 |
| 控制流 | 用异常控制正常流程；`switch`/映射缺少穷尽检查导致新增枚举时静默走默认分支；条件表达式过长 | 新增枚举值时是否会被编译器或测试发现遗漏 |
| 注释与可读性 | 复杂流程、非直观约束和兼容代码缺少"为什么"的说明；注释复述代码或与实现不一致 | 注释要求按项目规范的流程分段条款核对 |
| 遗留物 | 调试日志、注释掉的代码、无负责人或无条件的 TODO、未使用的导出、参数和文件 | 全部引用方、动态入口和注册表 |
| 类型与错误 | 类型安全见 [工程与类型](engineering.md)，异常与日志见 [错误与日志](errors-logging.md) | 按对应参考的成立条件判断 |

## C. 项目规范逐条核对

项目规范条款以文档当前内容为准，不依赖记忆或本文列举：

1. 执行 `rg -n '^#{2,3} ' .agents/code/syntax.md` 列出全部条款，并读取根 `AGENTS.md` 的「开发约定」「按改动查规范」「测试」章节（如 API 路由、MongoDB 索引、测试位置）。
2. 按改动类型判定每条是否适用：例如新增 TypeScript 类型对应 `type` 与 `interface`、类型推导条款；新增数据写函数对应可选 `session` 条款；新增 API 对应 `parseApiInput` 与 OpenAPI 条款。
3. 只对本次新增或修改的代码判定 `符合 / 违反 / 不适用 / 待确认`，违反项写明文件、行号和条款锚点链接。
4. 条款本身的例外条件（如兼容、框架约束）在依据中说明。

## 判断是否影响通过

**必须修复**：满足主 skill 的明确规范违规条件，或同时满足以下质量证据：

- 问题由本次新增或加重，能够定位到实际实现、重复来源及消费者。
- 能指出具体成本，例如同一业务规则现在必须在两个位置同步修改、同一状态出现多份可写来源，或没有边界职责的转发层让调用链增加跳转；不必等到行为已经分叉或线上故障。
- 存在范围可控的修正方向，能说明它如何保留现有契约和必要边界，且不会引入更大的耦合；已核对可能的业务、兼容或框架约束。

通用质量问题中，误导性命名（名称与实际语义、单位或真假方向不符）、对入参或共享对象的隐式修改、缺少穷尽检查导致新增枚举被静默处理，在能指出具体误用场景时按上述条件列为必须修复。

**非阻塞建议**：收益有限、存在同样合理的设计取舍，或只是命名/排版等偏好且无明确规则要求。说明收益与取舍，不能因“质量问题”标签自动升级。同类建议合并为一条，避免用大量琐碎意见淹没关键问题。

**待确认**：无法证明语义相同、入口不可达或边界冗余时，列出缺少的证据；关键缺口按主 skill 判断 `blocked`，普通疑问不自动阻塞。没有依据时不建议删除代码。

## 防止误判的对照

| 场景 | 审查判断 |
| --- | --- |
| 新 API 将现有业务 schema 字段原样复制一份，并手写相同结构的 type；无特殊边界需求 | 即使校验和测试通过，也应指出规范违规及双重维护，建议复用 schema 并推导类型 |
| 两个入口复制同一套配额计算规则，已有可合法复用的纯函数 | 定位两处规则和现有函数，核实默认值及单位后要求复用，不必先证明计算结果已经不同 |
| 字段看似相同，但 API 接收原始输入、内部 schema 表达规范化后的数据 | 先比较转换与兼容语义，不能直接认定两份 schema 冗余 |
| 两层都有校验，但分别跨越 HTTP 和独立队列消费者的信任边界 | 分别核实输入来源，不能为去重删掉独立入口校验 |
| 新增 `export { X } from './x'`，理由只是旧代码也这样写、编译能通过 | 引用当前禁止 re-export 条款，判为必须修复，不降为个人风格建议 |
| 测试输入相似，但一个验证纯计算，另一个验证权限拒绝发生在写入之前 | 验证目标不同，保留；测试的独立预期不应复用被测实现来“去重” |
| 无关旧函数违反规范；本次没有复制、改动或加重它 | 不作为本 PR 的当前缺陷，也不要求顺带全量清理 |
| 函数 80 行，但按步骤分段注释、每步职责清晰 | 不因长度列为发现；只有混合多种职责或无法单测核心规则时才指出 |
| 变量名 `limit` 实际表示字节数，调用方按条数传入 | 能指出误用路径，作为误导性命名列为必须修复，建议改为 `maxBytes` 等带单位名称 |

检查依据压缩进主报告的“质量与规范”，详细问题只在“重要发现”展开，不另写一份质量报告。
