## 〇、范围变更说明与旧范围对比

### 0.1 变更摘要

- **US-11 反转**：user-story US-11 由「知识库检索不受影响」改为「召回结果按文件级权限过滤，只能检索到有查看权限的 collection 内容，防止越权检索」；user-story §5 范围内显式包含「知识库检索（RAG 检索）的召回按文件级权限过滤」；§6 NFR 新增「检索性能」「检索正确性」两项关注点。

#### 🟡 警告问题（建议修复，不阻塞但存在风险）

**[🟡-C1] [T-7 附录 vs R006 vs F014 增量方向] `authDatasetCollection` 语义是否变更的表述互相矛盾，检索回归控制策略存在分歧风险（变更引入）**

T-7 附录默认方案称「authDatasetCollection 不改变既有调用方语义，降低回归面」；而 R006 与 F014 增量方向均称「authDatasetCollection 由透传 dataset 权限改为 collection 维度解析」，R006 还将「及检索链路（FR-11）」列为 authDatasetCollection 变更的影响面。但 F014 正常路径第 1 步明确检索入口为 `authDataset`（dataset 级、不变），文件级过滤由**新增独立**「可读集合批量解析」函数承担——即检索链路本不应经 `authDatasetCollection`。三处对「authDatasetCollection 是否变更、变更是否影响检索链路」口径不一致：实现方可能对「检索入口鉴权是否走 authDatasetCollection、回归用例集该覆盖检索链路还是只覆盖 CRUD」产生分歧，直接影响 R006 所述回归控制。
→ **建议**：统一口径为「检索入口保持 `authDataset` 不变；文件级过滤由新增独立批量解析函数承担，检索链路不调用 `authDatasetCollection`；`authDatasetCollection` 升级为 collection 维度解析仅影响 F012 CRUD/详情调用方，按版本化发布 + 全量回归控制」。同步删除 R006 中「及检索链路（FR-11）」或改为「检索链路经新增独立函数解耦、不受 authDatasetCollection 变更影响」。

**[🟡-C2] [F011 / F012 边界表]「tmbId(read)+group(write)→按位 OR 叠加」与权威定义「tmbId 优先、不叠加」直接矛盾（沿用上轮 🟡-N5，未修复；变更后风险升高）**

§2.2 权威定义/通用约定：「个人 tmbId 记录优先；若不存在，取 groupId 集合与 orgId 集合记录的 `sumPer` 最大值」。**代码核实**（`packages/service/support/permission/controller.ts:49-65`）：`getTmbPermission` 命中个人 tmbId 记录（含 permission=0）即立即返回，不叠加 group/org。F002 边界亦写「tmbId 优先返回，不叠加」。但 F011 边界「用户同时命中 tmbId(read) 与 group(write) → 最终权限 = read|write」、F012 边界「命中 tmbId(read) + group(write) → read|write（按位 OR）」仍主张叠加。该矛盾现进一步波及 F014：F014 依赖 F011 的「可读集合批量解析」做检索过滤，若解析语义在 tmbId/group 上分叉，将直接影响越权/漏召回正确性；同时 F012 CRUD 路径上 tmbId=read + group=manage 按 OR 将获得 manage（潜在提权）。
→ **建议**：以权威定义与实际代码为准，将 F011/F012 边界改为「tmbId 记录存在（含 permission=0）→ 取 tmbId，不叠加 group/org；tmbId 记录不存在 → group/org 集合按位 OR 取最高」，并补负向用例「tmbId=read + group=write → 解析结果 read（非 read|write）」。

**[🟡-C3] [F003]「非 folder 传 currentOnly 报错」与「website/api 等非 folder dataset 允许设置范围字段」仍口径不清（沿用上轮 🟡-N6 软化形态）**

F003 EP-2 / 正常路径步骤 3「非 folder 传 currentOnly 报错」未限定「非 folder」指非 folder **collection** 还是包括 dataset；F003 边界表「dataset 类型为 website/api 等非 folder | 允许设置范围字段」与 user-story §4「生效范围适用对象 dataset（所有）」一致，但与 EP-2 的「非 folder 报错」仅当把「非 folder」解读为「非 folder collection」时才不矛盾。F002 输入表虽已把 currentOnly 限定到「仅 folder 类型 collection 允许」，但 F003 独立表述未同步限定，实现方可能对普通（folder 型）dataset 与 website/api（叶子）dataset 产生不同处理。
→ **建议**：全文统一为「currentOnly 适用于所有 dataset 类型（无 folder 子树时仅设置范围字段、不产生传播）；仅非 folder collection 传 currentOnly 报错」，同步修订 F003 EP-2 与正常路径步骤 3 措辞，并在 T-2 中补一句「非 folder collection 与叶子 dataset 的区分」说明。

**[🟡-C4] [F014 边界 / NFR-7 vs NFR-8] 性能缓存/短路与「无陈旧缓存导致越权召回」的失效机制未绑定权限写事务（变更引入）**

F014 边界「高并发检索（单 API 100 QPS）→ 解析批量 `$in` + 缓存/短路」与 NFR-7「缓存/短路」明确以缓存支撑热路径；NFR-8 同时要求「权限变更后立即重发检索，读取最新权限，无陈旧缓存导致越权召回」，F014 边界亦写「读取最新权限」。文档未说明缓存/短路的失效时机——若实现方采用纯 TTL 缓存，权限收紧后 TTL 窗口内仍可能返回已无权 collection 内容，构成越权召回（安全违反，直接违背 NFR-8）。「读取最新权限」与「缓存」两条要求需一个明确的失效信号才能同时满足。
→ **建议**：显式约束「可读集合解析结果（含短路判定）的缓存必须以权限写事务提交为失效信号（写后立即失效），不得以纯 TTL 作为唯一失效手段」，写入 F014 边界或 NFR-8。

#### 🔵 建议项（可选优化）

**[🔵-B1] [F014 EP-2]** fail-closed 降级给出「按最小可读集合（空集）处理该次召回」与「拒绝该次召回」两个可选项，未择一（F001/F011 边界统一为「空集」，EP-2 多出「拒绝」选项）。建议统一为「按空集处理，返回空召回」，避免实现差异。

**[🔵-B2] [F014 / NFR-7]** 「全继承态 dataset 走短路路径（可读集合 = 全量候选，近似零额外开销）」的「全继承态」判定机制未定义。若判定为每请求实时查询（是否存在 `inheritPermission=false` 或 `permissionEffectScope=currentOnly`，恒定为常数查询）则安全；若实现方以陈旧标志位判定短路，权限收紧后可能产生越权召回。建议显式说明判定方式并声明其为常数查询。
