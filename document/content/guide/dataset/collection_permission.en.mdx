Collection-level permissions are a commercial capability. They control individual files and folders within a knowledge base. Access requires both knowledge base read permission and the applicable collection permission.

## Permission Inheritance

With collection permissions disabled, files and folders use knowledge base permissions. Enabling the feature materializes permission snapshots for existing collections. Inheriting collections follow their parent; independently configured collections retain their own permissions.

![Enable collection permissions](/imgs/optimized/current/collection-permission-enable.png.webp)

## Step 1: Enable Collection Permissions

1. As a knowledge base administrator, open the target collection's action menu and select "Permissions".
2. Confirm enabling collection permissions for the knowledge base. Snapshot creation can take time for large libraries.
3. After initialization succeeds, open the collection's collaborator settings.

The knowledge base information panel provides a disable action. Disabling deletes every collection collaborator configuration in that knowledge base and restores knowledge base inheritance. Record required grants before confirming; enabling again creates fresh inherited snapshots.

## Step 2: Configure Collaborators

Choose members, groups, or organizations and assign roles:

| Role | Scope |
|---|---|
| Read | View collection content |
| Write | Update content, synchronize, and adjust processing parameters |
| Administrator | Manage collection settings and collaborators |
| Creator | Own the collection; deletion and ownership transfer require this role |

Collaborator updates replace the submitted list in full. Preserve the existing creator entry. Modifying inherited grants may require confirming a switch to independent permissions. Restoring inheritance retains grants unique to that collection and synchronizes its subtree.

![Configure file and folder collaborators](/imgs/optimized/current/collection-collaborators.png.webp)

## Step 3: Verify Retrieval Identity and File Access

1. **Member-authenticated retrieval**: Search tests and application search configured to authenticate the current member compute readable collections and intersect them with metadata filters.
2. **Application-selected knowledge**: A workflow using preselected knowledge bases with `authTmbId: false` follows application access settings and skips member-specific collection filtering. Configure member authentication and a trusted identity mapping when enforcing per-user document access.
3. **Special identities**: Team owners and authorized system-root operations have elevated access. Team administrators still follow resource collaborator permissions.
4. **Source file links**: Download and preview links use the storage service's authorization and signing rules. Signed links can grant access to their holders until expiry; handle them as sensitive credentials.

## Acceptance Checklist

- [ ] Test both an authorized member and a restricted member against the same source document.
- [ ] Verify write, collaborator-management, deletion, and ownership-transfer controls separately.
- [ ] Test published channels and API calls using their actual execution identities.
- [ ] Confirm that returned citations, file links, and previous conversation history meet the intended disclosure scope.
