Collection tags classify material and constrain retrieval. You need knowledge-base management or appropriate write permission. Commercial-license and SaaS-plan availability follow your environment. The condition-row procedure applies to deployments providing the current tag-filter interface.

## Basic tag operations

Open tag management in knowledge-base details, create a tag with a type, and assign values to collections. The current interface supports number, date, and multiple-choice types; compatibility logic handles historical string tags. Renaming, deleting, or reassigning tags can affect retrieval conditions, so test after changes.

## Collection filtering in knowledge search

Open collection filtering in knowledge-search configuration and add a condition row: choose a tag or supported field, an operator, a value source, and a comparison value. Combine conditions using AND or OR. Variable references must resolve to values compatible with the tag type at runtime.

Example: create a multiple-choice Department tag and assign Finance and Support to two collections. Add a condition that Department contains Finance and test a finance question. Expect results from the Finance scope. Switch to Support and verify that the scope changes.

For empty results, inspect assigned values, operator, AND/OR, resolved variables, collection permissions, and processing status. Conditions constrain the search scope; source content and retrieval parameters determine matches within it.

## Legacy JSON conditions

Older configurations may contain JSON fields such as `tags` and `createTime`; historical `tags` used `$and` or `$or`. Read retained workflows according to their filter version. After migrating to condition rows, save and compare the retrieval scope. Current conditions use `logic` and `conditions`; API integrations must follow the generated contract of the selected interface.
