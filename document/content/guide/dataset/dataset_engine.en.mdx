## Search modes

| Mode | Input and effect | Useful questions | Conditions |
| --- | --- | --- | --- |
| Semantic search | Embeds the query to retrieve semantically related chunks | Natural language and paraphrases; cross-language results depend on the model | Available vector indexes and embedding model |
| Full-text search | Retrieves candidates through term matching | Identifiers, model numbers, specialized terms | Completed full-text indexes; matching depends on the deployment backend |
| Hybrid search | Fuses semantic and full-text candidates with an adjustable semantic weight | Questions combining meaning and keywords | Both paths available; compare with fixed questions |

### Result reranking

Reranking is a toggle that requires an available rerank model. It scores retrieved text candidates again and contributes to result fusion. Results depend on candidate coverage, the question, and the model. Missing material must first be included in retrieval.

If the rerank call fails, text results fall back to the original retrieved list and this run reports reranking as unused. Inspect errors, run details, and results exposed by the interface. If actual usage status is missing, ask an administrator to inspect the model call. The toggle expresses the requested configuration; actual execution determines threshold behavior.

### Search filters

#### Citation limit

A **token** budget controls returned citation content. Fusion, deduplication, and applicable threshold filtering happen before budget trimming. Whole-chunk retention includes the last chunk that crosses the budget, so actual content can exceed the configured limit. Reserve room for the system prompt, message history, and answer, and check the model's context limit.

A larger budget may retain more clauses while increasing context use and distraction. Use [fixed questions](/en/guide/dataset/test-retrieval) to check that required conditions survive.

#### Minimum relevance

A numeric setting from **0 to 1**. Filtering depends on the scores actually available in this run:

| Actual execution | Threshold basis |
| --- | --- |
| Text reranking succeeds and is used | Rerank scores |
| Pure semantic search with reranking unused | Vector scores |
| Full-text or hybrid search with reranking unused | Results may be returned without threshold filtering |

Candidates lacking the target score are retained, so inspect their text. In hybrid search, a rerank-service failure may change both ordering and threshold applicability. Confirm the effective conditions before comparing thresholds. Raising the threshold can also remove useful clauses.

## Query rewriting

Query rewriting is an optional model step that uses the configured message history to resolve references and expand a query. “Which documents do I need for that?” requires the preceding reimbursement topic. It adds a model call and latency; its model and history scope follow the Application configuration.

When run details expose the rewritten query, check its subject, identifiers, and dates. Test complete single-turn questions, exact identifiers, and follow-ups separately, then retain settings that meet coverage and latency needs.

## Result ranking and fusion

Multiple retrieval paths contribute through reciprocal rank fusion (RRF). Reranking and image paths may also affect order. A score describes matching for its model or retrieval path, final order reflects fusion, and answer correctness requires fact and citation checks.

| Result information | What it establishes |
| --- | --- |
| Source Collection and text | Correct version and conditions needed for the answer |
| Score and score type | Matching and threshold basis for this run; assess scores separately across models |
| Result order | The position of relevant clauses in context |
| Actual usage status or errors, when exposed | Whether reranking, filtering, and relevant models ran as expected |

## Retrieval scope and indexes

Scope depends on selected Knowledge bases, enabled Collections, tag filters, and applicable readable-Collection permissions. See [Collection tags](/en/guide/dataset/collection_tags) and [Collection permissions](/en/guide/dataset/collection_permission).

A Data chunk can have multiple search indexes. Supplementary indexes help different questions find the same text; the text must still contain the complete evidence for the answer. See [Update material](/en/guide/dataset/update-data).

## Image search method

Image-description search requires an available vision model and corresponding description indexes. Image-vector search requires an embedding model that accepts images and completed image-vector indexes. Combined text-image queries use available paths; results depend on imported content, model capabilities, and the query.

For weak image matching, check image clarity, completed indexes, and model support, then compare image-only and combined input. See [RAG fundamentals](/en/guide/dataset/rag).

## Common tuning tips

Check processing and scope first, then adjust search mode, query rewriting, reranking, effective thresholds, and citation budget one at a time. Use the checklist in [Test retrieval](/en/guide/dataset/test-retrieval) and recovery steps in [troubleshooting](/en/guide/dataset/faq).
