## Graph Dispatch Engine Mechanics

Workflows initiate execution from the "Workflow Start" node. The scheduler drives graph traversal based on in-edge dependencies:

```
[Workflow Start] ──(active)──► [Intent Classifier] ──(active)──► [Knowledge Search] ──(active)──► [AI Chat Generation]
                                      │
                                      └──(skipped)────────► [Ticket Form] ──(cascading skipped)──► [Ticket Response]
```

### 1. In-Edge Grouping Readiness Evaluation
The scheduler evaluates node execution conditions against incoming edges:
- **Execution Ready**: When all predecessor edges in a dependency group complete waiting and at least one edge is `active`, the node joins the ready queue and begins execution immediately.
- **Concurrent Dispatch**: Independent nodes that reach readiness simultaneously execute concurrently, maximizing I/O efficiency.

### 2. The Three-State Edge Model
Every edge on the canvas assumes one of three discrete states during execution:

| Edge State | Meaning and System Behavior |
| --- | --- |
| `waiting` | Initial pending state. Upstream predecessor nodes have not finished executing; downstream nodes wait. |
| `active` | Activated state. Upstream nodes executed successfully and met branch criteria; downstream nodes are triggered. |
| `skipped` | Skipped state. Upstream conditional branches omitted this route, propagating skips downstream. |

### 3. Skip Propagation Mechanics
When upstream nodes (such as Condition Switch or Question Classifier) activate a single route, unselected output edges are marked `skipped`. The scheduling engine cascades `skipped` markers downstream. Any node whose in-edges are all marked `skipped` skips its own execution cleanly, eliminating hanging deadlocks.

## Exception Branches and Circuit Breakers

To maintain workflow resilience against upstream service degradation, the platform provides explicit exception paths:

1. **Explicit Exception Outlets**: For nodes equipped with exception ports (such as HTTP Request or Code Sandbox), execution errors or timeouts trigger the exception edge immediately, skipping standard business outputs and routing error diagnostics to fallback nodes.
2. **Default Error Interception**: When nodes lacking exception outlets encounter errors, the system skips downstream edges automatically while recording execution traces, allowing parallel branches to finalize cleanly.
3. **Execution Step Quotas**: To guard against infinite loops, each request enforces a maximum step limit. Upon reaching this quota, the scheduler halts further node execution and records the termination in the execution result.

## Interactive Checkpoints

FastGPT supports human-in-the-loop interactions and state checkpoints during workflow runs:

```
[Upstream Execution] ──► [User Selection / Form Input] ──► (Workflow Suspends & Saves Checkpoint)
                                                                 │
                                                                 ▼ (Awaits User Input)
[Next Turn Resumes]  ◄── [Load Checkpoint & Restore] ◄───────────┘
```

1. **Execution Suspension**: When reaching a "User Selection" or "Form Input" node, the system returns the interactive payload to the client, while persisting conversation context, pending edges, and variable snapshots into an operational checkpoint.
2. **State Restoration**: When the user submits their selection or form in chat, the next request loads the checkpoint, reconstructing the execution context and driving downstream nodes to completion.
3. **Cooperative Cancellation**: When users click "Stop" during streamed responses, the system writes a cancellation flag. The scheduler exits cooperatively at the next scheduling cycle and persists all generated records.

## Orchestration Best Practices

1. **Left-to-Right Layout**: Structure pipelines to flow naturally from "Workflow Start" on the left toward response nodes on the right.
2. **Single-Exit Aggregation**: Use a "Specified Response" node to govern final message presentation, avoiding fragmented outputs from scattered nodes.
3. **Standard Variable Naming**: Define clean identifiers in start nodes and global settings to support reliable downstream variable referencing.
