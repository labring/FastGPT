Complex workflows combine multiple model calls, external HTTP requests, code sandboxes, and nested containers. Before publishing, use canvas debugging, error-capture branches, and version snapshots to verify behavior and add fallback paths.

## 1. Canvas Debugging and Node Run Details

1. **Start a debug run**: Click **Run** in the top-right corner of the workflow editor to open the debug preview drawer. Fill in any pre-chat global variables and send a test message.
2. **Live execution status**: Active nodes highlight on the canvas as they execute. When execution reaches a [User Selection](/en/guide/build/workflow/nodes/user-selection) or [Form Input](/en/guide/build/workflow/nodes/form_input) node, the workflow enters interactive suspension until you submit the control in the preview pane.
3. **Inspect node inputs and outputs**: After the run completes, open **Full Response (Run Details)** below the message and inspect each executed node in order:
   - **Inputs**: Resolved prompts, variable values, retrieval filters, and request payloads.
   - **Outputs**: Model responses, retrieved chunk counts, extracted fields, script return values, or error strings.
   - **Latency and usage**: Execution duration (ms) and token/point consumption per node.

## 2. Error-Capture Branches (Error Handling)

Nodes that interact with external services or execute dynamic code expose error outputs and failure branches so a single node error does not abort the entire workflow:

### Nodes with Error Capture

| Node Type | Error Output Field | Common Trigger Conditions |
| --- | --- | --- |
| **HTTP Request** (`httpRequest468`) | `Error message` (`error` / `system_httpRawError`) | Request timeout, connection failure, or non-2xx HTTP status |
| **Code Run** (`code`) | `Error message` (`error`) | JS/Python syntax error, runtime exception, or sandbox timeout |
| **AI Chat / Agent / Question Classify / Content Extract** | `Error message` | Model rate limit (429), context overflow, or invalid provider credentials |
| **Document Parsing** (`readFiles`) | `Error message` | Unreachable, expired, or corrupted file URL |
| **Parallel Run** (`parallelRun`) | `parallelStatus` / `parallelFullResults` | Partial or total task failure (`partial_success` or `failed`) |

### Build a Fallback Path

1. Connect the node's normal **Success** handle to your primary processing branch.
2. Connect the **Failed (Error)** handle to a fallback branch (such as a backup model, a [Specified Reply](/en/guide/build/workflow/nodes/reply) node with a recovery message, or an alerting step).
3. Reference the upstream `Error message` output in the fallback branch to log diagnostic context or guide the user.

## 3. Auto-Saved Drafts and Version Rollback

1. **Draft vs. published isolation**: Canvas edits, connections, and parameter changes are auto-saved to your working draft and used during editor debug runs, while live share links, portal sessions, and API calls continue using the active published version.
2. **Publish a snapshot**: Click **Save and Publish** in the top-right corner and enter a version note to create an immutable published snapshot.
3. **Inspect and roll back versions**: Open the **Version History** drawer to review saved and published snapshots. Select an earlier snapshot to restore it to the editor draft, then click **Publish** to roll back live traffic.

## Troubleshooting Checklist

| Symptom | Where to Check |
| --- | --- |
| Downstream node is skipped after a branch | Check incoming-edge readiness and skip propagation in [Workflow Core Mechanics](/en/guide/build/workflow/intro) |
| Connection handle refuses a wire | Check ordinary vs. tool connections and container boundaries in [Workflow Connection Rules](/en/guide/build/workflow/rules) |
| Live users hit errors while editor debug succeeds | Inspect real user inputs, file link expiration, and version differences in [Conversation Logs](/en/guide/build/logs) |
