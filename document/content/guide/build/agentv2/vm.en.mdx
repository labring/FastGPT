The Virtual Machine (VM) provides Chat Agent V2 with an isolated code execution sandbox, persistent file I/O, and runtime dependency management.

## What is a Virtual Machine

When analyzing complex spreadsheets, performing mathematical computations, rendering dynamic charts, or executing Skills, agents require a genuine operational runtime. The virtual machine provides an isolated containerized environment (e.g., Python 3.11, Node.js 20), allowing agents to write and run scripts, handle errors, and generate downloadable file assets.

Virtual machine execution relies on backend sandbox services (such as OpenSandbox or Sealos Devbox). Self-hosted operators must configure sandboxes according to the [Deployment Guide](/en/self-host).

---

## Architecture and Directory Layout

The platform isolates virtual machine files by tenant, application, and session identifiers:

```
<workspaceRoot>/
  ├── sessions/
  │     └── <chatId>/             # Session-specific directory isolating uploaded and generated files
  └── projects/
        └── <versionId>/          # Shared directory mounting published Skill version bundles
```

- **Session-Level Isolation**: Each conversation uses a dedicated workspace path `sessions/<chatId>`, where user-uploaded files mount automatically.
- **Automatic Dialog File Injection**: Files uploaded in the chat input box are automatically synchronized into the session workspace's `user_files/` directory before execution begins, allowing the Agent to read and process them via local paths.
- **State Persistence and Reset**: The same `chatId` reuses its session directory. Sandbox instances are scoped by source, application, and user. Restarting a chat changes its context and directory; sandbox lifecycle policies govern instance recycling and volume retention.
- **Security Isolation and Command Encoding**: Containers enforce CPU, memory, disk I/O, and network boundaries, and all executed commands are Base64-encoded before decoding inside the container to prevent shell injection.

## Virtual Machine Lifecycle

During environment initialization and execution, the platform manages the sandbox through discrete phases:

![Agent sandbox initialization](/imgs/diagrams/sandbox-initialization.en.light.svg)

### Startup Scripts and Dependency Management
The application "Startup Script" runs after runtime acquisition, the initialization lock, and configuration and file preparation. It can install Python packages (e.g., `pip install matplotlib pandas`) or system binaries:
- **Two-Stage Execution Order and Atomic Deployment**:
  1. **Application Startup Script**: Runs first inside the virtual machine workspace directory (such as `/workspace`) using the shell commands configured in the application panel.
  2. **Skill Entrypoint Script**: When published Skills are attached, each Skill bundle extracts into a temporary staging directory (`.tmp-<versionId>-<random>`) and atomically swaps into `projects/<versionId>` upon completion, after which its initialization script (such as `entrypoint.sh`) executes inside that Skill's directory.
- **Dual-Key State Deduplication (`~/.fastgpt/runtime/state.json`)**:
  - **Application Startup Script (SHA-256 Hash Deduplication)**: The runtime computes the SHA-256 hash of the startup script text and compares it against `~/.fastgpt/runtime/state.json`. Subsequent warm turns skip execution when the hash matches, and re-run automatically when the script text changes or the sandbox is rebuilt.
  - **Skill Entrypoint Script (Version ID Deduplication)**: Skill entrypoints deduplicate by immutable **Skill Version ID**, ensuring each published Skill version initializes once per sandbox instance lifecycle.

<span id="execution-constraints--fault-tolerance" />

### Execution Constraints and Fault Tolerance

- **Preparation Failures**: Runtime acquisition or initialization lock failures return an error for the current preparation. Skill editor debugging uses a separate preparation branch.
- **Startup Timeout Protection**: Script execution duration is bounded by the `AGENT_SANDBOX_ENTRYPOINT_TIMEOUT_SECONDS` environment variable (defaults to 30 seconds; configurable from 1 to 600 seconds).
- **Non-blocking Resilience**: Non-zero exit codes or timeouts during script execution log warnings without crashing the conversational flow, allowing builders to inspect missing dependencies in debug panels.
- **Buffer Output Limits**: Output limits depend on the execution service. Logs may be truncated; write large results to files and inspect the generated artifacts.

## Sandbox Debugging and File Manager

1. **Real-Time Status Tracking**: In the preview drawer, the interface visualizes container readiness (provisioning, executing startup scripts, and ready states).
2. **Virtual Machine File Manager**: Click "View VM Files" in the upper right corner of the debug drawer to browse files, preview images (such as `revenue.png`), or download generated datasets (such as `channel_summary.csv`).
3. **Diagnostics**: When scripts fail with missing module errors, inspect the startup script logs and return codes to verify that dependencies installed successfully.
