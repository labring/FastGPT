---
title: Integrate knowledge ingestion and retrieval
description: Use generated API contracts for import, processing checks, retrieval testing, and application association.
---

Prepare a team-level API key and the required read/write permissions on the knowledge base. Use your deployment's `/apidoc/systemopenapi` for current fields, methods, and API-key availability. [API getting started](/en/openapi/intro) lists cloud reference addresses.

## Objects and identifiers

`datasetId` identifies a knowledge base and `collectionId` a collection. Content collections hold chunks; folder collections organize other collections. Chunks have retrieval indexes. The interface URL helps locate a resource; submit its identifier in the field specified by the selected operation.

## Build an ingestion path

1. Find knowledge-base creation or existing-base lookup in the generated reference. Verify creation permissions, type, and model configuration.
2. Choose a collection-creation operation for files, text, URLs, or external sources. Verify its format and processing settings.
3. Retain returned knowledge-base and collection identifiers. Use the corresponding query operation to inspect processing status and failures.
4. Once processing completes, submit a question with a known answer to the search-test operation. Inspect returned text and collection origin.
5. Associate the knowledge base with an application and follow [application integration](/en/openapi/app) to verify retrieval through to an answer.

Reuse the material and expected answers from [your first knowledge-base Q&A](/en/guide/getting-started/knowledge-qa).

## Example: import text and retrieve it

First create a general knowledge base with an available embedding model in the interface and copy its ID. Use the origin and key from API getting started, then set `FASTGPT_DATASET_ID`. This import creates a collection and consumes processing quota; repeating it creates another collection.

```bash
export FASTGPT_DATASET_ID='YOUR_DATASET_ID'
curl --fail-with-body "$FASTGPT_ORIGIN/api/core/dataset/collection/create/text" \
  -H "Authorization: Bearer $FASTGPT_API_KEY" \
  -H 'Content-Type: application/json' \
  --data @- <<EOF
{"datasetId":"$FASTGPT_DATASET_ID","name":"Leave policy example","text":"Employees receive 12 days of annual leave."}
EOF
```

The successful response contains `data.collectionId` and `data.results.insertLen`. After import returns, confirm processing has completed in the knowledge-base interface before running retrieval. Results should contain the 12-day annual-leave passage and collection origin. For empty results, check processing state, model permissions, and the knowledge-base ID. Inspect business `code` and `message` as well as HTTP status for failures.

```bash
curl --fail-with-body "$FASTGPT_ORIGIN/api/core/dataset/searchTest" \
  -H "Authorization: Bearer $FASTGPT_API_KEY" \
  -H 'Content-Type: application/json' \
  --data @- <<EOF
{"datasetId":"$FASTGPT_DATASET_ID","text":"How many days of annual leave do employees receive?","limit":1500}
EOF
```

## Maintenance and failures

Repeated imports, deletions, and replacements change material available to applications. Verify batch operations on a small sample before processing the remainder. Distinguish upload, parsing, segmentation, embedding, and permission failures, retaining collection IDs and errors. Check tag conditions against [current filtering](/en/guide/dataset/collection_tags) and the interface version.

See [third-party knowledge sources](/en/guide/dataset/third-party/third_dataset) for synchronization contracts. [Historical knowledge-base parameters](/en/openapi/legacy/dataset) preserve old fields and examples for migration comparisons.
