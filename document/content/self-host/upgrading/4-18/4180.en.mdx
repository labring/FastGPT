## Important notes

### Deprecated configurations and features

- `SYNC_INDEX` no longer takes effect and is maintained automatically by the system.
- In-generation stream recovery parameters no longer take effect and now use fixed system settings.
- Only `OpenSandbox` is supported as the Sandbox runtime; all other Sandbox providers are removed.

### Compatibility notes

- **API Key health checks**: Due to security issues, `GET /api/support/openapi/health` now reads credentials from the `Authorization: Bearer <apiKey>` header instead of the URL’s `apiKey` parameter. Update existing health probes to send the key in this header and remove it from the URL.
- **Workflow input bindings**. The Workflow runtime resolves bindings based on which Nodes are reachable, which outputs are available, and whether the types match. If an existing Workflow depends on an unreachable Node, a disabled output, or a mismatched type, bind the input to an available upstream output of the expected type. The runtime treats the affected input as empty until you update the binding.
- **Dynamic selection options**: User selection Nodes and single- or multi-select form fields now keep only the first `200` valid variable-bound options at runtime, with each option truncated to at most `100` UTF-16 code units. Workflows that depend on longer option values or later candidates must adjust their candidate data and review downstream matching logic.
- **API identity parameters**: API sessions no longer allow switching user identity; existing sessions use their saved identity. Continue with the same `customUid`; omitting, clearing, or changing a bound value, or switching from the default to a custom identity, is rejected. Integrations that reuse a session across users must allocate separate `chatId` values for different users. A nonempty `customUid` requires an API Key. It is mutually exclusive with `authProxy`, even when empty; integrations that send both must choose one identity.
- **Session ID length**: Session management, file, citation, and Sandbox APIs now limit `chatId` to `1024` characters. Integrations that use longer custom IDs must adjust their generation rules and review existing oversized session IDs and their linked records.
- **File previews and downloads**. If your integration embeds HTML, SVG, or XML file previews, open them in a separate page. In short-link redirect mode, FastGPT serves these files through its proxy, so download clients must handle the file response directly. In short-link redirect mode, FastGPT responds to `HEAD` with file metadata. If your client reads `Location` to obtain the redirect URL, use `GET`. If your R2 deployment used `STORAGE_EXTERNAL_ENDPOINT` to override the signing endpoint, verify after upgrading that clients can reach the R2 service endpoint.
- **Download short links**. If you use a custom Nginx root-path regex rewrite with `FILE_DOWNLOAD_PUBLIC_URL_PREFIX`, update the regex before upgrading to match `v1` links and `v2` links with or without an extension. In multi-instance deployments, coordinate the App and Pro upgrades so that once new instances start issuing links, download requests go only to App instances that support `v2`. Rolling back to a version that supports only `v1` makes previously issued `v2` links unusable.
- **Log CSV exports**: Scripts that parse Team members from the “User” column must support `ID:name` instead of the previous member name; when a member has no name, the column contains only the ID. Channel columns are now split into “Call channel” and “Channel name,” so scripts that parse column names must also be updated.
- **Collection deletion API**: Select exactly one request-body form: `id`, `collectionIds`, or `datasetId + apiFileIds`. Legacy `query.id` remains supported but is deprecated; new integrations should use the request body.
- **Speech recognition usage**: Existing custom speech recognition integrations must check their upstream usage responses. Duration-based billing reads `usage.seconds`; missing or invalid values count as `0`, with no fallback to client-reported recording time or estimates from transcribed text.
- **Sealos Devbox retirement and Sandbox path changes**: Starting in 4.18.0, the `sealosdevbox` runtime and its Admin Console settings are removed. Existing deployments must first run upgrade script 8 to migrate, switch to OpenSandbox, and verify cold-recovery stability before manually running upgrade script 9’s irreversible cleanup once rollback is no longer needed. The Sandbox workspace path moves from `/workspace` to `/home/sandbox/workspace`, and initialization deduplication state moves to `/var/lib/fastgpt-runtime/state.json`. Update custom startup scripts or derived images that hardcode the legacy paths.

## Upgrade guide

**Prerequisite**: Complete the required historical migrations on 4.17.x before upgrading. Version 4.18.x removes the old task registrations and implementations, so they will no longer run; historical status and error records remain in the database.

### Deployment template changes

- **Image registry for mainland China**: FastGPT has stopped publishing images to Alibaba Cloud. The mainland China Docker Compose templates now pull FastGPT, Plugin, Code Sandbox, and Agent Sandbox service images from `ghcr.dockerproxy.net/labring/`, and `install.sh` updates the registry prompt to China Mainland / Global mirrors.
- **Default object storage changed to RustFS**: Default Docker Compose templates replace `fastgpt-minio` with `fastgpt-rustfs` (`rustfs:1.0.4`, single-disk `/data` layout, named volume `fastgpt-rustfs`), updating `STORAGE_S3_ENDPOINT` and `NO_PROXY` to `fastgpt-rustfs`. Existing deployments can keep their current storage; see [MinIO to RustFS migration](/en/self-host/docker_minio_to_rustfs) to switch.
- **Default MongoDB version and initialization**: The `main` Compose templates update the default MongoDB version to `8.0.38` (`x86_64` CPUs must meet MongoDB 8.0 instruction set requirements). Replica set initialization and health checks use `mongosh` to wait for a writable primary before starting dependent services, with improved shutdown signal forwarding.
- **Dedicated Plugin database and callback URL**: Docker Compose templates point `fastgpt-plugin`’s `MONGODB_URI` to a separate `fastgpt-plugin` database, explicitly set `DB_MAX_LINK=100` to avoid sharing collections with the main database, add `FASTGPT_BASE_URL=http://fastgpt-app:3000`, and depend on `fastgpt-mongo` health. Custom deployments should configure a main service URL reachable from the Plugin container; if `401` errors appear during file upload callbacks, check this address first, update it, recreate the Plugin container, and retry the Tool. Before replacing an existing deployment’s template, preserve its dedicated Plugin database connection, or back up and migrate existing Plugin data before switching databases.
- **Agent Sandbox template and health check updates**: Compose templates upgrade OpenSandbox Server to `release-1.2.1` and map `host.docker.internal:host-gateway` so it can reach sandbox ports published on the host (add this mapping to `extra_hosts` on `fastgpt-opensandbox-server` in custom Compose deployments using this hostname). `fastgpt-agent-sandbox-proxy` adds `FASTGPT_APP_REQUEST_TIMEOUT_SECS=60`. Health checks for `fastgpt-code-sandbox`, `fastgpt-opensandbox-server`, and `fastgpt-volume-manager` now use built-in `node` or `python` commands, and the static `deploy/k8s/volume-manager.yaml` manifest has been removed (see [OpenSandbox Configuration](/en/self-host/config/sandbox/opensandbox) for Kubernetes volume management).

- App supports mounting `/app/defaultConfig.json`, which participates only in initial setup when all business configuration domains are empty; subsequent file edits do not overwrite database settings. The legacy `config.json` has been completely removed and is no longer read at runtime.
- Commercial edition deployments must explicitly configure `TEAM_MODE` (`single`, `multi`, or `sync`) and restart Pro after changes; the old database team mode no longer applies. `sync` mode also requires `EXTERNAL_USER_SYSTEM_BASE_URL` and fails with an error if it is missing.
- Manage Code Sandbox and MCP SSE under Admin → Subservice configuration; environment variables no longer apply, and deployment defaults can be provided via `/app/defaultConfig.json`.
- **Content moderation Plugin migration**: The legacy built-in Baidu text moderation (`censor.BAIDU_TEXT_CENSOR_CLIENTID` / `censor.BAIDU_TEXT_CENSOR_CLIENTSECRET`), custom censor URL (`censor.customCensorURL`), and per-model `censor` flag in the commercial edition are deprecated and replaced by the `moderation` Plugin system managed by `fastgpt-plugin`.
  - If you used legacy Baidu moderation, go to **Admin Console > Content Moderation > Moderation Policy** to configure and enable the official **Baidu Content Security (`baidu`)** Plugin.
  - If you used a custom moderation URL (`customCensorURL`), install the official **Legacy Custom Moderation (`legacy-custom-censor`)** Plugin to connect your existing HTTP service without code changes, or build a native `moderation` Plugin with `@fastgpt-plugin/sdk-factory`.
  - See the [Content moderation upgrade and migration guide](/en/self-host/migration/content-moderation) for legacy behavior comparisons and field mappings, and the [Content moderation guide](/en/plugin/moderation) for day-to-day configuration, testing, and custom Plugin development.

### Image updates

### Upgrade scripts

Items 1–7 run automatically; items 8–9 are manual Agent Sandbox migration and cleanup tasks (`manual: true`) that an administrator must trigger from **Admin Console → System Upgrade** after verifying the prerequisites.

1. Added **Migrate system configuration** (`20261116_migrate_system_configs`), which runs automatically at startup and blocks App business startup until it succeeds. It imports legacy settings, fills missing fields, and encrypts managed secrets while preserving admin values, explicit clears, Licenses, and instance identity; original legacy configuration data is retained. The migration preserves legacy values that fail the new save rules and logs the affected fields. Admins can correct them after upgrading. External file links and cross-origin access remain restricted if the security configuration is damaged. The task reruns idempotently from the beginning. On failure, correct the issue using the logs, restart the node holding the lease, and wait for the lease to expire so the task can retry automatically.
2. Added **Initialize Dataset vector indexes** (`20261022_initialize_dataset_vector_indexes`), which runs automatically in the background after startup for PostgreSQL without blocking the App: it first verifies and drops the legacy global `vector_index` online, then counts vectors in active Datasets in batches and queues index maintenance jobs. A successful migration means counting and queueing are complete; index builds continue in a globally serial queue. If cleanup or scanning fails, resolve the issue and retry from the upgrade management page to resume from the saved checkpoint. A custom index with the same name but a different definition is preserved and causes an error.
3. PG partial indexes require `halfvec` support (pgvector `0.8.0` or later), permission to create and drop indexes online, and sufficient memory, shared memory, and disk space. Datasets whose indexes are not ready or have failed continue to use exact search, which may increase query time. Failed builds do not automatically retry with a lower resource budget; after the issue is resolved, the next actual vector count queues another attempt. A cache hit does not trigger a retry.
4. Added **Backfill historical chat channels** (`20261104_backfill_chat_publish_source`), which runs independently with batched reads and writes in the background after startup without blocking the App or waiting for long-running tasks in the regular background queue. It fills `publishSource` separately for chats and statistics records without changing legacy fields, identities, messages, or counters. Historical API, MCP, and deleted channels may retain only a type without a recoverable channel ID; unrecognized legacy sources are classified as `unknown` without guessing their channel. Records that previously failed source enum validation can be retried directly from the upgrade management page without modifying legacy data or resetting progress; other conflicting references or invalid data remain recorded as failures and can resume from the checkpoint after repair. Final validation now scans in batches and saves checkpoints, so it can resume at the appropriate batch after an interruption or after invalid data is repaired; legacy checkpoints restart only validation and preserve completed backfills.
5. Added **Backfill API Key types** (`20261104_backfill_openapi_key_type`), which scans all keys in batches, fills missing `type` values as `personal`, and stores valid `appId` values as BSON ObjectId values. Credentials, ownership, quotas, and default target or binding semantics remain unchanged. Repair invalid records and retry from the upgrade management page. Management queries support only normalized data. Legacy-format data present during migration or written by old instances is outside query compatibility support. Legacy records written after the initial scan boundary are not automatically backfilled and require separate normalization.
6. Added **Migrate model pricing** (`20261120_migrate_model_pricing`), which runs independently in the background after the system configuration migration finishes. It fills missing STT pricing types with `duration` and preserves existing rates and explicit `tokens` pricing. It then backfills `maxInputTokensK` for system LLMs in a single transaction and validates both sets of changes. If any legacy limit for a model is below `1`, the migration converts finite limits that lack the new field from millions to thousands of tokens, rounding to the nearest integer with a minimum of `1`. If all finite legacy limits for a model are at least `1`, the migration copies them as thousands of tokens and checks that they are positive integers. Legacy models whose first tier still lacks the new limit use that tier for billing until backfill. The migration preserves the original `maxInputTokens` values so a rolled-back version can read tiers that the new version has not rewritten. Review failures on the upgrade management page, correct them, and retry.
7. Added **Clean up deprecated MongoDB indexes** (`20261123_cleanup_mongo_indexes`), which runs independently in the background after startup. The migration drops listed indexes only when the name, keys, and options all match, preserving custom indexes with different definitions. If a replacement index is still unavailable after 30 minutes by default, the migration keeps the old index and records a failure. Resolve the issue and retry from the upgrade management page. `MONGO_DEPRECATE_INDEX` is enabled by default. Set it to `false` or `0` to inspect indexes and record pending cleanup without dropping them.
8. Added **Migrate legacy sandboxes to OpenSandbox (.tar.zst)** (`20261117_migrate_sandbox_to_opensandbox`, **manual**): 4.18.0 stores runtime records in MongoDB `agent_sandbox_instances_v3` and `.tar.zst` cold archives under S3 `sandbox/archive-v2/`. Restarting alone does not run this task. Active `agent_sandbox_instances_v2` records not yet migrated (`sealosdevbox`, legacy `sandbox/archive/*/package.zip`, or legacy `/workspace` volumes) are blocked at runtime with `agentSandboxMigrationInProgress` (`409`); deployments with no active legacy sandboxes (or only soft-deleted orphan records) complete quickly as a no-op. **Cutover order (mixed 4.17.x and 4.18.0 rolling upgrades are not supported)**:
   1. **Stop all 4.17.x App and Pro nodes first**.
   2. **Upgrade sandbox components to `v0.5.0+`**: update `AGENT_SANDBOX_OPENSANDBOX_IMAGE` (including custom derived images), `fastgpt-agent-volume-manager`, and `fastgpt-agent-sandbox-proxy` to `v0.5.0+`, and OpenSandbox to `release-1.2.1`. If active `sealosdevbox` instances exist, keep `AGENT_SANDBOX_SEALOS_BASEURL` and `AGENT_SANDBOX_SEALOS_TOKEN` (plus `AGENT_SANDBOX_SEALOS_WORK_DIRECTORY` if customized) until both migration and cleanup finish.
   3. **Start 4.18.0 services** and wait for the startup migration (item 1) to succeed.
   4. **Manually run this task in Admin Console → System Upgrade**: reads `v2` read-only across `runningDevbox` → `stoppedDevbox` → `legacyArchives` → `validation` and writes to `v3` and `sandbox/archive-v2/`, leaving `v2` records, remote Devboxes (`pause`d), old `/workspace` volumes, and old `package.zip` files untouched. Fix any failed items and retry from checkpoint.

   **Post-migration verification**: once status is `Completed` with zero unresolved failures, spot-check existing Agent sessions and Skill editors for cold restore, file read/write, terminal/preview connections, and Skill publishing.

9. Added **Clean up legacy sandbox resources** (`20261117_cleanup_legacy_sandbox_resources`, **manual, depends on item 8**): requires zero active unmigrated `v2` records in preflight; trigger manually only after verifying 4.18.0 in production (keep Sealos ENV until remote Devbox cleanup finishes, then remove). After verifying each active sandbox's replacement `.tar.zst` archive exists under `sandbox/archive-v2/`, it idempotently deletes legacy remote Devboxes, old `/workspace` volumes, legacy `sandbox/archive/*/package.zip` objects, and legacy `agent_sandbox_instances_v2` records (including `v2` orphans for soft-deleted sources and residual `deleting` rows). **Rollback boundaries**:
   - **Sandbox layer**: before item 9 runs, legacy `v2` records, Devboxes, `/workspace` volumes, and `package.zip` objects remain untouched, requiring **no PVC snapshots and no S3 sandbox archive restore**. On a shared OpenSandbox control plane, 4.17.5 looks up instances by `sessionId` and attaches to or `resume`s `Running`/`Paused` instances. Therefore, **after stopping 4.18.0 App/Pro nodes and before restoring 4.17.x traffic**, terminate/delete any 4.18.0 trial sandboxes by their remote instance IDs in `agent_sandbox_instances_v3` (**do not merely `Pause`**; new external PVCs set `deleteOnSandboxTermination: false`, so termination preserves volumes and archives) and confirm no recoverable instance remains for that `sessionId`—or run 4.18.0 trials against an isolated OpenSandbox control plane. Then switch sandbox components back to `v0.4.x`, start 4.17.x, and verify on a sandbox that was `running` before upgrade and cold-restored in 4.18.0 that 4.17.x reconnects to its legacy `/workspace` volume and Devbox (randomized-suffix `v3` PVCs remain isolated from legacy volumes and can be cleaned up if the upgrade is abandoned).
   - **Whole-app rollback**: due to other non-backward-compatible 4.18.0 migrations (such as model pricing tiers and API Key normalization) and `.tar.zst` Skill versions unreadable by 4.17.x, whole-app rollback still requires restoring pre-upgrade DB backups (plus S3 backups if non-sandbox assets were deleted or `.tar.zst` Skill versions were published).
   - **Irreversibility**: once item 9 runs, remote Devboxes, old `/workspace` volumes, legacy `package.zip` objects, and `v2` records are permanently deleted.

## 🚀 New features

1. **[Tools and channels]** Added App API Keys bound to a single App, managed separately from personal keys on the App publishing page. App managers share control of these keys for that App’s chats and chat management, independently of the owning member’s App permissions; the Commercial edition transfers key ownership through resource handover, and deleting an App also removes its bound keys.
2. **[Tools and channels]** Chat and related management APIs now share support for external user IDs and Team member proxies. Use `customUid` to narrow access to a user’s history, messages, files, citations, and Sandbox resources; personal keys with proxy permission can use `authProxy` to act with the represented member’s permissions.
3. **[Tools and channels]** Chat logs now include an “Authorizer” column, hidden by default, separate from “User” to distinguish your users from the authenticated Team member. API `customUid` values appear unchanged as the user, and CSV exports follow the selected columns. Log columns now size to their contents so long UIDs do not squeeze member names. App chat logs now load as you scroll. Search by title keyword or enter the full session ID for an exact match. Each App remembers your search mode, and CSV exports use the current mode and filters.
4. **[Tools and channels]** Added FastGPT branding to public share pages across desktop, mobile, and embedded layouts; when enabled, new links show it by default, and desktop visitors can dismiss it for the current visit. Persistent hiding requires a valid plan entitlement, configurable per plan or individual subscription in the Commercial edition; legacy links without a saved preference remain exempt, while links with a saved hiding preference show branding again if the entitlement becomes invalid and hide it again when the entitlement is restored.
5. **[Tools and channels]** Added Plugin-based content moderation, disabled by default. When enabled, policies can independently check user input, model context, and final output, including streamed output, with configurable actions for suspected risks and moderation service errors. Admins can configure Plugins, switch the active service, test moderation results, and view global moderation records. FastGPT selects the first configured Plugin automatically when no service is active. The Moderation Policy page updates its navigation based on whether moderation is on and a Plugin is active. Uninstalling an inactive Plugin preserves unsaved policy changes. Chat details show the moderation records for that chat.
6. **[Tools and channels]** Added the official beta CLI, `@fastgpt/cli`, with login, profile switching, identity and environment checks, Dataset management and joint search, and App chat and history commands. JSON output and command metadata discovery support scripts and Agents. It also supports file and link imports, Collection and chunk management, and discovery of available Apps, models, system Tools, and Code Sandbox dependencies. Edit, validate, and compile Workflows offline, or connect to FastGPT to fetch authorized templates, pull App drafts or historical versions, compare drafts, debug, run test assertions, and check for sync conflicts before saving or publishing. Output supports field selection, value extraction by path, and compact command discovery.
7. **[Tools and channels]** The official TypeScript and JavaScript SDK (`@fastgpt/sdk`) and Python SDK (`fastgpt-sdk`) are both in beta. They provide typed access to chat, Datasets, App logs, and models through System OpenAPI, with support for streaming chat, resuming interactive Workflows, and automatic pagination. The Python SDK provides synchronous and asynchronous clients for Python 3.10 or later.
8. **[Tools and channels]** The MCP client supports outbound proxies (`HTTP_PROXY`, `HTTPS_PROXY`, and `ALL_PROXY`), delegating target DNS resolution and internal-network egress controls to the proxy layer. Destinations that match `NO_PROXY` continue to connect directly with local address checks.
9. **[Workflows and Agents]** Workflow Agent Nodes can now be added from the template panel and used as Tool Nodes by other Agents. Dataset inputs support variable bindings; standalone ChatAgent Apps can also be referenced as Workflow child Apps or Agent Tools, with file inputs and resumable interactions for composing multi-Agent Workflows.
10. **[Workflows and Agents]** Added MCP and HTTP Toolkit Nodes that you can configure directly in a Workflow without first creating a standalone Tool App. Customize child Tool descriptions and authentication, debug each Tool, and let Tool call Nodes use the latest remote Tool definitions at runtime.
11. **[Workflows and Agents]** Commercial edition Workflow Builder can build, validate, and repair Workflows directly from clear creation or modification requests, while still waiting for preview confirmation when you ask to review a proposal first. Valid candidates can be delivered directly; you still apply them to the canvas manually. If a run ends naturally without delivering a candidate, the same Agent checks requirement coverage in its existing context.
12. **[Workflows and Agents]** Commercial edition Workflow Builder supports switching between independent tasks within a session, saving each task’s requirements, proposals, and draft separately so work can continue from saved data after context compression or an interrupted run. Recovery still checks task status and the canvas baseline; unsaved drafts may be lost if the sandbox is lost.
13. **[Workflows and Agents]** Added fullscreen viewing for simple App, ChatAgent, and Workflow debug views and the complete response dialog, preserving the current content when switching sizes. Entering fullscreen moves outside keyboard focus into the debug view. Press Esc to exit. The Workflow debug panel can also be resized by dragging its edge, making long responses and run details easier to read.
14. **[Workflows and Agents]** With vision enabled, FastAgent and Pi Agent can use images returned by MCP, HTTP, Workflow Tools, Plugins with multimodal output, and Sandbox file Tools in the next model turn. Each Tool result can pass up to `4` images. Text results remain available if an image fails to load or vision is off. Downstream Nodes can still use the Plugin’s output values.
15. **[Workflows and Agents]** Publish multiple Skills in one package with `SKILL.md` files at any folder depth. Publishing skips dependency folders and invalid Skill files and requires at least one valid Skill.
16. **[Models and billing]** System models now support an “Upcoming deprecation” flag in model management and model and speech selectors; Commercial edition admins can create notification plans with multiple rounds for Teams whose currently published Apps or Datasets statically use these models, sending in-app messages with optional SMS or email. Plans support failure inspection, run recovery, retries, and termination, and stop new deliveries at the deadline; model removal remains a separate action.
17. **[Models and billing]** Commercial edition Team models can now use custom request URLs and authentication through configuration APIs or templates as a transitional option for direct chat, Agent, embedding, reranking, and speech requests, retaining endpoint settings after edits. Endpoints undergo safety checks when saved and requested, including redirect restrictions; model lists hide endpoint and authentication details.
18. **[Models and billing]** OpenAI and Azure Model providers now offer Auto, Responses, and Chat Completions as upstream chat protocols, with new providers defaulting to automatic selection based on the model. This affects only chat models, and the upstream must support the selected protocol.
19. **[Models and billing]** System LLMs support separate rates per million tokens for cache reads and creation. Omitted rates inherit the tier’s input rate, and a rate of 0 makes that usage free. Usage details show recorded cache counts, and the channel dashboard estimates Points using current rates. See [Model configuration](/en/self-host/config/model/intro).
20. **[Models and billing]** Model management now supports dragging models into a custom order and canceling before saving; the root account can reorder system models, and with team models enabled in the Commercial edition, members with the “Install model” permission can reorder their own models. “Available models” groups your own team models, shared team models, and system models in that order and applies the custom order within each group; JSON configuration updates preserve this order, which the client also uses for its final system-model fallback. Newly created or newly imported models appear at the top of their group without changing the relative order of existing models.
21. **[Models and billing]** Model tables with permission configuration now show creators and identify system models separately. Member display pages can load current creator details, while shared-link catalogs do not expose member information.
22. **[Models and billing]** Speech recognition models now support rates per `60` seconds or separate rates per million input and output tokens. Model management, the public pricing page, and usage details reflect the selected billing type; API, Lark, and WeChat Official Account entry points record usage against the model actually called.
23. **[Models and billing]** Usage in the Commercial edition now supports mutually exclusive member, department (including subdepartments), or group filters, with the same scope applied to details, charts, and CSV exports. Selections use current organization and group memberships; members with Team management permission can view usage for the selected members, while other members can view only their own usage.
24. **[Models and billing]** System models can now be imported in batches from system channels: FastGPT fetches the upstream channel catalog, filters out already installed models, automatically matches the most specific preset template (or lets you configure a blank template), binds imported models to the selected channel, and reports per-model import results.
25. **[Datasets and files]** Added optional MongoDB vector storage. Setting a separate search connection with `SEARCH_MONGO_URL` gives MongoDB priority over other vector stores. Use it for new vector stores, since FastGPT does not migrate existing vectors automatically. The search database requires MongoDB `8.3+` and `mongot`. It uses `1536`-dimensional unit vectors and an HNSW INT8 index, chooses exact or approximate search based on the number of vectors that match the filters, and reranks results using the original vectors.
26. **[Datasets and files]** With Dataset enhancement enabled in the Commercial edition, the template FAQ import API now supports optional automatic index generation using both questions and answers as input. Automatic indexing tasks that exceed the processing length limit fall back to standard vector indexing, retaining each entry and its input order.
27. **[Datasets and files]** Dataset search adds a rerank candidate limit of `10–100` chunks, with a default of `100`. Candidates are sent to the rerank model in text recall order after fusion and deduplication, helping balance search quality, latency, and model load; after successful reranking, text chunks beyond the candidate limit are excluded from weighted fusion so they cannot bypass the similarity filter.
28. **[Datasets and files]** Added a unified Dataset search API for joint searches across Datasets, text or image queries, and results limited by chunk count or token budget. It supports reranking, query expansion, and Commercial edition metadata filters; joint vector searches require the same Embedding model.
29. **[Datasets and files]** API file Datasets now support batch deletion by external file or directory IDs through `datasetId + apiFileIds`, including the corresponding derived folders and child documents, without first looking up internal Collection IDs. Deletion still requires ownership of each deletion root.
30. **[Datasets and files]** Use the column headers in a Dataset’s Collection list to sort by name, creation time, or update time in either direction. Changing the sort returns the list to the first page and keeps the current search and tag filters.
31. **[Teams and permissions]** The root account can search and switch to any available Team to manage its resources and members, with switches recorded in audit logs. Membership created for cross-Team administration does not consume tenant seats or change the Team’s actual owner when switching.
32. **[Teams and permissions]** Commercial edition Team audit logs now have a Resource column with links to associated Apps, Tools, Datasets, Collections, and Skills. Deleted resources are marked and retain their recorded names when available. Details highlight what changed, and the list and CSV are sorted by operation time, newest first. Combine date, member, and event filters. The default range is the most recent `7` local calendar days including today, and you can select older dates and inactive members. Signed-in members with Team management permission can export all matching records as localized CSV, up to `50000` records per export. Narrow the filters if you exceed the limit. The CSV includes associated resources and uses the query start offset for timestamps. Each export request creates an audit record. Collection audit logs cover creation, renaming, moves, enable and disable actions, tag changes, restored permission inheritance, and sync attempts. They also cover signed-in users viewing source content or exporting Q&A from Collection details. Details can show the associated Dataset and relevant paths. Password sign-in logs can show the IP address and its region when available.
33. **[Teams and permissions]** Commercial edition user management APIs now include Team memberships, member names, and department paths. Team member lists also return login usernames to distinguish accounts from member identities.
34. **[System and operations]** Added an admin instance configuration center with settings for core services, security, resources, and subservices, filtered by deployment edition; shared settings are also available in the Community edition. Select parsing providers, test service connectivity, and save changes across configuration domains. The form validates settings on save, marks fields with errors, and preserves the draft if concurrent edits conflict. Managed secrets are encrypted, and the form shows only whether they are configured.
35. **[System and operations]** Commercial edition admins can use **Ops Dashboard → Performance** to view Dataset search latency trends, failure rates, and stage timings by time range, search mode, and index size.
