## Version Policy

Starting with 4.14.11, FastGPT uses separate version names for stable releases and rapid-development releases:

1. Two stable release lines are maintained. For example, while new features are developed in 4.16.x, fixes are maintained for 4.14.x and 4.15.x.
2. Stable releases have no suffix, such as 4.14.11, 4.14.12, 4.15.0, and 4.15.1. A fix for 4.14.11 is released as 4.14.12 and applied to the 4.15.x stable line. These maintenance releases contain fixes and preserve the existing feature set.
3. Rapid-development releases use a beta suffix, such as 4.16.0-beta.1, 4.16.0-beta.2, and 4.16.0-beta.3.
4. A development line becomes a stable release approximately every 2 months. A consolidated upgrade script lets you apply all migrations from that development cycle with one request.

For stable deployments, choose releases without a beta suffix. Dedicated maintenance releases provide fixes while preserving the existing feature set.

## Upgrade Steps

Upgrading FastGPT usually involves two steps:

1. Update the image
2. Run the upgrade initialization script

## Updating Images with Docker Compose

Simply modify the `image:` field in the `yml` file, then run:

```bash
docker-compose pull
docker-compose up -d
```

## Running the Upgrade Initialization Script

After updating the images, check the version notes in the documentation. Versions that require an upgrade script are typically labeled with "includes upgrade script". Open the corresponding documentation and follow the instructions to run the **upgrade script** -- in most cases, you just need to send a `POST` request.

## FAQ

### Why do I need to run an upgrade script?

Starting with FastGPT 4.17+, the application automatically runs a distributed startup migration executor. Nodes coordinate via MongoDB leases to run registered schema transformations sequentially with checkpoint cursors. For large datasets, schedule upgrades during maintenance windows to allow sufficient time for data backfill.

### What is `{{host}}`?

`{{}}` denotes a variable. `{{host}}` refers to a variable named "host", which is your server's domain name or IP address.

On Sealos, open the app details and look under **Network Configuration**. The **External Address** column shows the public URL; use its domain name for `{{host}}` when the request already includes `https://`.

![App details showing the external address and environment variables](/imgs/optimized/updateImageSealos4.png.webp)

### How to get the rootkey

You can find it in the `environment` section of your `docker-compose.yml` file -- it's the value of `ROOT_KEY`.

On Sealos, you can find it in the environment variables panel shown in the image above.

### How to upgrade across multiple versions

1. Read every intervening release note and follow the documented upgrade path, including required intermediate versions.
2. Back up MongoDB, vector storage, object storage, and configuration consistently; verify restoration in a separate environment.
3. Rehearse the upgrade with a copy of production data. Check startup migrations and run only the manual steps required by those releases.
4. Upgrade during a maintenance window and verify login, ingestion, retrieval, chat, and file downloads before restoring traffic.
5. Prepare a rollback using compatible application images and data backups. Data migrations can require restoring the prior data state together with the prior version.
